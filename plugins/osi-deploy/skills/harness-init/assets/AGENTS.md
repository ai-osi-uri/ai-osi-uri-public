## 4. セッションの進め方（必ず守る作業手順）

1. **開始時**: `claude-progress.md` と `feature_list.json` を読み、現在地と次にやるべき機能を把握する。
2. **着手**: `feature_list.json` から **最優先の未完了機能を1つだけ** 選び、`status` を `in_progress` にする。
   - **同時に `in_progress` にできる機能は常に1つだけ**（やりすぎ・中途半端を防ぐ）。
3. **実装**: 選んだ機能のスコープ内だけを変更する。関係ない箇所には触らない。
4. **検証**: その機能の `verification` 手順を実際に実行する。
5. **記録**: テスト出力などの**証拠（evidence）を残してから** `status` を `passing` にする。
6. **終了時**: 「セッション終了の作法」（下記）を実行してから終わる。

## 5. 完了の定義（Definition of Done）★最重要

ある機能を「完了（passing）」と呼べるのは、**次のすべて**を満たしたときだけ:

- [ ] `verification` に書かれた手順を実際に実行した
- [ ] 期待どおりの結果（ユーザーに見える振る舞い）を確認した
- [ ] その**証拠**（テスト出力・ログ・スクショ等）を `feature_list.json` の `evidence` に記録した
- [ ] フル検証コマンドが通っている
- [ ] 中途半端な未記録の作業を残していない

> 「たぶん動くはず」「実装したので完了とします」は**禁止**。証拠がなければ `passing` にしない。

### 5-1. 「期待どおり」の判定基準（不変条件）

`verification` を設計するとき、正常に通ることだけでなく次が成り立つことを確かめる。
手順やケース一覧はここに書かない。境界やケースは仕様から自分で洗い出すこと。

1. 仕様に書かれた振る舞いは成り立ち、書かれていない振る舞いは起きない。
2. 入力と状態の境界は仕様から自分で洗い出し、その両側を確かめる。
3. 操作の前後でデータに矛盾が残らない。
4. 商用でこれに反する事象が起きたら、ここに行を足してから直す。
