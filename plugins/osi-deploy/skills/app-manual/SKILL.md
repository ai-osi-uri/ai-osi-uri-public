# アプリの使い方マニュアル（atomic）

アプリを公開しても、**現場が使えなければ納品は終わっていない**。このスキルは、
公開済みアプリの手順書を実装から起こし、Drive に格納するところまでを担当する。

## なぜ実装から起こすのか

手順書がズレる原因は、ほぼ全部これ。**作った本人の記憶から書く**。

実際に起きた事故（AI同友会）：ログインをマジックリンクからパスワードに変え、受付画面を
開催回の下に移したあと、マニュアルだけが旧仕様のまま残った。配られた運営が
「書いてある画面が無い」で止まる。書いた時点では正しかったので、誰も間違いに気付けない。

だから、**マニュアルの記述はすべて現物のコードに出典がある状態にする**。
会話の履歴・以前のマニュアル・記憶は出典にならない。

---

## 入力契約

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| `REPO_DIR` | ✅ | 対象アプリのローカル clone |
| `APP_URL` | ✅ | 公開 URL（`https://example.com`）。フル URL で受け取る |
| `APP_NAME` | ✅ | 資料タイトルに使う名前 |
| `AUDIENCE` | 任意 | `internal`（運営・現場）/ `enduser` / `both`。既定 `internal` |
| `DRIVE_DIR` | 任意 | 格納先。未指定なら drive-record.md の規則で決める |
| `PREV_VERSION` | 任意 | 既存マニュアルのパス。あれば版を上げて旧版を退避する |

---

## Step 1: 実装から材料を集める（推測禁止）

コードを読んで、以下を**実際の文字列のまま**書き出す。ここで拾えなかったものは
マニュアルに書かない。「たぶんこうなっている」で埋めない。

| 集めるもの | どこから | 何に使うか |
| --- | --- | --- |
| ルート一覧 | `app/**/page.tsx`・`route.ts`（Next.js）、ルータ定義 | 画面の地図・URL |
| 画面の名前とナビ | サイドバー / ヘッダのコンポーネント | 章立てと呼び方 |
| ボタン・ラベル・プレースホルダ | JSX の文字列 | 手順の文中に鍵括弧で引用する |
| 操作の結果 | サーバーアクション / API ハンドラ | 「押すと何が起きるか」 |
| メール文面 | メール送信モジュールのテンプレ | 自動送信メールの一覧表 |
| 認証方式と権限 | 認証ライブラリ / ミドルウェア / ガード | ログインの章・入れる人の範囲 |
| 課金 | 決済 SDK の呼び出しと Webhook | 本番かテストか・課金の起点 |
| 定期実行 | cron / スケジューラのルート | 「自動で動くもの」の説明 |

**照合ゲート**：書き終えたら、マニュアル中の画面名・ボタン名・URL を1つずつ
コードに grep して当てる。当たらない語が1つでもあれば、その記述を直すまで先へ進まない。

---

## Step 2: 読み手を決めて2版に分ける

| | 運営・現場版（internal） | エンドユーザー版（enduser） |
| --- | --- | --- |
| 読む人 | 管理画面を触る人 | 会員・顧客 |
| 中身 | ログイン・日々の操作・事故の防ぎ方 | 申し込み・自分の画面の使い方 |
| 書いてよいこと | 審査基準・課金の状態・削除の影響 | 本人が自分で操作できる範囲だけ |
| 禁止 | — | 内部の判断基準・他人の情報・管理画面の存在 |

`both` のときは**別ファイル**にする。1つの資料に混ぜると、外に出せなくなる。

---

## Step 3: 文言の規則

現場に配る資料なので、書き方を固定する。

1. **URL はフルで書く。パス表記を使わない。**
   `/admin/login` ではなく `https://example.com/admin/login`。読む人はブラウザに
   打ち込む。パスだけ書かれても何をすればいいか分からない。
2. **画面の言葉をそのまま鍵括弧で引く。**
   「＋ 開催回を作る」を押す、と書く。「新規作成ボタン」と言い換えない。
   言い換えた瞬間、画面と資料が別語彙になって探せなくなる。
3. **命令形にしない。**「〜してください」「〜します」。運営は部下ではない。
4. **専門語を持ち込まない。** ルーティング・レコード・エンドポイントは書かない。
   「画面」「一覧」「行」で足りる。
5. **押すと何が起きるかまで書く。** 手順だけ書いて結果を書かないと、
   押していいのか判断できない。特に**取り消せない操作**は必ず影響範囲を書く。
6. **自動で動くものは「手で送らなくてよい」と明記する。**
   書いていないと、運営が親切心で二重に送る。

---

## Step 4: 構成（internal 版の既定）

アプリによって増減させてよいが、この順序は崩さない。**全体像 → 入口 → 地図 →
日々の操作 → 自動で動くもの → 事故の防ぎ方**。

| # | ページ | 中身 |
| --- | --- | --- |
| 1 | 表紙 | アプリ名・用途・主要 URL を全部（管理・利用者・申込）・版と日付 |
| 2 | 全体の流れ | 誰が何をするか。**人が手を動かす箇所を先に数で言い切る**（「触るのは4か所」） |
| 3 | ログインする | 権限ごとに入口が違うなら、その違いを最初に。認証方式・パスワード要件 |
| 4 | 画面の地図 | ナビの項目を全部並べ、何をする場所かを1行で |
| 5〜 | 日々の操作 | 業務の順に1ページ1手順。番号付きの手順＋結果 |
| N-2 | 自動で送られるメール | きっかけ・宛先・内容の表。送信元アドレスも |
| N-1 | 利用者から見た画面 | 問い合わせに答えられるように |
| N | 気をつけること | 取り消せない操作・本番課金・忘れると止まるもの。最後に問い合わせ先 |

**「気をつけること」は必ず入れる。** 事故は操作の難しさではなく、
影響範囲を知らないまま押すことで起きる。

---

## Step 5: 刷る

`osi-docs` の `pptx-custom` があればそれを使い、社内体裁（ブランド配色・レイアウト規約）
に揃える。無ければ基盤 `pptx` スキルで刷る。

- 16:9・1ページ1トピック
- 手順は番号の丸と本文の2段。結果は本文の下に小さく
- 注意は帯（危険は赤系、通常は生成りの背景）
- ページ内に**説明のためだけの図を足さない**。手順書は読むもので、眺めるものではない

---

## Step 6: 目視 QA（必須ゲート）

pptx を書いたら、**必ず画像にして自分の目で見る**。テキストの量は書いている間は
分からず、はみ出しは生成物を見るまで表面化しない。

```bash
soffice --headless --convert-to pdf --outdir "$QA" "$OUT"
pdftoppm -r 80 -png "$QA"/*.pdf "$QA"/p
```

全ページを開いて確認する：

- [ ] 文字がスライド下端からはみ出していないか（**いちばん多い事故**）
- [ ] 箱から本文が溢れていないか。行が重なっていないか
- [ ] URL が途中で折れて読めなくなっていないか
- [ ] Step 1 で集めた語と、資料上の語が一致しているか

はみ出しは、行間や開始位置を詰めて**作り直してから**もう一度見る。
1回で通ることは少ないので、通るまで回す。

---

## Step 7: 格納と版

- 保存先は `drive-record.md` と同じ案件フォルダ配下（運営資料の置き場）
- ファイル名は `{アプリ名}_使い方_v{n}.pptx` / 外部版は `..._利用ガイド_v{n}.pptx`
- **旧版は `_旧版/` に退避する。同じ場所に並べない。**
  中身が食い違う2本が並ぶと、必ず古いほうが配られる
- 版を上げたら、何が変わったかを1〜2行で伝える（読み手は差分だけ知りたい）

---

## 呼び出し元との約束

### create-app から

共通後処理の Drive 記録（Phase N-1）の直後、完了レポートの前に実行する。
接続情報の README と使い方マニュアルが**同時に**揃った状態で納品する。

### update-deploy から

**毎回は作らない。** 以下のどれかに触れた修正のときだけ再生成する。

- 画面の追加・削除・移動（ルートが変わった）
- ナビ・ボタン・ラベルの変更
- ログイン方式・権限の変更
- メール文面の追加・削除
- 課金の条件・金額の変更

文言の微修正・スタイル調整・内部リファクタでは動かさない。
迷ったら「マニュアルの記述と食い違うか」で判断する。

---

## やってはいけないこと

- 記憶・会話履歴・以前のマニュアルから書く（**必ずコードから引く**）
- 実装を確かめずに「たぶんこう動く」と書く
- パスだけを書いてフル URL を書かない
- 画面のラベルを分かりやすく言い換える
- 目視 QA を飛ばして納品する
- 内部の判断基準をエンドユーザー版に混ぜる
- 接続情報・API キー・環境変数の値を載せる（技術メモは drive-record.md の担当）
