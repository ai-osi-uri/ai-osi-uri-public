# アプリの使い方マニュアル（atomic）

アプリを公開しても、**現場が使えなければ納品は終わっていない**。このスキルは、
公開済みアプリの手順書を実装から起こし、Drive に格納するところまでを担当する。

## なぜ実装から起こすのか

手順書がズレる原因は、ほぼ全部これ。**作った本人の記憶から書く**。

実際に起きた事故（AI同友会）：ログインをマジックリンクからパスワードに変え、受付画面を
開催回の下に移したあと、マニュアルだけが旧仕様のまま残った。配られた運営が
「書いてある画面が無い」で止まる。書いた時点では正しかったので、誰も間違いに気付けない。

だから、**マニュアルの記述はすべて現物のコードに出典がある状態にする**。
会話の履歴・以前のマニュアル・記憶は出典にならない。

---

## 入力契約

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| `REPO_DIR` | ✅ | 対象アプリのローカル clone |
| `APP_URL` | ✅ | 公開 URL（`https://example.com`）。フル URL で受け取る |
| `APP_NAME` | ✅ | 資料タイトルに使う名前 |
| `AUDIENCE` | 任意 | `internal`（運営・現場）/ `enduser` / `both`。既定 `internal` |
| `DRIVE_DIR` | 任意 | 格納先。未指定なら drive-record.md の規則で決める |
| `PREV_VERSION` | 任意 | 既存マニュアルのパス。あれば版を上げて旧版を退避する |

---

## Step 1: 実装から材料を集める（推測禁止）

コードを読んで、以下を**実際の文字列のまま**書き出す。ここで拾えなかったものは
マニュアルに書かない。「たぶんこうなっている」で埋めない。

| 集めるもの | どこから | 何に使うか |
| --- | --- | --- |
| ルート一覧 | `app/**/page.tsx`・`route.ts`（Next.js）、ルータ定義 | サイトマップ・URL |
| 画面の名前とナビ | サイドバー / ヘッダのコンポーネント | 章立てと呼び方 |
| ボタン・ラベル・プレースホルダ | JSX の文字列 | 手順の文中に鍵括弧で引用する |
| 操作の結果 | サーバーアクション / API ハンドラ | 「押すと何が起きるか」 |
| メール文面 | メール送信モジュールのテンプレ | 自動送信メールの一覧表 |
| 認証方式と権限 | 認証ライブラリ / ミドルウェア / ガード | ログインの章・入れる人の範囲 |
| 課金 | 決済 SDK の呼び出しと Webhook | 本番かテストか・課金の起点 |
| 定期実行 | cron / スケジューラのルート | 「自動で動くもの」の説明 |

**照合ゲート**：書き終えたら、マニュアル中の画面名・ボタン名・URL を1つずつ
コードに grep して当てる。当たらない語が1つでもあれば、その記述を直すまで先へ進まない。

---

## Step 2: 読み手を決めて2版に分ける

| | 運営・現場版（internal） | エンドユーザー版（enduser） |
| --- | --- | --- |
| 読む人 | 管理画面を触る人 | 会員・顧客 |
| 中身 | ログイン・日々の操作・事故の防ぎ方 | 申し込み・自分の画面の使い方 |
| 書いてよいこと | 審査基準・課金の状態・削除の影響 | 本人が自分で操作できる範囲だけ |
| 禁止 | — | 内部の判断基準・他人の情報・管理画面の存在 |

`both` のときは**別ファイル**にする。1つの資料に混ぜると、外に出せなくなる。

---

## Step 3: 文言の規則

現場に配る資料なので、書き方を固定する。

1. **URL はフルで書く。パス表記を使わない。**
   `/admin/login` ではなく `https://example.com/admin/login`。読む人はブラウザに
   打ち込む。パスだけ書かれても何をすればいいか分からない。
2. **画面の言葉をそのまま鍵括弧で引く。**
   「＋ 開催回を作る」を押す、と書く。「新規作成ボタン」と言い換えない。
   言い換えた瞬間、画面と資料が別語彙になって探せなくなる。
3. **命令形にしない。**「〜してください」「〜します」。運営は部下ではない。
4. **専門語を持ち込まない。** ルーティング・レコード・エンドポイントは書かない。
   「画面」「一覧」「行」で足りる。
5. **押すと何が起きるかまで書く。** 手順だけ書いて結果を書かないと、
   押していいのか判断できない。特に**取り消せない操作**は必ず影響範囲を書く。
6. **自動で動くものは「手で送らなくてよい」と明記する。**
   書いていないと、運営が親切心で二重に送る。

---

## Step 4: 構成（internal 版の既定）

アプリによって増減させてよいが、この順序は崩さない。**全体像 → 入口 → サイトマップ →
日々の操作 → 自動で動くもの → 事故の防ぎ方**。

| # | ページ | 中身 |
| --- | --- | --- |
| 1 | 表紙 | アプリ名・用途・主要 URL を全部（管理・利用者・申込）・版と日付 |
| 2 | 全体の流れ | 誰が何をするか。**人が手を動かす箇所を先に数で言い切る**（「触るのは4か所」） |
| 3 | ログインする | 権限ごとに入口が違うなら、その違いを最初に。認証方式・パスワード要件 |
| 4 | サイトマップ | ナビの項目を全部並べ、何をする場所かを1行で。「画面の地図」のような和語の言い換えは使わない |
| 5〜 | 日々の操作 | 業務の順に1ページ1手順。番号付きの手順＋結果 |
| N-2 | 自動で送られるメール | きっかけ・宛先・内容の表。送信元アドレスも |
| N-1 | 利用者から見た画面 | 問い合わせに答えられるように |
| N | 気をつけること | 取り消せない操作・本番課金・忘れると止まるもの。最後に問い合わせ先 |

**「気をつけること」は必ず入れる。** 事故は操作の難しさではなく、
影響範囲を知らないまま押すことで起きる。

---

## Step 5: 刷る

**先に `osi-docs` の `pptx-custom` を Read する。** あれは描画エンジンで、社内体裁
（配色・余白・衝突回避・単位表記の絶対ルール）を持っている。無ければ基盤 `pptx` スキル。

**`deck-composition` は経由しない。** 構成は本スキルの Step 4 が持っている。
pptx-custom は「slide-plan.md を受け取る」前提で書かれているが、手順書ではこの Step 4 の
表が slide-plan の役割を果たす。ここで構成を考え直すと、業務の順序が崩れる。

実装は python-pptx（`Presentation` から自前で組む）。テンプレ編集より、
座標を関数で持てるぶん事故が少ない。

### 体裁の型

- 16:9（10.0 × 5.625 インチ）・1ページ1トピック・外余白 0.66"
- **見出しは「明朝の通し番号 ＋ 見出し」。タイトル下にアクセント線を引かない**
- 手順は「番号 ＋ 太字の一行 ＋ 灰色の結果一行」、行と行は細い罫で分ける
- 注意・補足は帯にせず、**差し色の一行**として置く。帯を多用すると全部が同じ強さになる
- 各ページ下端に、そのページの名前（ランナー）とノンブルを小さく

### 配色は案件ごとに決める。前の案件の定数をコピーしない

**濃い1色（支配色）＋ 紙白 ＋ 低彩度の差し色1色**の3色で組む。差し色は
**線・通し番号・注意の一行にしか使わない**。塗り面には使わない。

濃い面が全体の6割前後を占めるように、表紙・要所・最終ページを面で敷いて挟む。
文字だけのページが続くと、めくったときのリズムが死ぬ。

例（IB CLINIC・2026-09）：墨黒 `#171614` / 紙白 `#F7F5F1` / 黄具 `#9A7B3F`。
それ以前は濃紺 `#141B2E` × 金 `#B8963F` だったが、**顧客ごとに取り直している**。

### 図を必ず入れる（旧版の「図を足さない」は誤りだった）

画面や物を操作する手順書で、その画面や物が一度も出てこないのは不親切。
ただし入れてよいのは**説明の役に立つ図だけ**で、装飾のための図は入れない。

- 画面 → ワイヤーフレーム（レール・本文・右パネルを実寸比の矩形で）
- 操作対象 → その形（歯・部材・帳票など）を図形で
- 選択肢の比較 → 同じ図を並べて、選ばれている方だけ差し色の輪郭で立てる
- 金額・数量の比較 → 値に比例した細いバーを添える

**AI 画像生成を使わない。** 日本語 UI も含めて文字が崩れる。図形コードで描く。
描き方と使い回せるヘルパーは [references/deck-recipe.md](references/deck-recipe.md)。

## Step 6: 目視 QA（必須ゲート）

pptx を書いたら、**必ず画像にして自分の目で見る**。テキストの量は書いている間は
分からず、はみ出しは生成物を見るまで表面化しない。

```bash
soffice --headless --convert-to pdf --outdir "$QA" "$OUT"
pdftoppm -jpeg -r 110 "$QA"/*.pdf "$QA"/p
```

全ページを開いて確認する：

- [ ] 文字がスライド下端からはみ出していないか（**いちばん多い事故**）
- [ ] 箱・帯から本文が溢れていないか。行が重なっていないか
- [ ] 段組みの列幅で見出しが不自然に折り返していないか
- [ ] URL が途中で折れて読めなくなっていないか
- [ ] ノンブル・ランナーに最後の一行が被っていないか
- [ ] Step 1 で集めた語と、資料上の語が一致しているか

**LibreOffice の行送りは指定より大きく出る。** 計算で「ちょうど収まる」高さは、
レンダリングでは溢れる。テキストボックスの高さは

```
必要高 ≒ 行数 × フォントpt × 0.0176" × 行間 + 0.20"
```

で見積もり、**さらに 1〜2 割の余白を足す**。溢れたら高さを増やすより、
まず**文を削って行数を減らす**（1行に収まる長さまで削るのが最短で確実）。

1回で通ることはまずない。IB CLINIC の11ページ版では、初回レンダリングで
7か所のはみ出しが出た。通るまで回す。

### 機械チェック（pptx-custom の絶対ルール）

目視の前に、単位表記（「◯◯億」で終わっていないか・`円円` がないか）を
スクリプトで 0 件にする。手順は pptx-custom の「日本語ビジネス文書の絶対ルール」。

## Step 7: 格納と版

- 保存先は `drive-record.md` と同じ案件フォルダ配下（運営資料の置き場）
- ファイル名は `{アプリ名}_使い方_v{n}.pptx` / 外部版は `..._利用ガイド_v{n}.pptx`
- **旧版は `_旧版/` に退避する。同じ場所に並べない。**
  中身が食い違う2本が並ぶと、必ず古いほうが配られる
- 版を上げたら、何が変わったかを1〜2行で伝える（読み手は差分だけ知りたい）

**Google Drive の案件フォルダが bash から見えないことがある。** ローカルに
キャッシュされていないフォルダは `ls` に出ず、`cp` も失敗する。そのときは：

1. 対象フォルダ内の既知のファイルを Read ツールで一度読む（キャッシュを引く）
2. それでも駄目なら、outputs に置いて `present_files` で渡し、
   **Finder でそのフォルダを一度開いてもらう**よう依頼する

見えないことを「フォルダが無い」と報告しない。案件フォルダは Drive 側に存在している。

## 呼び出し元との約束

### create-app から

共通後処理の Drive 記録（Phase N-1）の直後、完了レポートの前に実行する。
接続情報の README と使い方マニュアルが**同時に**揃った状態で納品する。

### update-deploy から

**毎回は作らない。** 以下のどれかに触れた修正のときだけ再生成する。

- 画面の追加・削除・移動（ルートが変わった）
- ナビ・ボタン・ラベルの変更
- ログイン方式・権限の変更
- メール文面の追加・削除
- 課金の条件・金額の変更
- **公開 URL が変わった**
- **アプリを分割した／統合した／改名した**

文言の微修正・スタイル調整・内部リファクタでは動かさない。
迷ったら「マニュアルの記述と食い違うか」で判断する。

### スキルを経由しなかったときも同じ

手で直した・別リポを立てて公開した場合も、上に当たるなら同じことをする。
**「そのスキルを使わなかったから対象外」は通らない。**
基準は使ったスキルではなく、**現物と手順書が食い違ったかどうか**。

## アプリの形が変わったとき（分割・統合・改名・URL変更）

いちばん壊れやすいのがここ。**マニュアルはリポジトリ単位ではなく、
現場が使う「ひとつの道具」単位で作る。**

1つのアプリを 2 つに分けても、**現場から見れば道具は 1 つ**（カウンセラーが開いて、
患者さまに見せる）。マニュアルも 1 本のまま、中で 2 つの URL を扱う。
リポジトリが増えたからといってマニュアルを 2 本に割らない。読み手が迷う。

作り直すときに必ず見る箇所：

| 箇所 | 何が嘘になるか |
| --- | --- |
| 表紙 | **URL**。増えた・変わったものを全部載せる |
| 全体の流れ | アプリが何個で、どれをどの端末で開くか |
| 開く | **ここが最も壊れる**。消えたボタン（例「患者画面を開く」）の手順が残る |
| サイトマップ | 画面の分割・ナビの項目・左上の版表示 |
| 気をつけること | 新しく増えた事故（コードの使い回し・版のズレ・通信経路） |

**消えた UI の語が本文に残っていないかを機械で確かめる。**
Step 1 の照合ゲートは「書いた語がコードにあるか」を見るが、逆方向
（**もう無い語が残っていないか**）は見ない。旧版から語を拾って grep する。

```bash
# 旧マニュアルから鍵括弧の語を抜き、新しいコードに無いものを洗う
python -m markitdown 旧版.pptx | grep -oE '「[^」]{2,20}」' | sort -u \
  | while read -r w; do t="${w//[「」]/}"; \
      grep -rqF "$t" "$REPO_A" "$REPO_B" || echo "もう無い語: $t"; done
```

版は上げる（v1 → v2）。**旧版は `_旧版/` に退避し、同じ場所に並べない。**

## やってはいけないこと

- 記憶・会話履歴・以前のマニュアルから書く（**必ずコードから引く**）
- 実装を確かめずに「たぶんこう動く」と書く
- パスだけを書いてフル URL を書かない
- 画面のラベルを分かりやすく言い換える
- 目視 QA を飛ばして納品する
- 内部の判断基準をエンドユーザー版に混ぜる
- 接続情報・API キー・環境変数の値を載せる（技術メモは drive-record.md の担当）
- 前の案件のパレットを流用する（**配色は毎回、相手から取り直す**）
- 図を AI 画像で作る（文字が崩れる。図形コードで描く）
- 文字だけのページで11枚通す（読み手はどこを見ればいいか分からなくなる）

---

## 正直に書くこと

**まだ出来ていないところを、資料から消さない。** IB CLINIC 版では
「お写真は、いまは合成した架空の口元が入っています／ご本人の写真への差し替えは次の版で」
を「気をつけること」に明記した。伏せると、現場が本番で気付いて止まる。

同じ理由で、**画面が出す注記をそのまま資料にも載せる**。
アプリ側で消せない注記を資料で省くと、資料のほうが強い約束をしたことになる。
