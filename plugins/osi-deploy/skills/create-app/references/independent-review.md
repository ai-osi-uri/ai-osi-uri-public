# 作り終えたら、別のAIがレビューする — 自分の仕事を自分で採点しない

> create-app の Phase N-1.5、update-deploy の Phase 5.3 から必ず読む。
> 画面の原則（[screen-structure.md](screen-structure.md)）に沿っているかを、**作ったAIとは切り離した別のAI**に確かめさせる手順。

## なぜか

決まりを書いても、作ったAIが自分で確かめると抜ける。「入れたつもり」の文脈を持ったまま見るので、
コードを読んでも、自分の説明どおりに見えてしまう。ローディング表示の抜けが、決まりにした後も繰り返されたのはこのため。

決まりの正誤は**作った時点で決まる**。時間を置いても答えは変わらないので、定期の点検にせず、
**作り終えた瞬間に、別の目で見る**。直す側がまだ文脈を持っているうちに直せるので、いちばん安い。

## 別のAIとは

- **作った会話を見ていない、もう1つの Claude**。モデルは同じでよい。目が別になるのは、作ったときの文脈を持たせないから
- 使える環境では**サブエージェント**（Claude が作業の途中で呼び出す別の Claude）で呼ぶ
- サブエージェントが使えない環境（ブラウザ版のチャットなど）では、本人に**新しい会話を1つ立ててもらい**、下の「レビュー役への頼み方」を貼って点検させる
- **同じ会話の中で、作ったAIが自分で確かめるのは、この関所として認めない**（作った側のセルフチェックは別にやってよいが、関所の代わりにはならない）

## レビュー役に渡すもの・渡さないもの

| 渡す | 渡さない |
|---|---|
| 決まり：screen-structure.md（**サーバーの最新版**。手元の写しは古いことがある。`get_skill` で create-app の `references/screen-structure.md` を読ませる） | 作った会話・作業の経緯 |
| コードの場所（手元の clone のパス、または `https://github.com/<org>/<repo>`） | 「ローディングは入れました」のような、作った側の説明や自己評価 |
| 公開URL（ログインが要るなら、テスト用の入り方） | 直してほしい箇所の予想 |
| 見てほしい画面の一覧（新規作成なら全画面、更新なら変わった画面＋共通の枠） | |

結論を渡すと、レビュー役はそれを確かめに行くだけになる。**決まりと現物だけを渡す。**

## レビュー役がやること

1. **決まりを読む**：screen-structure.md の「チェック」の項目を全部、点検の表にする
2. **コードを読む**：サイドバーの項目、`app/layout.tsx` の進み具合バー、`app/loading.tsx`、ボタンの処理中表示、一覧の API が `q`・`page` を受け取り 1 ページ分と全件数だけ返しているか、`main` の `max-width`、詳細がドロワーか自分の URL を持つか
3. **動かして見る**（コードだけで済ませない）。Playwright などで：
   - 通信を 2 秒遅らせてナビを押し、0.05 秒後に進み具合バーが出ているか、本文に「読み込み中…」が出るか
   - 保存・AI処理のボタンを押し、処理中に押せなくなり文言が変わるか
   - 1440px 幅で撮り、本文の右に余白が残っていないか
   - 一覧で検索し、ページを送り、詳細を開いて戻ったとき同じ検索・ページに戻るか
   - `/` を開いたら主オブジェクトの一覧に着くか
4. **結果を下の形で返す**。推測で「たぶん大丈夫」と書かない。確かめられなかった項目は「未確認」とし、理由を書く

## 結果の形

```
レビュー結果: 通過 ／ 差し戻し（外れ n 件・未確認 m 件）

| # | チェック項目 | 判定 | 根拠 |
|---|---|---|---|
| 1 | サイドバーは名詞だけ | 通過 | components/Sidebar.tsx 12-30 行 |
| 7 | 進み具合バー | 外れ | layout に NavigationProgress が無い。遅延2秒でナビ→バーが出ない（スクリーンショット添付） |
| … | | | |

直し方の案（外れごとに1行）
```

判定は **通過／外れ／要確認（決まりの当てはめに迷う）／未確認（確かめられなかった）** の4つ。
決まりに当てはまらない画面（使い方のページ、ログイン画面など）は外れにしない。

## 直しの往復

1. 外れがあれば、**作った側のAIが直す**（レビュー役は直さない。直す人と見る人を分けておく）
2. 直したら、**外れだった項目だけ**をもう一度レビュー役に見せる（新しく呼ぶ。前回の会話を引き継がせない）
3. 往復は **3 回まで**。3 回で通らなければ、残った外れを本人に見せて判断を仰ぐ
4. 「要確認」は本人に一言で聞く。「未確認」は、確かめられなかった理由とともに完了報告に書く

## 関所（DoD）

- **レビューが「通過」になるまで、create-app は Drive 記録・マニュアル・完了レポートに進まない。update-deploy は完了報告を出さない**
- 結果の表を `deploy-progress.md`（create-app）または `update-progress.md`（update-deploy）に貼る
- 完了報告に 1 行入れる：`レビュー: 通過（別のAI・外れ n 件を直した／未確認 m 件: 理由）`
- 省いてよいのは、画面が無いもの（API だけ・バッチだけ）と、画面に触れない更新（文言の微修正・内部の作り替え・環境変数だけ）。省いたら完了報告に `レビュー: 不要（理由）` と書く

## 新しい指摘は決まりに書き足す

レビュー役が見られるのは、**書いてある決まりだけ**。本人や現場から新しい種類の指摘が来たら、
その場で直すだけで終わらせず、screen-structure.md の原則とチェックに書き足す。
そうすれば、次からはレビュー役が拾う。この往復が回らないと、レビューは今ある決まりのところで止まる。

## レビュー役への頼み方（サブエージェントにも、新しい会話にもそのまま使う）

```
あなたは、業務アプリの画面が決まりに沿っているかを確かめるレビュー役です。
このアプリを作った人の説明は渡しません。決まりと現物だけで判断してください。

決まり：create-app の references/screen-structure.md（get_skill で最新版を読む）
コード：{コードの場所}
公開URL：{URL}（入り方：{テスト用の入り方 または 不要}）
見る画面：{画面の一覧}

やること：
1. 決まりの「チェック」の項目を全部、点検の表にする
2. コードを読んで、各項目を確かめる
3. 実際に画面を開いて確かめる（通信を2秒遅らせてナビを押す、ボタンを押す、1440px幅で撮る、
   一覧で検索してページを送り、詳細から戻る、/ を開く）
4. 項目ごとに 通過／外れ／要確認／未確認 で判定し、根拠（ファイルと行、または画面での結果）を書く

してはいけないこと：
- コードを書き換えない（直すのは作った側）
- 確かめていない項目を「通過」にしない
```
