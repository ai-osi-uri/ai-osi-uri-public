# 見た目の決め方 — 使う人が「自分のための場所だ」と信じられる見た目を、手順で決める

> create-app の Step 1-D と Phase 3、Phase N-1.5（レビュー）から読む。update-deploy で見た目を大きく変えるときも読む。
> 画面の組み方（何をどこに置くか）は [screen-structure.md](screen-structure.md)。ここは、色・書体・形・余白・動きの決め方。

## なぜか

見た目は飾りではなく、使う人がそのサービスを信じるかどうかを決める。
「誰が・どんな気分で開くか」を決めずに作ると、作る側の思い込み（「高級なら黒に金」「業務なら青」）で色が決まり、
相手の目には安っぽく・怪しく・古く見える。直してもらうたびに好みの話になり、何が正しいか誰にも言えない。

だから見た目は、**先に1枚の決まりにして本人と合わせてから作る**。決まりがあれば、レビュー役も「決まりに沿っているか」で判定できる。

**この作業の本質**：開いた瞬間に、使う人が「これは自分のための、この値段（この手間）にふさわしい場所だ」と信じられること。
感じてほしい気分を言葉で決め、それを今の流行りと同じ相手が普段使うものに照らして、色と形に落とす。

## いつやるか

- **お客さま（会員・利用者・一般の人）が開く画面があるときは必須**。試作でも省かない
- 社内の人だけが使う業務の画面（管理画面など）は、既定の落ち着いた見た目でよく、1〜3 は省いてよい（4 の見本は撮って見せる）
- 同じアプリに両方あるときは、決まりを使う人の画面の外枠（ラッパーの class）にだけ効かせ、管理画面に漏らさない

## 手順

### 1. 誰がどんな気分で開くかを書く

| 項目 | 書くこと |
|---|---|
| 開く人 | 年代・立場・払う金額（または手間）。議事録・要件定義書から |
| 場面 | いつ・どこで・何で・何秒くらい開き、何をしたいか |
| 感じてほしいこと | **3語**（例：特別・落ち着き・秘密が守られる） |
| 感じさせたくないこと | 似た業種で誤解されやすい印象（例：安っぽさ・怪しさ・派手さ・古さ） |

ここは本人の言葉と議事録から書く。分からないところは仮に置き、4 の見本と一緒に見せて合わせる。

### 2. 参考を集める（その月の流行りを必ず入れる）

- **同じ相手が普段使っている、上質なアプリ・サービスを2〜3個**。何をまねるか（言葉・安心の見せ方・仕組み・色）を1行ずつ
- **その月の流行りのまとめを2〜3本**（モバイルなら UI の流行りの記事、業種があればその業種の見本）。公開日を書く
- 読んだページだけを書く（検索の抜粋だけで書かない）。確かめた日付を添える
- 流行りで「古くなったもの」も拾う（例：装飾だけの動き、光沢・グラデーション、浮いた層）。避ける根拠になる

### 3. 決まりを1枚にする（リポジトリの `docs/design.md`）

頭に **作成日と次の調べ直しの日（1か月後）** を書く。中身は 1・2 と、次の決まり：

- 地（背景）・面（カード）・区切り（罫線か影か）の色
- 文字の色（主・副・薄い）。純黒を使うか
- 差し色（何色・**どこにだけ使うか**）
- 主ボタン・副ボタンの形
- 書体（見出し・本文・英字）と、数字の形
- 角の丸み・しるし（ランクや状態）の描き方
- 写真や画像が無いときの見せ方
- 余白と、1画面に出す段の数
- 動き（何を伝えるときだけ動かすか。動きを減らす設定では止める）
- 端末がダークモードのときの切り替え

色は CSS の変数（トークン）にして、決まりの値とコードの値を同じにする。

### 4. 1画面だけ作って見せ、OK をもらう

- いちばんよく開かれる画面（ホームなど）を1つだけ決まりで作る
- **スマホの幅（およそ 390〜500px）で撮って、本人に見せる**。ログインが要って撮れないときは、見本のデータで描く見本ページを別ブランチの試しの公開（プレビュー）に置いて撮る
- 見せるときは画像と一緒に、1 の3語と、決まりの要点を3行で添える。「どう感じるか」で直しを受ける
- OK の前に残りの画面を作り込まない。直しが入ったら決まり（`docs/design.md`）を先に直してから画面を直す

### 5. 残りの画面を同じ決まりで作る

決まりに無い判断が出たら、画面で決めずに決まりに1行足してから作る。

### 6. 決まりに沿っているかを別のAIが見る

Phase N-1.5 のレビューで、`docs/design.md` と撮った画面を照らす（[independent-review.md](independent-review.md)）。

### 7. 毎月、流行りを調べ直す

- 流行りは動く。`docs/design.md` の「次の調べ直しの日」に 2 をやり直し、変わった点だけ決まりと画面を直して、作成日と次の日を書き換える
- 毎月の調べ直しは定期の仕組み（ルーティン・リマインダー）で回す。作り終えたら、完了レポートに「毎月の調べ直しの日」を書き、定期の仕組みを作るかを本人に聞く

## 落とし穴

- **暗い地に金＝高級、ではない**。今は夜の店・ゲームに寄って見えやすい。上質さは、明るく落ち着いた地・細い罫線・少ない差し色・余白で出すほうが伝わることが多い。どちらにするかは 1 の3語と 2 の参考で決める
- 差し色で面を塗ると、どこが「いま選ばれているもの」か分からなくなる。差し色は小さく・意味のある所だけ
- 英字の飾り書体は、数字が上下に揃わない形（オールドスタイル）のことがある。時刻・金額が並ぶ画面では `font-variant-numeric: lining-nums tabular-nums` で揃える
- 横にスクロールする並びは、最初の1枚が画面の端にくっつく。`scroll-padding` と左右の余白を本文と同じにする
- 日本語の書体（明朝など）は読み込みが重い。見出しだけに使い、先読み（preload）は切る
- 手元でフォントの配信元に届かない環境では、手元のビルドが書体で止まることがある。公開先のビルドで確かめる

## チェック（レビュー役が見る）

- `docs/design.md` があり、1〜3 が埋まり、作成日と次の調べ直しの日が書いてある
- 参考に、その月の流行りの資料（公開日つき）が入っている
- コードの色・書体・角の丸みが決まりの値と同じ（トークンで持っている）
- 差し色が決まりで決めた場所以外に使われていない。面が差し色で塗られていない
- スマホの幅で撮った画面が、決まりと食い違っていない（段の数・ボタンの形・しるしの描き方）
- 端末のダークモードで開いて、決まりどおりに切り替わる
- 使う人の画面の決まりが、管理画面に漏れていない
