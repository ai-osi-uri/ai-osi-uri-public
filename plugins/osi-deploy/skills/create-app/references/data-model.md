# データの形の原則 — 同じ振る舞いは 1 つの型、違いは属性、役割は付け外し、関係はずっと付く相手に

> create-app Phase 1-C（要件定義）で、データの表を決めるときに読む。画面の組み方は screen-structure.md、見える範囲は access-control.md。

## 原則

1. **同じ振る舞いをするものは 1 つの型にする。違いは「種類」の属性で持つ。**
   「個人」と「会社」のように、どちらも持ち主になる・お金を払う・中に人がいる、なら表を分けない。表を分けると、両方に同じ処理を 2 回書き、
   片方にだけ足した機能がもう片方で動かない、が必ず起きる。
2. **役割は型を増やさず、その型の属性として付け外しする。**
   「紹介する」「売る」「管理する」のような役割を専用の表にすると、同じ相手が二重に登録され、どちらが正かが分からなくなる。
   役割と、その役割の条件（割合・上限など）は、役割を持つものの属性にする。役割を外しても記録は残る。
3. **関係は、ずっと付いていく相手に付ける。途中で入れ替わる入れ物に付けない。**
   「誰が連れてきたか」のように一生変わらない関係を、あとで移ったり増えたりする所属（会社・チーム）に付けると、移った瞬間に関係が消える。
   変わらない関係は人に、変わる関係は所属に。
4. **見えない入れ物を用意して、例外をなくす。**
   「会社に入っていない人」を特別扱いすると、全部の処理に分岐が増える。1 人ずつ見えない入れ物（自分だけの所属）を持たせれば、
   処理は「所属の中で動く」1 本で済み、画面ではその入れ物を見せない。

## 確かめ方（要件定義のレビューで見る）

- [ ] ほとんど同じ列を持つ表が 2 つ以上ないか（あれば 1 つにして種類の列で分ける）
- [ ] 役割ごとの表（〇〇者の表）が、元の型と同じ相手を二重に持っていないか
- [ ] 一生変わらない関係が、移る・増える所属の側に付いていないか
- [ ] 「〇〇に入っていない場合」の分岐が、あちこちの処理に散っていないか

## 実例

> 2026-11：持ち主として「個人」と「会社」を別に扱い、さらに「連れてきた人」を別の表で持っていた。
> 連れてきた関係が会社に付いていたため、人が別の会社に移ると関係が消え、同じ相手が「会社」と「連れてきた人」の両方に登録されていた。
> 個人と会社を 1 つの型（種類の属性で分ける）にし、連れてくる役割はその型の属性に、関係は人に付け直した。会社に入っていない人には見えない入れ物を持たせた。
