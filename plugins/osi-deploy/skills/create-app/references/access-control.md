# データの見える範囲 — ログインした人が、他人のデータに届かないこと

> create-app の Phase 4（作るとき）と Phase N-1.5（別のAIによるレビュー）、update-deploy の Phase 5.3 から必ず読む。
> ログインのあるアプリは全部が対象。試作でも省かない。

## なぜか

「ログインしているか」と「その人のデータか」は別の確認。前者だけ入れて後者を忘れると、
ログインした人が番号を 1 つ変えるだけで、他人のデータを順番に全部取れる。攻撃に技術は要らない。

この抜けは、画面を普通に使っている限り見えない。作るときのテストは「自分のデータが正しく見えるか」を確かめるので、
「他人のデータが見えないか」は、**工程として決めておかないと誰が作っても抜ける**。検収でも気づかれない。

## 原則

1. **1 件を扱う処理は、持ち主を条件に入れて探す。** 番号（ID）で探してから持ち主を比べるのではなく、
   検索の条件そのものに「ログイン中の人のもの」を入れる。対象は 取得・更新・削除・ファイルの取得・PDF の出力 の全部。
2. **他人のものは「見つかりません」で返す。** 「権限がありません」と返すと、その番号のデータが在ることを教えてしまう。
3. **役割ごとに範囲を決め、範囲の外は拒む。** 役割が 2 つ以上あるアプリ（利用者・店舗の担当・運営 など）は、
   アプリ定義のときに「誰が・何を・どこまで」の表を作る。担当が自分の所属（店舗・会社・部署）を自分で書き換えられる作りにしない。
   所属・役割・権限の項目は、本人が更新できる入力の型（DTO・フォーム）に入れない。
4. **他人のパスワード・メールアドレスを変えられる処理は、運営の役割だけに置く。** 担当の役割には置かない
   （招待・本人による再設定にする。[admin-console.md](admin-console.md)）。
5. **返す項目は、見せると決めたものだけにする。** データベースの 1 行をそのまま返さない。
   役割ごとに返す項目の一覧（許可リスト）を持つ。運営用の項目（手数料・請求先・内部メモ・連絡先・最終ログイン）は、
   利用者向けの返事に入れない。検索のための一覧は、選ぶのに要る項目（名前と番号など）だけ返す。
6. **入口に回数の上限を付ける。** ログイン・パスワードの再設定・確認コード・仮パスワードの確認は、
   同じ相手・同じ送り元からの連続した失敗を数え、上限で止める。全体の流量制限（WAF など）だけに任せない。
7. **おかしな動きを知らせる。** ログインの失敗・成功と、ログインせずにデータの口へ来たことを、ツールポータルの受け口に送る
   （決まった部品とつなぎ方は [intrusion-watch.md](intrusion-watch.md)。数える・知らせる・記録を見せるのはポータル）。
   短い時間に同じアカウントが 1 件取得の API を大量に呼んだときの知らせは、まだ部品に入っていないので、要るアプリはアプリの中で入れる。
   通知の宛先（誰が受けて、誰が動くか）は、公開の前に本人と決めて drive-record に書く。
8. **回数や在庫が減る処理は、資格を確かめてから減らす。** 特典・クーポン・在庫・ポイントは、
   その人がその操作をしてよい状態か（利用した実績があるか・すでに受け取っていないか）をサーバで確かめる。

## 仕組みごとの入れ方

| 仕組み | 入れ方 |
|---|---|
| Supabase（RLS あり） | 全テーブルで RLS を有効にし、ポリシーに持ち主（`auth.uid()`・テナント）を書く。**サービスロールの鍵で読む処理は RLS を通らない**ので、その処理には 1 と同じ条件をコードに書く。会社ごとに分けるアプリは `supabase-multitenant-rls` |
| 自前の API（AWS・Railway・Cloudflare など、RLS が無い） | API の 1 本ごとに、ログイン中の人を受け取り、検索の条件に入れる。役割の範囲は共通の関所（ガード・ミドルウェア）に置き、**その関所を付け忘れた API が無いこと**を一覧で確かめる |
| ファイル（Storage・S3・R2） | 置き場を非公開にし、持ち主を確かめたあとで期限つきの URL を出す。推測できるパスに置かない |

## チェック（レビュー役が全部たしかめる）

役割が 1 つのアプリは A・C・D、2 つ以上のアプリは A〜D。

**A. 他人の番号で取りにいく（必須・実際に動かす）**

1. 同じ役割のアカウントを 2 つ作る（甲・乙）。乙でデータを 1 件ずつ作り、番号を控える
2. 甲でログインし、番号を受け取る API の全部に、乙の番号を入れて呼ぶ（取得・更新・削除・ファイル・PDF）
3. 全部が「見つかりません」で、乙のデータが変わっていないこと

**B. 役割の範囲の外に出る（役割が 2 つ以上のとき・必須）**

4. 担当の役割で、別の所属（店舗・会社）の番号を入れて呼ぶ → 拒まれる
5. 担当の役割で、自分の所属・役割を書き換える値を送る → 変わらない
6. 担当の役割で、他人のパスワード・メールアドレスを変える API を呼ぶ → 拒まれる
7. 担当の役割で、全体の集計・全員の一覧を呼ぶ → 自分の範囲の分だけ返る

**C. 返す項目（コードと実際の返事の両方で見る）**

8. 利用者向けの返事に、運営用の項目が入っていない
9. 一覧・検索の返事に、選ぶのに要らない個人の項目（メール・電話・住所・生年月日）が入っていない
10. パスワード（ハッシュを含む）・鍵・内部メモが、どの返事にも入っていない

**D. 入口と知らせ**

11. ログインをわざと 10 回続けて失敗させる → 途中で止まる
12. ポータルの受け口につながっている（`/api/health` が `intrusion: true`、セキュリティのタブの「外からのアクセス」が「いまは大丈夫です」）。
    ログインを続けて失敗させる → ポータルに検知が立つ（intrusion-watch.md の「確かめる」）

**E. テストとして残す（コードで見る）**

13. A と B の確認が、自動テストとして入っている（「権限：」で始まる名前のテスト。あとで誰かが変えても落ちて気づける）
14. API の一覧（全部の道）に、関所（ログイン・役割・範囲）のどれが付いているかの表がある。付いていない道は、理由が書いてある

## API の一覧の作り方（14 の表）

コードから機械的に出す。手で書かない（書き漏れた道がいちばん危ない）。

- 全部の道（メソッドとパス）
- 付いている関所（ログイン・役割・範囲）
- 番号を受け取るか。受け取るなら、持ち主を条件に入れているか
- ログインの要らない道は、その理由（ログイン・再設定・外部からの通知 など）

この表を `deploy-progress.md` に貼る。更新のときは、足した道・変えた道の行だけ見直す。

## すでに動いているアプリに入れるとき

1. 上の「API の一覧」を作る
2. チェック A〜D を回す（本番のデータに触れない環境で。本番しか無いときは、試し用のアカウント同士で A だけ回す）
3. 外れを重い順に並べて本人に見せる：他人のデータを変えられる・乗っ取れる ＞ 他人の個人情報が見える ＞ 取引上の情報が見える ＞ 回数の上限・知らせが無い
4. 直す順番と出し方を本人と決めてから直す（動いているアプリは update-deploy の手順）
5. 直したら E のテストを足し、もう一度 A〜D を回す
