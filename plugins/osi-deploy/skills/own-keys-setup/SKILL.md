# 鍵設定に鍵を預ける（own-keys-setup）

## §0 考え方

- **お試し（マネージド）は体験用。** 共用アカウントで、鍵なしでアプリを作って公開するためのもの。枠は アプリ 2 本・GitHub 2・Vercel 2・Supabase（データベース）1、画像・動画・音声は「生成枠」（会社ごとの通算。`health_check` の「お試しの枠」行に残り % が出る。使い切ると `[quota_exceeded:generation]`）。
  2 本目のアプリ、AI 秘書、本番運用は **自分の鍵** で作る。作ったものが本人のアカウントに残り、費用も各サービスから本人に請求される。
- **何が要るかはサーバが知っている。** 鍵の一覧と「やりたいこと別にそろっているか」は `health_check` の `uses` 行が正本。
  スキル本文に鍵の表を持たない（増えたらサーバ側だけ直せば済むように）。
- **鍵の値は Claude を通さない。** 本人がツールポータルの「鍵設定」に貼る。チャットに貼られたら使わず、
  「チャットに残ったので、発行元で作り直してから画面に貼ってください」と伝える。
- **人の手は 2 つだけ。** ① 発行元で「作成」（発行・同意）を押す ② 出てきた秘密の値をコピーして鍵設定の欄に貼り、「確かめて登録」を押す。
  それ以外（発行画面までたどり着く・名前／権限／期限を入れる・鍵設定の画面を開く・秘密でない欄を埋める・貼る欄にカーソルを置く・登録できたか確かめる）は Claude がやる。
  「〇〇の画面で発行して貼ってください」と文章で説明して止まるのは、仕事を投げ返している状態なので禁止。
- **秘密の欄と、そうでない欄を分ける。** 秘密＝トークン・シークレット・API キー本体・秘密鍵（.p8 など）・サービスアカウントの JSON。これは本人が貼る。
  秘密でない＝ID（キー ID・Issuer ID・アクセスキー ID・アカウント ID・組織 ID）・リージョン・プロジェクト名・パッケージ名・チーム名。これは Claude が画面から読んで入れてよい。迷ったら秘密として扱う。
- **切り替えは本人が押す。** 「自社アカウント」はポータルの画面のボタン。Claude からは切り替えない。
- **会社の鍵と自分の鍵。** 道具は、アプリの置き場（GitHub・Vercel・Supabase）・AI・決済・クラウド・契約サービスでは**会社の鍵を先に**使い、
  会社に無いときだけ自分の鍵を使う。メール・電子署名のつながり（メールのアプリ・電子署名のサービス）だけは自分の鍵が先。
  だから預ける先は、会社で使うものは「会社の鍵」（入れられるのは会社の owner / admin）、その人として送る・署名するものは「自分の鍵」。

## §1 いまを見る

1. `health_check` を呼ぶ（URL で繋いだコネクタ。テキストで返る）。読むのは 3 か所：
   - `keys :` … いま「マネージド（お試し）」か「鍵設定」か
   - `uses :` の下の行 … `○/✕ [id] やりたいこと  足りない鍵: …  ※注意  <ポータルの URL>#<id>`
   - `broken :` … 預けたのに効いていない鍵（期限切れなど）
2. `health_check` がテキストでなく JSON で返るなら、ダウンロード版の拡張を使っている。このスキルではなく
   `setup-deploy-environment` に渡して終わる。
3. やりたいことを 1 つに決める。呼び出し元から渡されていればそれ。無ければ聞く（選択肢は `uses` の行の題名をそのまま）。
   決済を付けるなら、親の「アプリを作って公開する」も対象に入る（子の扉は親がそろわないと動かない）。

## §1b ポータルの画面を確かめる（Chrome を使うとき・最初に 1 回）

鍵設定の画面を開いたら、何かを押す前に 2 つを見る。

1. **右上の会社名と、左下のアカウント**が、いま鍵を入れたい会社・本人か。テスト用のアカウントや別の会社でログインしていたら、
   そこで止めて「ログインし直してください」と頼む（Claude はログインしない）。違う会社に入れた鍵は、道具には効かない。
2. **預ける先（会社の鍵 / 自分の鍵）**を §0 で決め、そのタブを開く。入れ直すときは、もう一方のタブに同じ鍵の古いものが残っていないかも見る。
   メール・電子署名の鍵で、自分の鍵に古いものが残っていると、会社の新しい鍵より先に使われる。消すのは本人の OK をもらってから（下の「消すとき」）。

## §2 地図を 1 行で出す

最初の返事で、これからやることを 1 行で見せる。例：

> ① 鍵を 2 つ登録（Vercel のトークン・Supabase の組織 ID）→ ② 「自社アカウント」に切り替え → ③ そろったか確かめる → 秘書づくりに戻ります

足りない鍵が 0 で切り替えだけなら ② ③ だけ。全部そろっていれば「そろっています」と言って、すぐ元の作業に戻る。

## §3 鍵を 1 つずつ

やりたいことが複数（「まとめて」「全部」）なら、よく使う順に並べて §2 の地図に載せ、1 つずつ進める。
足りない鍵ごとに、次の 4 手で進める。Claude in Chrome が使えないときは §3b。

1. **発行元を整える（Chrome・タブ A）**：`credential-handoff` の手順 2 で、発行画面の「作成」直前まで進む。
   - 名前・説明の欄は Claude が入れる（`<会社の短い名前>-<用途>-<年月日>` のように、後で何の鍵か分かる名前）
   - 権限・期限・種類は、この用途に必要な最小のものを選んでおき、選んだ理由を 1 行で添える
   - 発行元が URL で名前・権限を受け取れるなら、それで開く（例：GitHub のクラシックトークンは
     `https://github.com/settings/tokens/new?scopes=repo,workflow&description=<名前>` で、名前と repo・workflow に印が付いた状態で開く。期限だけ本人が選ぶ）
   - ログイン・本人確認（GitHub の「Confirm access」など）・CAPTCHA に当たったら、そこだけ本人に頼み、終わったら続きを Claude が進める
   - 権限を新しく作る操作（クラウドの利用者やロールを作り、権限を付ける）は、Claude からは進められないことがある。止められたら回り道をせず、
     入れる値（名前・付ける権限・選ぶ種類）を画面の順にそろえて本人に渡し、置き場（タブ B）の準備は Claude が続ける
2. **置き場を整える（Chrome・タブ B）**：`uses` 行の末尾の URL（`…/keys#<id>`）を開く。そのやりたいことに要る鍵だけが並ぶ。
   - 鍵設定の画面の「登録」「作り直して登録」を押すと、手順つきの画面（1/3 → 3/3）が開く。発行元の説明の手順（1・2）は
     Claude が「できた」で進め、**最後の「貼る欄」の手順で止めておく**
   - 秘密でない欄（§0）は、発行元の画面や既存の設定から値を読んで Claude が入れる
   - 秘密の欄をクリックしてカーソルを置いておく（貼るだけの状態）
3. **3 行で渡して待つ**：
   ```
   【何の鍵か】<何が動くようになるか>（<選んだ権限>）
   ① タブ A で「<作成ボタンの名前>」を押し、出てきた値をコピー
   ② タブ B の「<欄の名前>」に貼って「確かめて登録」
   ```
   作成後の画面には秘密の値が出ている。本人が「貼った」と言うまで、タブ A の画面は読まない・撮らない。
   値がチャットに貼られたら使わず、発行元で作り直してもらう。
4. **確かめる**：`health_check` をもう一度呼び、その鍵が `credentials:` で OK になり、**会社の鍵 / 自分の鍵のどちらで動いているか**（末尾 4 桁とかっこ書き）が
   入れたものと同じかを見る。そのうえで、その鍵を使う道具を 1 回だけ読むだけの呼び方で動かす（GitHub なら `github_get_file` で会社のリポジトリの一覧）。
   ここまで通ってから次の鍵へ。
   `NG（無効・期限切れ）` なら作り直し。権限不足（例：GitHub の repo と workflow）を疑うときは、Claude が発行画面の権限を直してから作り直してもらう。

組になる鍵（Supabase のトークンと組織 ID、App Store Connect のキー ID・Issuer ID・秘密鍵、AWS のアクセスキー ID とシークレット）は、
同じ発行画面から出るので 1 回の受け渡しでまとめる。片方だけでは足りない扱いになる。

### §3b Chrome が使えないとき

1 つの鍵ごとに 3 行だけ出して待つ：何のため／どこで作る（鍵設定の画面の「取得ページを開く」）／どこに貼る（`…/keys#<id>`）。
Chrome をつなぐと発行画面まで代わりに進められることを、最初に 1 回だけ伝える。

### 消すとき（古い鍵を外す）

鍵設定のゴミ箱・「消す」は、ブラウザの確認（「消しますか？」）が出て、Chrome の操作がそこで止まる。Claude からはこの確認を押せない。
押す前に「何を消すか（会社の鍵か自分の鍵か・鍵の名前・末尾 4 桁）と、消すと戻せないこと」を本人に見せて OK をもらい、
押したら「出てきた確認で OK を押してください」と頼んで待つ。

## §4 切り替え

鍵がそろって、`keys :` がまだ「マネージド」なら：

> ポータルの「鍵設定」の上にある「自社アカウント」を押してください（確認が出たら OK）。押したら「押した」と送ってください。

切り替える前に一度だけ伝えること：お試しで作った公開中のアプリは、切り替えた後もお試し（共用アカウント）に置かれたまま動き続け、道具からもそのまま操作できる（中身の置き場に合わせて鍵が選ばれる）。自社アカウントに移したいときは、ポータルの「公開中のアプリ」（/managed/projects）の「自社アカウントへ引っ越す」をアプリ 1 本ずつ押してもらう。GitHub と Vercel は自動で移り、データベース（Supabase）は画面でしか移せないため運用者が移す（お客さまには、自分の Supabase の組織に運用者を招待してもらう）。
お試しが選べない人（会社がマネージドを申し込んでいない）は、最初から自分の鍵で動いているので切り替えは要らない。

## §5 確かめて戻る

`health_check` を呼び、目的の行が `○` になったことを確かめる。

- `○` → 「そろいました。続きを始めます」と言って、呼び出し元のスキル（`create-app` / `secretary-create` など）の止まったところへ戻る
- `✕` のまま → 足りない鍵の名前と、画面の URL だけをもう一度示す

## 呼び出し元との約束

| 呼び出し元 | いつ呼ぶか | 渡すやりたいこと |
|---|---|---|
| `create-app` | `[quota_exceeded:projects]` / `[quota_exceeded:resources]`（お試しの枠）を受けた／本人がお試しの枠を超えて作りたいと言った | `app`（決済があれば `pay` も） |
| `create-app` | URL のコネクタで、作るアプリに要る `uses` の行が `✕`（`[app]`＝GitHub・Vercel・Supabase、`[cloudflare]`、`[railway]`、`[pay]` など） | ✕ の行の id（複数あれば全部） |
| `create-app` | Stripe の道具が「Stripe の鍵が未登録」で止まった | `pay` |
| `setup-deploy-environment` | `health_check` がテキストで返った（URL のコネクタの人がダウンロード版の手順に来た） | 呼び出し元のやりたいこと（無ければ `app`） |
| `secretary-create` | URL のコネクタで、`uses` の `[secretary]` が `✕` | `secretary` |
| `deploy-mobile-app` / `mobile-secrets-sync` | 配信の鍵が足りない（`mobile_health_check` の `apple.ok` / `google` が false、`mobile_keys_to_github` が `missing`、`asc.*`・`play.*` が `NG`）と分かり、本人が「今用意する」を選んだ | `ios` / `android`（配信する先だけ。Firebase も要れば `firebase`） |
| `ai-video-production` | `[creative]` が `✕`、`fal.key`・`elevenlabs.key` が `NG`、または `[quota_exceeded:generation]` で、本人が「今用意する」を選んだ | `creative` |
| LINE の道具 | 「アプリの画面で、そのアプリの LINE 公式アカウントの鍵を預けると使えます」と出た | （下の「LINE はアプリごと」） |
| 本人 | 「鍵を設定して」「〇〇を使えるようにして」／鍵設定の「AI に頼む」の指示文 | 言われたもの（無ければ `uses` の `✕` から選んでもらう） |

## LINE はアプリごと

LINE 公式アカウントのチャネルアクセストークンは、1 つの公式アカウントにひもづく鍵で、アプリごとに別のアカウントになる。
だから会社の鍵・自分の鍵としては預けない（鍵設定の画面にも出ない）。アプリに預ける。

1. どのアプリの LINE かを本人に確かめる（`list_projects` の案件）。
2. 公式アカウントがまだ無ければ、作るところから手伝う。公式アカウントは API では作れないので、ブラウザで LINE Official Account Manager を開き、
   作成 → Messaging API の有効化 → LINE Developers でチャネルアクセストークン（長期）の「発行」の手前まで Claude が進める。ログインと「作成」「発行」は本人が押す。
3. 鍵はポータルのアプリ一覧 → そのアプリ →「LINE 公式アカウント」の「登録する」で預けてもらう（会話に貼らせない）。
4. 送るときは LINE の道具に `project`（アプリの slug）を付ける。鍵のあるアプリが 1 つなら省略できる。

## 事故の型

- 手順を全部まとめて書き、本人がどこで止まったか分からなくなる → 1 回に鍵 1 つ
- 「発行して貼ってください」と説明だけして止まる → 発行画面の作成直前と、貼る欄のカーソルまで Claude が進める
- 権限づくりで止められ、別の手段で押し通そうとする → 値をそろえて本人に渡す
- 作成後の画面を読んで秘密の値を見てしまう → 本人が「貼った」と言うまで発行元のタブは読まない
- LINE の鍵を会社の鍵として預けるよう案内する → LINE はアプリごと。アプリの画面で預ける
- 秘密でない ID まで本人に打たせる → ID・リージョン・名前の欄は Claude が入れる
- 鍵がチャットに貼られ、そのまま使う → 使わない。作り直しを案内する
- 鍵を入れただけで自分の鍵に切り替わったと思い込む → 切り替えは別のボタン。`keys :` で確かめる
- 期限切れの鍵が「登録済み」に見えて、作る途中で 401 → `credentials:` の `NG` を見る。OK でも、道具を 1 回動かして確かめる
- `uses` の行が `○` なのに、その行の鍵が `credentials:` で `NG`・`broken:` に出ている（期限切れの鍵を `○` と数えることがある） → `uses` だけで「そろっている」と言わない。`NG` の鍵は足りない扱いにして作り直す
- テスト用のアカウント・別の会社でログインしたまま鍵を入れる → §1b で右上の会社名と左下のアカウントを先に見る
- 会社の鍵を入れ直したのに、自分の鍵の古いものが残っていて止まる（メール・電子署名） → §1b でもう一方のタブも見る
- 消すボタンを押して確認ダイアログで Chrome が止まる → 押す前に本人に伝え、確認の OK は本人に押してもらう
