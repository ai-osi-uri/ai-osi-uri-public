# Cloud Run で「常時動く・重い処理をする」アプリを動かすときの注意

録画・動画の加工・定期処理など、リクエストに答えるだけでなく **裏で動き続けるアプリ** を
Cloud Run（常時 1 台・CPU 常時割り当て）で動かすときに、実際に事故になったことと防ぎ方。
別のホスト（Railway / Render / VM など）から移すときも、まずこの表を確かめる。

## 事故リスト（判断として残す）

| # | 起きたこと | 原因 | 防ぎ方 |
| --- | --- | --- | --- |
| 1 | 数分おきにコンテナが落ちる（`signal 9`／メモリ超過）。落ちるたびに起動時の再開処理がまた同じ重い処理を始めて、落ち続ける | ① 画像の描画でフレームごとに新しいキャンバスを作り、ネイティブのメモリが返らずに数 GB まで増えた ② `/tmp` はメモリ上（gen2）なので、作業ファイルもメモリ上限に数えられる | 描画の入れ物（canvas 等）は **1 つ作って毎回クリアして使い回す**。ループの中で作らないことをテストで縛る。起動時の再開は **回数の上限** を持たせ、超えたら「失敗」にして止める（1 件の不具合でサービス全体を巻き込まない） |
| 2 | 動画の書き出しが途中で失敗する／壊れたファイルが残る | GCS をマウントしたフォルダ（gcsfuse）は **前から順に書く** ことしか得意でない。ffmpeg の `+faststart` のように後から先頭へ戻って書く処理は失敗する | 加工はローカルの作業フォルダで完成させ、中身が空でないことを確かめてから、マウント先へ **順に流して** 一時名で置き、最後に名前を変える |
| 3 | 大きい動画だけ再生・保存できない（真っ黒・途中で切れる） | Cloud Run は **1 回の応答が 32MiB まで** | 大きいファイルは Range（206）で 16MB 程度に分けて返す。画面側の「保存」も分けて取って繋げる |
| 4 | 移した直後に過去のデータ（動画など）が見えない | Dockerfile の `ENV`（保存先のパス）が、新しい置き場（マウント先）と食い違っていた | 移す前に、アプリが読む保存先の環境変数と、実際のマウント先・DB を **一つずつ突き合わせる**。移した直後に件数を数えて比べる |
| 5 | ある機能を切っていたら、別の機能の記録まで読まれず、全員が止まった | 「機能 A が有効なときだけ DB を初期化する」条件に、機能 B も乗っていた | 初期化の条件は「DB の接続先があるか」で決める。機能の ON/OFF とつなぎ込みを混ぜない |
| 6 | 前のホストより月額が倍になった | CPU・メモリを「足りなそうだから」で大きく取った | 大きさは **計測したメモリの山** から決める（山の 1.5〜2 倍）。前のホストの実際の請求（アプリ単位の使用量）を先に見て、目安を出してから移す |

## 大きさと費用の決め方

- 常時 1 台・CPU 常時割り当ては「台数 × CPU × 時間」と「メモリ × 時間」で毎月かかる。2CPU/4GiB と 1CPU/2GiB で約 2 倍違う。
- まず小さめで動かし、重い処理（いちばん長い入力）をローカルで流して RSS の山を測る。山 × 1.5〜2 を上限にする。
- 下げたあと数日は、落ちた記録（`signal 9`、`Memory limit exceeded`）とメモリの使用率を見る。
- 前のホストの費用を口で言わない。請求画面のアプリ単位の数字を見てから比べる。

## 規模が大きくなったら

- 同時に走る重い処理（録画・書き出し）の **数を見える化** し、上限を持たせる。
- それでも足りなくなったら、重い処理だけ Cloud Run Jobs などに切り出す。最初から分けない（費用と手間が増える）。

## gcp_api で Cloud Run を直すときの小技

- PATCH は `updateMask=template` で **template を丸ごと** 送る（環境変数・シークレット・ボリュームを落とさない）。直前の template を GET して保存し、そこから変える。
- 応答が大きすぎるときは `fields=name,done` で絞る（`template.containers.image` のような深い指定は 400 になることがある）。
- 一時的な環境変数（再実行の指示など）は、終わったらすぐ外した template で入れ直す。
