## 3. 技術的な学び（横展開できるもの）

開発の過程で判明した、フォーム自動送信における一般的な知見。

### 3.1 ネイティブイベントの発火が必須

**`el.value = "..."` で値をセットするだけでは、多くのフォームは送信できない。**
フォームの JS 検証は「人が入力した／押した」ことを示すネイティブイベントを見ているため。

- テキスト系: 値のセット後に `input` / `change`（必要なら `blur`）を `bubbles: true` で発火する
- チェックボックス・ラジオ・セレクト: プロパティ設定ではなく**実クリック**
- Playwright の `fill()` / `check()` / `click()` を使えば自動的に発火するため、この問題は回避できる

同意チェックの実クリックで初めて送信が通る、というケースが実際にあった。

### 3.2 ラベル取得は DOM 構造に依存する

`<tr><th>氏名</th><td><input></td></tr>` というテーブル構造で、「前の行」を見てラベルを取ると
**全項目が1つずつズレる**。氏名欄を会社名と誤認し、広範囲で未マップになる。
同じ行の `<th>` を見るよう構造ごとに取得方法を変える必要がある（table / dl / 汎用）。

### 3.3 ページ読み込みは `networkidle` を使わない

広告タグの多いサイトでは通信が止まらず、待ち切れずに「URL未解決」と誤判定する。
`domcontentloaded` ＋ 固定待機に変更することで解消した。

### 3.4 完了検知は1系統では足りない

送信成功の判定は、次を順に評価する。

1. URL 遷移（`/thanks`, `/complete` 等）
2. 完了文言の辞書マッチ（同一ページに差し込まれる型）
3. 多段ステップの最終到達（入力 → 確認 → 完了）
4. タイムアウト（一定時間で `不確定` として打ち切り。**自動再送しない**）

### 3.5 状態分類が改善の羅針盤になる

失敗を6状態（成功／不確定／要手動／ブロック／除外／エラー）で分類すると、次に何を直せばよいかが決まる。
「失敗率」ではなく「失敗の種類の分布」を見る。

## 4. 改善ループ（これ自体が資産）

ツールそのものよりも、**到達率を上げ続けるループ**に価値がある。

```
① 回す（未処理のみ送信）
   ↓
② 分類する（6状態で台帳に自動記録・失敗理由も1行）
   ↓
③ 原因を実物で見る（失敗が多い型を1〜2社、実際のHTMLを開く）
   ↓
④ 直す（検出・入力ロジック、または設定）
   ↓
⑤ 再実行して測る（未送信だけ戻して再送 → 前回との差分が改善効果）
   ↓
⑥ ノウハウを貯める（対処が辞書として蓄積される）
   ↓ ①へ
```

## 6. 自動化しない領域（方針として固定）

以下は「まだできていない」ではなく、**意図的にやらない**。

- **CAPTCHA の突破** — `ブロック` として確定させ、メール送付側へ回す
- **営業お断りへの送信** — 検出して `除外`
- **`不確定` の自動再送** — 二重送信のリスクがあるため
- **台帳の無断書き換え** — URL修正・除外化は人の承認を経る
- **エンジン本体のソース自動書き換え** — リスクが高い。知識をデータに外出しすることで改修頻度そのものを下げる
