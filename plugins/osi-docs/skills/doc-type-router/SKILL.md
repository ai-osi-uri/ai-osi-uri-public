# 資料の型ルーター（doc-type-router）

資料づくりは「工程」と「型」の2つで考える。

```
★doc-type-router（型を選ぶ）
        ↓ doc-type.md
storyline-gate → deck-composition → pptx-custom
  考える            構成する            刷る
```

- **工程**はどの資料でも同じ。考える（骨子）→ 構成する（何枚・どの順）→ 刷る（見た目）。
- **型**はその資料が何のためにあるか。型が変えるのは、骨子の重心・1枚の密度・描き方・載せないもの・形式。
  **章の並び（テンプレート）ではない。** 章は今までどおり deck-composition が「読み手の問いの木」から作る（原則0-0）。

このスキルは型を選び、型の指示を工程に渡すだけ。会社共通の決まり（言葉づかい・強調色・目次の出し方・
相手の内情を書かない 等）はここには持たない。それは既存の置き場所（deck-composition の原則と
`references/review-questions.md` の指摘台帳、pptx-custom の絶対ルール）が正本で、どの型でも当たる。

---

## 1. 型を選ぶ

問いは1つだけ：**読み手は、この資料を見て何を決めるのか。**

| 読み手が決めること | 型 | 型の指示の置き場所 | 形式の初期値 |
|---|---|---|---|
| 作るもの・やることの芯を信じて、進めてよいか | 企画書 | [types/kikakusho.md](types/kikakusho.md) | スライド |
| 買うか・頼むか（社外の相手） | 顧客向け提案 | deck-composition 0-2「顧客向け提案書の標準形」。リード案件なら `proposal-package` に渡す | スライド |
| 自社の中で、投資・採用・方針を承認するか | 社内会議・稟議 | storyline-gate「社内会議・稟議向けの骨子」＋ deck-composition 0-2「社内会議・稟議向けの標準形」 | スライド |
| 状況をつかみ、次の判断をする（定例の報告） | 定例報告 | 組織の定例報告のルール（`osi-profile.md` に定めがあればそれ） | 組織の定めに従う（無ければ Word） |

- **依頼の言葉より、読み手が決めることを優先する。** 「企画書を作って」でも、中身が毎週の状況報告なら定例報告の型にする。
- 当てはまらないときは候補を2つに絞り、「読み手はこれを見て何を決めますか？」と1回だけ聞く。聞けないときは最も近い型で進め、どの型で作ったかを冒頭に書く。
- 1つの会議で2つの型が並ぶことはある（例：定例報告の中で、別添として企画書を出す）。その場合は資料を分け、型ごとに作る。
- 形式は型の初期値に従う。依頼に形式の指定（pptx・Word・PDF・スライドの成果物 等）があればそちらを優先する。

## 2. 型の指示を doc-type.md にまとめて渡す

選んだ型の指示を読み、次の1枚にまとめて以降の工程に渡す。

```markdown
# doc-type.md
- 型: 企画書
- 読み手が決めること: （一文）
- 形式: スライド
- 考える（storyline-gate へ）: 型ファイルの「考える」節を転記
- 構成する（deck-composition へ）: 型ファイルの「構成する」節を転記
- 刷る（pptx-custom へ）: 型ファイルの「刷る」節を転記
- 載せないもの: 型ファイルの「載せないもの」節を転記
- 仕上げの点検: 型ファイルの「仕上げの点検」節を転記
```

- 各工程は doc-type.md があれば読み、型の指示を自分の既定に**足して**使う（各工程の「型を受け取ったとき」節）。
- 型の指示と工程の既定がぶつかったら、型の指示を優先する。ただし会社共通の決まり（指摘台帳・絶対ルール）は型で外さない。

## 3. 型を増やすとき

- `types/<型名>.md` を1つ足し、上の表に1行足す。型ファイルは「考える／構成する／刷る／載せないもの／仕上げの点検」の5節だけを持つ（[types/kikakusho.md](types/kikakusho.md) が見本）。
- 型ファイルに案件名・相手の名前・具体的な金額を書かない。
- 受けた指摘が「この型のときだけ」の話なら型ファイルに、「どの資料でも」の話なら指摘台帳に足す。迷ったら指摘台帳。

## 4. 終わったら

どの型・どの形式で作ったかを1行で伝える。
