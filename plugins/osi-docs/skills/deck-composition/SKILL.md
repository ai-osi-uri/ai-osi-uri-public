# デッキ構成（Deck Composition）

骨子（何を/誰に/どの順で信じてもらうか）は決まった。次は**それをスライドの並びに割る**工程。ここを飛ばして描画に行くと、「綺麗だけど何が言いたいか分からないデッキ」になる。

このスキルの仕事は1つ：承認済みの `storyline.md` を受け取り、**スライド構造（`slide-plan.md`）**に翻訳する。各スライドが何を言い切り、どの順で並び、どこで章が変わるかを決める。色も図形もまだ描かない。

```
storyline-gate → ★deck-composition（ここ）→ pptx-custom
  考える            構成する                  刷る
```

---

## 入出力（スキル間の契約）

- **入力**：承認済み `storyline.md`（コアメッセージ＋論理の骨子3〜5段＋証拠設計＋落とし穴）。無ければ先に storyline-gate へ。business-plan-builder から来た場合は `question-tree.md`（問いの木）も受け取る。
- **出力**：`slide-plan.md`。スライドの順序リスト。各スライドは「答える問い・Action title・1メッセージ・前からの繋ぎ（subtitle）・載せる証拠/ビジュアルの指定（数字は出どころ付き）・所属する章」を持つ。
- **次工程**：`slide-plan.md` を pptx-custom に渡して描画させる。本スキルは描画しない。

---

## 4つの観点（原則の地図）

原則は数が多いので、**使うときは4つの観点で読む**。どの原則も、読み手がどこで止まるかの4種類のどれかを防ぐためにある。

| 観点 | 読み手が止まる形 | 主な原則 |
|---|---|---|
| **A. 流れ** | 「なぜ急にこの話？」「これは何の続き？」 | 0-0, 0-2, 1, 2, 4, 5, 7, 8, 10, 16, 19, 20 |
| **B. 言葉** | 「この言葉はどういう意味？」「どこを読めばいい？」 | 0, 3, 6, 14, 21 |
| **C. 相手の受け取り方** | 「否定された」「なら最初から言って」「どう答えれば？」 | 9, 15, 17, 18, 22 |
| **D. 根拠** | 「その数字は誰の？どこから？いつの？」 | 11, 12, 13 |

**指摘を受けたら、原則を足さない。** どの観点の話かを決め、`references/review-questions.md`（指摘台帳）に問いとして1行足す（足し方は台帳の冒頭）。原則を足すのは、どの観点の問いにも書けない「作り方そのもの」の話のときだけ。こうしておくと、原則は増え続けず、確かめる問いだけが案件ごとに厚くなる。

## 構成の原則（0-0〜0-2 は前提、1〜22 は本文の作り方）

### 0-0. 章は「読み手の問いの木」から作る（型から作らない）

**これが全原則の前提。** 章の型（現状→課題→提案→数字→決めてほしいこと）を先に置くと、各ページは正しくても、ページの間で「なぜ急にこの話？」「その数字はどこから？」という飛躍が生まれる。

1. 読み手がこの会議で答えを出したい**根の問い**を1つ書く（読み手の言葉で）。
2. それに答えるために読み手が順に納得すべき**子の問い**を3〜6個書く（なぜ／どこから／どれが／いつ／いくら）。
3. 子の問いの順番を章の順番にし、各問いに**答えるスライド**を割り当てる。
4. **答えるスライドの無い問い＝穴。答える問いの無いスライド＝不要。**
5. 各スライドの直後に読み手が口にしそうな問いを1つ書き、次のスライドがそれに答えているかを見る。

**絞り込む前に、絞り込む理由を見せる。** 全体の数字（売上の増加額）から特定の事業・施策の話に移るときは、間に「その増加のうち、どの事業が何割か」を置く。これが無いと読み手は「なぜこの事業の話？」で止まる。

下の 0-2 の「標準形」は、問いの木を立てた後に抜けを見るための参考。型を先に埋めない。

### 0. 階層で書き方を変える（Action title を全階層に適用しない）

**これは原則1〜15の前提**。ここを間違えると、資料全体の道案内が壊れる。

| 階層 | 役割 | 書き方 | 例 |
|---|---|---|---|
| **表紙タイトル** | **何の提案書か** | **提案の中身を名乗る**。問いや主張にしない | ○「現場のAI活用に関するご提案」／✕「4年で4.9倍を、誰が担うのか」 |
| **章タイトル（中扉・目次）** | **その章で何を話すか** | **ラベルでよい。むしろラベルであるべき** | ○「貴社の理解」「弊社のご提案」／✕「すでに答えは書かれています」 |
| **本文スライドのタイトル** | その1枚の主張 | **言い切る（原則3）** | ○「利益もAUMも、4.9倍という同じ倍率です」 |

表紙・目次・章扉は**主張する場所ではなく、読み手が現在地を知るための道具**。ここを主張に置き換えると、
「後日社内で回覧されたとき、何の提案書か分からない」「これから何の話が始まるのか分からない」という事故になる。

**刺さる問いや強い主張は捨てない。本文スライドに下ろす。** 表紙のサブタイトル1行に置くのは可。

### 0-2. 章立ては「論証順」ではなく「会議の進行順」で切る

骨子（storyline）は論証の順序で書かれている（事実 → 課題 → 提案）。**それをそのまま章立てにしない。**
提案書は論文ではなく、その場で読み上げるものなので、**会議の進行順**に並べる。

**顧客向け提案書の標準形**

```
　本日の目的                    ← 章に入れない。冒頭に単独で置く
                                  「今日は何をご提案しに来たか」＋「本日お聞きしたいこと」

第1章  貴社の理解               ← 我々が理解している相手の状況（事実と論点）
第2章  弊社のご提案             ← 打ち手・対象・実績
第3章  進め方とお聞きしたいこと ← 始め方と、相手に答えてほしい質問
```

- **アジェンダの基本形は「貴社の理解」と「弊社のご提案」の2本。** 進め方・確認は3本目。
- **「本日の目的」を章の中に入れない。** 「貴社の◯◯」という章の1枚目が「本日の目的」になっていたら、それは論証順で切っている証拠。
- 章を8個並べない。**3つ前後の大きな塊**にし、その中の小見出しはパンくずで示す。

**社内会議・稟議向けの標準形**（自社の中で「決めてもらう」資料。顧客向けの「貴社／弊社」は使わない）

```
　決めてほしいこと              ← 章に入れない。冒頭に単独で置く
                                  「何を・いつまでに・誰が決めるか」＋ 結論（推す案）を1行

第1章  いま起きていること       ← 事実と数字（現状・問題・放置した場合の影響）
第2章  選択肢と推す案           ← 案A/B/（やらない）の比較と、推す理由
第3章  費用・リスク・進め方     ← いくら・何が起きうるか・止める条件・日程
```

- 1枚目で**結論と決裁事項**を言い切る（社内の読み手は結論から読む。背景から始めない）。
- 「やらない」案を必ず比較に入れる（稟議で最初に問われる）。
- 保存先は `osi-profile.md` の `{{paths.internal_docs}}`（既定「共通/社内資料」）。案件フォルダには置かない。
- 配色は自社資料の扱い（`osi-profile.md` の `brand.*`、未設定なら中立色。pptx-custom「どの色を使うか」）。

### 1. 枚数は骨子から導く（先に決めない）

「17枚で」「14枚で」と先に枚数を決めない。骨子の各段（3〜5段）を起点に、**1段が1枚で足りるか／複数枚に割るべきか**を判断して積み上げる。足りなければ足し、冗長なら畳む。結果として枚数が決まる。

### 2. 1スライド1メッセージ

1枚に主張を詰め込まない。骨子の1段が2つの主張を含むなら2枚に割る。**枚数を増やしてでも呼吸させる**方が、詰め込んで読ませるより伝わる。

### 3. 本文スライドのタイトルは Action title（言い切る）

各**本文**スライドのタイトルは、**結論を1文で言い切る**。論点ラベル（「市場規模について」「課題」）にしない。
（表紙・章タイトルには適用しない。原則0を参照）

- ❌「市場規模」→ ✅「狙う市場は、競合と違う場所にある」
- 日本語 24pt で1行に収まる目安 **≤21文字**。収まらなければメッセージが二つある＝割る合図。
- **表・グラフのスライドは、タイトルで「何を読んでほしいか」を言う。** ❌「稼働数の推移」→ ✅「1人あたりの稼働が増えないと、5期の計画に届かない」。どの行・列を見ればいいかを強調で示す指定を slide-plan に書く。

**タイトル・メッセージの禁止パターン（顧客向け）**

| 禁止 | 理由 | 直し方 |
|---|---|---|
| 「〜とは」「〜の分析」「〜について」 | ラベルであって主張がない | 事実面は「◯◯の実績」「◯◯の過去事例」、提案面は「◯◯へのご提案」 |
| 「だから◯◯はこうする」 | 社内の言い方 | 「◯◯へのご提案」 |
| 「本日の位置づけ」「我々から提案します」「本日は◯◯を説明します」 | **主語が提案側**になっている | 主語を顧客に。「◯◯についてご認識を合わせたい」 |
| メッセージが数字の羅列（「国内は2,700億円、海外は616億円です」） | 事実の要約で、主張がない | 「自力で伸びるのは約330億円。不足は1,150億円です」 |
| 「〜を整理します」「〜の状況です」で終わる | 同上 | 何が言えるのかを言い切るまで確定しない |
| 読み手が使っていない略語・業界語で言い切る（席／クレジット／β／Phase／FY／KPI／ICP／GTM／トラフ 等） | 読めるが意味が取れず、内容の議論に入れない | 読み手が議事録・依頼の場で使った言葉に置き換える（例：席→利用人数、GTM→売り方）。→ 自問：**タイトルだけを読んで、議事録の言葉しか知らない人が意味を取れるか** |
| 言い切りが比喩や省略で圧縮されている（「AI秘書を顔に席＋オプション」「原価のデータを握る側に立つ」） | 作り手には一文でも、読み手には解読が要る | 主語・目的語を補って普通の文にする。長くなるなら2枚に割る |
| 「新規事業」「新サービス」「3事業」のような総称で言い切る | 何の話かがぼけ、読み手は中身に入れない | 事業名・サービス名・地域名で書く（原則14） |

**判定基準：そのタイトル／メッセージを読んで、聞き手が頷くか首を振るかのどちらかになるか。** どちらにもならないなら、それは主張ではなくラベル。

### 4. Subtitle は「繋ぎ」であってラベルではない

サブタイトルは前のスライドから現在へ橋を架ける。聞き手の無言の問い「なぜ今これを見ているのか」に答える。

- ❌「コア事業の説明」→ ✅「では本丸の定額サービス事業を——仕組み・価格・現状を見ていく」

### 5. ピラミッドで積む（縦は why/so-what、横は MECE）

頂点＝コアメッセージ。2段目＝骨子の3〜5主張。各主張に紐づくスライド群は、その主張の下で**重複せず漏れなく**並ぶ。縦は「なぜ？／だから？」で繋がる。骨子のピラミッドをそのままスライドの階層に落とす。

### 6. 概念は使う前に定義する

複数スライドで使う用語・略語（自社サービス名, ARR, NPS 等）は、**初出のスライドで**定義する。5枚後に「Xとは」を置かない。定義はサブタイトルにインラインで入れるか、使い始める前に定義スライドを1枚置く。

### 7. 15枚超はナビゲーションを付ける

長いデッキは「いま全体のどこか」を常に示す。3点セット：先頭付近の**目次**、章の変わり目の**章扉**、各スライド上部の**パンくず**（例：`PART C · 実行方法`）。繰り返し参照する中心図があれば**アンカー**にして、各詳細スライドを「この図のこのセルを今ズームしている」と接続する。

**章扉は全章に置く（1つも欠かさない）。** slide-plan.md を確定する前に「章の数 ＝ 章扉の枚数」を数えて一致を確認する。1章だけ扉が無い、が最も起きやすい欠落。

**目次は階層化する。** 章をフラットに10個並べない。**大区分（現状／ご提案／効果と進め方 等）→ 章**の2階層にして、大区分ごとにページ範囲を持たせる。

**目次の小項目名は、本文スライドのタイトルと同じ文字列にする（同じ元リストから両方を生成する）。** 目次とタイトルを別々に書くと必ず食い違い、読み手は「目次のどれを今話しているのか」を探し始める。slide-plan.md の「スライド一覧」を唯一の元にし、描画側（pptx-custom）は目次・章ラベル・パンくずをそこから機械的に作る。

**議論用の資料（事業主・経営層に「この考え方でいいか」を聞くたたき台）は、15枚以下でも目次を置き、章の区切りごとに再掲する。** 提案書と違い、議論用は読み手が構成そのものを問う（「なぜこの順で話すのか」「なぜこの話が要るのか」）。先頭に一度だけ目次があっても、章に入った時点では忘れられている。
形：番号付きの章（1. 2. 3.）＋その下に小項目（2.1 2.2）。**再掲時は、これから話す章だけ黒、他の章はグレー**。右または下に「この章で話すこと」を1〜2行。章扉の代わりに目次の再掲を置いてよい（扉を全章に立てると議論用には枚数が膨らむ）。
→ 自問：各章の名前は「その章に何が書いてあるか」が分かるラベルか（「現在地」より「資料から読み取った現在の状態」）。

> 観測（2026-09 / ある事業者の事業戦略のたたき台・23枚・事業主向け）：先頭1枚の目次だけで出したところ「最初の目的の後になぜ機能一覧が来るのか」「6層37分類の話がなぜ大事なのか」と構成自体を問われた。章ごとに目次を再掲し（次の章だけ黒・他はグレー）、小項目名をスライドタイトルと同じ文字列にしたら通った。小項目名を要約して書いた版は「アジェンダの内容とタイトルが合っていない」と差し戻された。

**ページ番号は slide-plan.md に書かない。** 描画後に実測して振るもの（pptx-custom 側）。構成段階で番号を確定させると、1枚増減した瞬間に全部ズレる。

### 8. 用語を統一し、本編を未解決で終えない

同じ概念を別の語で呼ばない（「中核資産」と「横断資産」を混在させない）。「未解決の論点／TBD」スライドはクロージング直前に置かない——本編の最後を「まだ決まってない19個」で締めると、それまでの説得が崩れる。付録に回す。（相手に答えてもらう質問で締めるのは別。原則15）

### 9. 本編は具体だけ。抽象は Appendix に置く

「3つの型」「フレームワーク」「分類」「マトリクス」といった**抽象の整理は本編に置かない**。本編は「誰が・いつ・何をして・数字がどう動いたか」の具体で通す。

抽象は作り手には気持ちよく見えるが、聞き手には「で、うちはどうすればいいのか」が残る。**抽象を1枚置きたくなったら、その抽象から導かれる具体が本編にあるかを確認し、抽象そのものは Appendix へ回す。**

同じ理由で、**調査の網羅性を見せるスライド**（「n社を調べました」の一覧そのもの）も、それ自体が主張になっていなければ Appendix。

### 10. 隣接する2枚が同じことを言っていないか

構成段階で最も見落とすのが**隣接重複**。「指標の目標と実績」の次に「指標が悪化している」を置くと、同じ表を2回見せることになる。

slide-plan.md を確定する前に、**連続する2枚のメッセージと載せる証拠を突き合わせ、同じ指標・同じ表が2回出ていないか**を確認する。重なっていたら片方を削るか、片方に畳む。

### 11. 外部事例は「3点セット」でしか載せない

他社事例・競合の動き・調査結果・市場データを本編に置くときは、次の3つが揃っていること。1つでも欠けたら、そのスライドは Appendix へ回すか、削る。

| # | 要素 | 欠けたときに起きること |
|---|---|---|
| ① | やったこと（**会社名・年月・出典付き**） | 何の話か、いつの話か分からない |
| ② | **結果**（数字。◯%削減／◯件／◯か月で） | 「へえ」で終わる。判断材料にならない |
| ③ | **相手ではこうする**（相手の業務名で書いた具体） | 「よその話」で終わる。**ここが本体** |

**③が一番大事で、一番よく抜ける。** 事例を集めた達成感で①だけ書き、②を忘れ、③に至らない。聞き手の頭には最初から最後まで「で、うちはどうすればいいのか」がある。③はその答えそのもの。

③は相手の固有名詞で書く。「業務効率化が期待できます」は③ではない。「仲介から届く物件概要書を、担当者が1件ずつ開いて見る／見ないを判断している。ここを投資基準による自動仕分けにする」が③。

枚数の目安：**①②に1枚使ったら、③には2枚以上使う。** 事例の枚数が③の枚数を上回っていたら、それは調査報告であって提案ではない。

事例から③へ渡すときは、**事例の「作り方」を抽出して橋にする**。「A社は◯◯をやった／B社は△△をやった」の羅列で終わらせず、「成果が出た会社に共通する作り方はこの3つ。ではそれを貴社のどの業務に当てるか」と繋ぐ。**並びは必ず 事例 → 当てはめ。** 提案が事例から来ていることが、ページの並びだけで分かるようにする。AI で作った素案は「提案・AIで作った素案」と明記する。

### 12. 「具体」の定義 ── 一覧は具体ではない

「対象になりうる業務を18個並べた」は**具体ではない**。それは網羅性の提示であって、聞き手は自分の明日が変わる像を受け取れない。

具体とは、1つの業務について次が全部書けている状態：

| 項目 | 例 |
|---|---|
| 業務名 | 開発用地の一次スクリーニング |
| いまの姿 | 仲介から届く物件概要書を、担当者が1件ずつ開いて判断している |
| 変わった後 | 投資基準で自動仕分け。判断根拠を併記し、担当者が上書きできる |
| 効果の測り方 | 1週間に検討できる物件数 |
| 最初の日程 | 1〜2日目に同席／3〜5日目に基準を書き出す／6〜8日目に一緒に作る |
| 出てくるもの | 動くツール1本、判断基準1枚 |
| 止める条件 | 担当者が翌週も使わなければ、そこで止める |

一覧（網羅）は1枚に留め、そこから**1〜3業務に絞って**この深さまで書く。**一覧だけで本編を終えるのは、提案していないのと同じ。**

各業務には**出所を書く**。相手の公表資料（中計・IR）に書かれているものか、こちらからの追加提案かを表に明示する。追加提案を、相手が既に決めたことのように混ぜない。ここを正直に分けると、追加提案のほうがむしろ通りやすくなる。

数字を出すときは**算出根拠を同じ画面に置く**。「3か月で20業務」と書くなら「他社は150名で500件＝1人3件。6名×3件＝約20件」まで見せる。根拠のない目標値は、その場で崩される。

### 13. 数字には出どころと導出を付ける（誰の数字か、どこから来たか）

本編に出る数字はすべて、次の2つを持つ。

- **出どころ**：「御社計画」「当社試算」「公表資料（名称・年月）」のどれか。**当社試算を、相手が出した数字のように書かない。** 額だけが出ていると、読み手は「それは誰が言った数字か」で止まる。
- **導出**：その数字の内訳・計算式が、**同じスライドか直前のスライド**にある。5枚後に種明かしをしない。読み手に逆算させない。

加えて：
- **シナリオを混ぜない。** 基準の計画と別シナリオ（堅め・施策あり・遅れた場合 等）を、名前を付けずに同じ表・同じグラフに並べない。並べるなら列・線を分けて名前を書く。
- **資金は線で見せる。** 売上・利益の推移 → 月次の現金の線（計画どおり／遅れた場合）→ 一番へこむ時点の不足額 → 調達したい額 → 使い道。額だけのスライドを先に置かない。
- **ツール・AI の提案は、相手の伸びを止めているもの（ボトルネック）を示した後に置く。**

slide-plan.md の「載せる証拠」欄には、数字ごとに出どころを書く（例：「5期売上 12.3億円（御社計画）」「最大不足 約7,700万円（当社試算・遅れた場合）」）。

### 14. 固有名詞と年月で書く

- 事業・施策・サービス・地域は**固有名詞**で書く。「新規3事業」ではなく3つの事業名。「ある地域で」ではなく地域名。
- 事例・実績・市場データには**年月**（開始・公表・対象期間）を付ける。いつの話か分からない事例は、読み手には古いか新しいかも判断できない。
- 施策には**いつ始めるか**（予定月・期）を書く。

### 15. 最後は「相手が答えられる質問」で終える

議論用・相談用の資料の最終ページ（と冒頭の「本日お聞きしたいこと」）は、「決めていただきたいこと」ではなく**質問**で書く。

- **Yes/No で終わる問い、「どう思いますか」で終わる問いにしない。** 相手が数字・名前・時期・どちらかの選択で答えられる形にする。
  ❌「資金計画をご確認ください」「AI施策を進めてよいですか」
  ✅「資金と採用の計画は、どちらの売上計画を基準に組みますか？」「8・9月の実績を教えていただけますか？」
- 表の列は **#／お聞きしたいこと／回答の例／答えで決まること**。回答の例があると答えやすく、答えで決まることがあると聞く理由が伝わる。
- 額を含む問いは**誰の数字か**を問いの中に書く（「約8,000万円（当社の試算）のうち〜」）。
- 冒頭と最終ページの質問は**同じ元リストから生成する**。


### 16. 根の問いが変わったら、直さずに組み直す

相手の目標や問いが途中で変わったら（例：資金の相談 → 期限までにある水準へ届くか）、既存のページを継ぎはぎしない。**問いの木を根から立て直し、これまでのページは素材として使う。** 章の順番・どこで絞り込むか・最後の質問まで、根の問いが決めているから。

### 17. 目標の「測り方」は、こちらで置いて見せる

相手が掲げた目標（企業価値・シェア 等）の測り方を、相手に聞き返さない。公表された物差しからこちらで置き、**置き方と、置き方を変えたときの幅**を同じページに書く（「当社の置き方」と明記）。相手が求めているのは定義の確認ではなく、「どうすれば届くか」の絵。

### 18. 相手の計画を否定せず、「目指す線」と「詰まりどころ」で話す

相手の計画に届かない見通しを出すとき、「このままでは届きません」と基準線から入ると、相手には計画の否定に聞こえる。順番は固定する：

1. **相手の計画を「目指す線」として先に置く**（相手の数字のまま）
2. **その線を目指す上で、詰まりそうな箇所を挙げる**（相手の資料から、出典付きで。数は2〜3に絞る）
3. **そこで詰まった場合の線**を、原因の名前で示す（「堅め」「保守的」ではなく「◯◯で詰まった場合」「今の体制のまま」）
4. 差（伸びしろ）がどこにあるか → 打ち手 → **実行前と実行後の比較**で閉じる

基準線を作り手の都合で下げた数字に見せると、「なら最初から施策込みで出せばいい」と言われる。基準線は、相手の計画を目指したときに起きることとして描く。

### 19. 「なぜ」は、抽象 → 具体 → 帰結 を1枚ずつ

「なぜ届かないか」の最初のページは構造を一言で言う（抽象）。次のページで数字で確かめ（具体。「足りるのか」と問うたら、足りる／足りないに正面から答える）、その次で計画にどう響くか（帰結）を見せる。1枚に3つを詰めない。
似た言葉で別のものを指すとき（現場で働く人と、それを管理する人 等）は、番号を振って区別して定義し、以後その呼び方を崩さない。

### 20. 打ち手の章は、考え方の前段から入る

打ち手の章の頭に、**〈課題をどう捉えたか → そこから立てた問い → どんな条件で事例を探したか〉**を置いてから事例に入る。提案がどこから来たかが見えると、読み手は案の良し悪しを議論できる。

- 事例の当てはめページは表の羅列にせず、**「事例から分かったこと → 相手で狙うこと → やること（時期つき）→ 値段・測る数字」**の一本の流れで書く。
- AI・ツールの提案は、**「今（人がやっている動作）→ 後（AI がやる動作）」**で書き、何をするかを動作で見せる。「AIで効率化」で止めない。

### 21. 計算は、読み手の常識どおりの一本道で見せる

利益や価値の計算は、読み手が知っている順番（売上 → 費用 → 税の前 → 税 → 税引後 → 倍率）の一本道で見せ、**最後の数字を色・太字で目立たせる**。「利益からさらに費用を引く」ように見える言葉の組み方は、そこで質問が出て止まるので、言葉を変える。

### 22. 相手が今日決めない計算・資料に無い理由は載せない

- 相手が今日決めない話（資金の入れ方の細かい試算 等）は本編から外し、社内メモに「聞かれたら口頭で」として持つ。
- 相手の資料に書かれていない理由（止めている理由 等）を推測で断定しない。書かれていることだけを出典付きで書く。

## 最重要QA（1）：声に出して読む

`slide-plan.md` ができたら、**各スライドの Action title と subtitle を、上から順に声に出して読む**。プレゼンするつもりで。

接続詞を足さずに自然に流れるなら、構成は通っている。「えーと、次は…」「これはつまり…」と**橋渡しの言葉を自分で発明したくなったら、その繋ぎ目のスライドが欠けているか順序が違う**。これは見た目のQAより重要——見た目のバグは聞き手が我慢するが、流れのバグは話し手が準備不足に見える。

## 最重要QA（2）：相手になって読む

声出しQAは「話し手として流れるか」の確認。次に**聞き手として止まらないか**を確かめる。

1. 読み手の立場・知っている言葉・関心を1〜2行で書く（例：「事業主。自社の数字は知っているが、財務モデルの言葉は知らない。知りたいのは、いくら要って、うちは何をすればいいか」）。
2. その人になって、スライドを1枚ずつ読み、**浮かんだ問いをそのまま書き出す**。
3. 問いが次のスライドで答えられていれば通過。答えられていなければ直す：

| 浮かんだ問い | 直し方 |
|---|---|
| 「なぜ急にこの話？」 | 間に理由（内訳・ボトルネック）のスライドを足す（原則0-0） |
| 「この数字はどこから？誰の数字？」 | 出どころと導出を付ける（原則13） |
| 「この表は何を見ればいい？」 | タイトルで読み方を言い、見る行・列を強調する（原則3） |
| 「何の話？」 | 固有名詞にする（原則14） |
| 「それはいつの話？」 | 年月を付ける（原則14） |
| 「これ、どう答えれば？」 | 答えられる質問に直す（原則15） |

可能なら、サブエージェントに読み手役を渡して読ませる。**渡すのは読み手の立場と slide-plan（または描画後の画像）だけで、作り手の意図は渡さない**（意図を知っていると飛躍が見えなくなる）。

> 観測（2026-09 / ある事業者の年次計画を読み込んだ打ち合わせ資料・30枚）：型で組んだ初版に対し、読み手（事業主側の担当）から「全体の売上から急に1事業の話に飛ぶ」「この稼働数の表の意味が分からない」「資金は額より、売上・利益と現金の線が見たい」「新規事業を事業名で書いて」「事例がいつのものか分からない」「決めてほしいことが答えようがない。8,000万は誰の数字か」と続いた。どれも上の表のどれかに当たる。作り手が声出しQAだけで確認していたため、話し手としては流れても、聞き手が止まる箇所を拾えていなかった。

> 観測（2026-09 / 同じ事業者・目標が「3年である企業価値に届くか」に変わった後の作り直し・38枚）：部分修正では通らず、問いの木から組み直した。その後の指摘は ——「企業価値は何で測るのか、を相手に聞くのではなく、こちらで置いて夢を描く」「堅めとは誰の仮説か。理由が無いと『最初から施策込みで出せ』になる」「なぜ届かないかは、まず抽象で一言、次に数字、次に計画への影響」「打ち手の章は、課題の捉え方と事例の探し方から入る」「事例の当てはめは表では伝わらない。事例 → 狙い → やること で」「『このままでは◯億円』は計画の否定に聞こえる。計画の数字を目指す上での詰まりどころを挙げ、そこで詰まると◯億円、と話す」。原則16〜22はここから来ている。

## 最重要QA（3）：4つの観点で指摘台帳を当てる

（1）（2）は作り手と読み手の目で「流れ」を見るQA。最後に、`references/review-questions.md` の問いを **A 流れ → B 言葉 → C 相手の受け取り方 → D 根拠** の順に1観点ずつ当てる。一度に全部を見ると、目立つ観点（見た目・数字）に引っ張られて C が抜ける。

- 可能ならサブエージェントに読み手役で当てさせる。渡すのは読み手の立場・資料・台帳だけで、作り手の意図は渡さない。
- 返させるのは「引っかかったページ番号と、読み手が口にしそうな一言」。
- 引っかかった問いの横の原則番号を見て直す。
- **ユーザーや読み手から新しい指摘を受けたら、その場で台帳に問いとして足す**（案件名・数字は書かない）。次の資料では、その指摘は出る前に拾える。

## ワークフロー

```
0. storyline.md（承認済み）を受け取る。無ければ storyline-gate へ戻す
0.5 問いの木を立てる（根の問い → 子の問い → 答えるスライド）。business-plan-builder から
    question-tree.md が来ていればそれを使う（原則0-0）
1. 骨子の各段・各問い → スライドに割る（原則1〜2）
2. 各スライドに Action title と繋ぎ subtitle を立てる（原則3〜4）
3. ピラミッド整合・用語・定義・ナビを点検（原則5〜8）
3.5 抽象が本編に残っていないか／隣接2枚が重複していないかを点検（原則9〜10）
3.6 外部事例が3点セット（やったこと・結果・相手ではこうする）になっているか、
    「具体」が業務名・現状・変化後・測り方・日程まで下りているかを点検（原則11〜12）
3.7 数字の出どころ・導出、シナリオの混在、固有名詞・年月、最後の質問が答えられるかを点検（原則13〜15）
3.8 相手の計画を「目指す線」として置き、詰まりどころ → 詰まった場合 → 打ち手 → 実行前後、の順か。
    打ち手の章に前段（捉え方・問い・事例の探し方）があるかを点検（原則17〜22）
4. 声に出して読むQA → 繋ぎ目の欠けを直す
4.5 相手になって読むQA → 浮かんだ問いに答えるよう直す
4.6 4つの観点で指摘台帳を当てる（references/review-questions.md）→ 引っかかった所を直す
5. slide-plan.md を確定 → pptx-custom に引き渡す（目次・章ラベルは slide-plan の一覧から機械生成させる。別途手書きしない）
6. 描画後、画像でもう一度「相手になって読む」と「指摘台帳」を当てる
7. 受けた指摘は、原則ではなく指摘台帳に問いとして足す
```

pptx-custom が機械的に読める1枚。これがスキル間の受け渡し物。

```markdown

- 根の問い: {読み手の言葉で1つ}
- 子の問い: 1. {…}（S3–S5） 2. {…}（S6–S9） …

## 章構成
- PART A: {章タイトル}（S1–S4）
- PART B: ...

## スライド一覧
| # | 章 | 答える問い | Action title（言い切り） | 1メッセージ | 繋ぎ(subtitle) | 載せる証拠/ビジュアル（数字は出どころ付き） | 読んだ直後の問い → 答えるスライド |
|---|----|-----------|------------------------|------------|---------------|--------------------|------------------|
| 1 | – | – | {表紙} | – | – | – | – |

## ナビ要否

- ページ番号は本ファイルに書かない（描画後に実測して振る）

## 確定前チェック
- 章が問いの木から作られ、答えるスライドの無い問い・答える問いの無いスライドが残っていない: はい/いいえ
- 全体の数字から特定の事業・施策に絞る前に、絞る理由（内訳）のスライドがある: はい/いいえ
- 表紙タイトルは「何の提案書か」を名乗っている（問い・主張になっていない）: はい/いいえ
- 章タイトルは「その章で何を話すか」になっている（主張になっていない）: はい/いいえ
- 「本日の目的」が章の外に置かれている: はい/いいえ
- 章の数 ＝ 章扉の枚数 が一致した: はい/いいえ
- 抽象（型・分類・フレーム）が本編に残っていない: はい/いいえ（残るものは Appendix へ）
- 隣接2枚で同じ指標・同じ表が繰り返されていない: はい/いいえ
- 全 Action title が「頷くか首を振るか」のどちらかになる（ラベルでない）: はい/いいえ
- 表・グラフのスライドは、タイトルで何を読むかを言っている: はい/いいえ
- 外部事例に「会社名・年月・出典」と「結果（数字）」が書かれている: はい/いいえ
- 外部事例のあとに「相手ではこうする」が相手の業務名で書かれている（事例 → 当てはめ の順）: はい/いいえ
- 事例に使った枚数 ≦ 相手の具体に使った枚数 になっている: はい/いいえ
- 具体スライドに「効果の測り方」と「最初の日程」が入っている: はい/いいえ
- 各施策に出所（相手の公表資料 / こちらからの追加提案）が書かれている: はい/いいえ
- 全ての数字に出どころ（御社計画／当社試算／公表資料）があり、導出が同じか直前のスライドにある: はい/いいえ
- シナリオが名前なしに混ざっていない: はい/いいえ
- 事業・施策・地域が固有名詞で書かれている: はい/いいえ
- 最終ページが、答えられる質問（回答の例・答えで決まること付き）になっている: はい/いいえ
- 目次の小項目名 ＝ 本文スライドのタイトル（同じ文字列）になっている: はい/いいえ
- 議論用資料なら、章の区切りごとに目次を再掲する指定がある: はい/いいえ
- タイトルに、読み手が使っていない略語（席／β／Phase／FY／KPI／ICP／GTM 等）が残っていない: はい/いいえ
```

## やってはいけないこと

- **骨子なしで構成し始める** — 入力は承認済み storyline.md。無ければ storyline-gate へ。
- **型の章立てを先に埋める** — 章は読み手の問いの木から作る。型は抜けを見るための参考（原則0-0）。
- **枚数を先に決める** — 「17枚で」から入らない。骨子から積み上げる。
- **ラベルタイトル（本文スライド）** — 「課題」「市場」で止める。言い切るまで確定しない。
- **逆に、表紙・章タイトルを言い切りにする** — 表紙は「何の提案書か」、章は「何を話すか」。ここを主張にすると道案内が消える（原則0）。
- **骨子の論証順（事実→課題→提案）をそのまま章立てにする** — 章は会議の進行順で切る（原則0-2）。「本日の目的」が章の中に入っていたら間違い。
- **骨子に無いスライドを足す** — かっこいいからで1枚増やさない。各スライドは骨子のどの段（どの問い）に紐づくか言えること。
- **描画に踏み込む** — 色・フォント・座標・図形を決める。それは pptx-custom の仕事。
- **声出しQA・相手になって読むQAを飛ばす** — 構成スキルで一番効くQA。
- **ラベルのまま／主語が提案側のまま確定する** — 「本日の位置づけ」「〜について」「だから◯◯はこうする」を残す。
- **抽象（型・分類・フレーム）を本編に置く** — Appendix に回す。
- **章扉を1つ落とす** — 章の数と扉の枚数を必ず数える。
- **ページ番号を slide-plan.md に書く** — 1枚増減で全部ズレる。描画後に実測する。
- **隣接2枚の重複を見逃す** — 同じ表を2回見せる構成は、必ず「これ要らない」と言われる。
- **他社事例を「やったこと」だけで載せる** — 結果（数字）・年月と「相手ではこうする」が無い事例は、相手にとって何の情報でもない（原則11）。
- **業務の一覧を並べて、具体を書いたつもりになる** — 一覧は網羅性の提示。具体は「1業務が、いま誰の手でどうなっていて、どう変わり、何で測るか」（原則12）。
- **事例のほうが具体より枚数が多い** — それは調査報告。提案書ではない。
- **相手の公表資料にある施策と、こちらの追加提案を混ぜる** — 出所を分けて書く。混ぜると全部が疑われる。
- **出どころの無い数字・導出が後ろにある数字を出す** — 読み手は「誰の数字か」「どこから来たか」で止まる（原則13）。
- **当社試算を相手の計画のように書く／シナリオを名前なしに混ぜる** — 全部の数字が疑われる（原則13）。
- **総称で書く（新規事業・ある地域）／事例に年月が無い** — 何の話か、いつの話かがぼける（原則14）。
- **最後を Yes/No の問いや「ご確認ください」で終える** — 相手が答えようがない（原則15）。
- **目次の小項目を、スライドタイトルと別の言葉で要約して書く** — 必ず食い違う。同じ元リストから生成する（原則7）。
- **議論用の資料で目次を先頭1枚だけにする** — 章に入った時点で構成が忘れられ、「なぜこの順か」を問われる（原則7）。
- **読み手が使っていない略語でタイトルを言い切る** — 読めるが意味が取れない。読み手の言葉に置き換える（原則3）。
- **指摘を受けるたびに原則を足す** — 原則が増えるほど守られなくなる。指摘は指摘台帳に問いとして足す（4つの観点）。
- **根の問いが変わったのに、既存ページの継ぎはぎで済ませる** — 絞り込みの位置も最後の質問も変わる。組み直す（原則16）。
- **目標の測り方を相手に聞き返す** — こちらで置いて見せる（原則17）。
- **「このままでは届かない」から入る** — 計画の否定に聞こえる。計画を目指す線に置き、詰まりどころとして話す（原則18）。
- **事例を表に並べて、当てはめを読み手に任せる** — 事例から分かったこと → 狙い → やること の流れで書く（原則20）。
