# 骨子ゲート（Storyline Gate）

資料づくりで一番効くのは、レイアウトでも配色でもない。**「何を、誰に、どの順で信じてもらうか」を、描き始める前に決めること**だ。プロとアマの差はここに出る。アマはスライド1枚目から描く。プロは骨子を1枚書いてから描く。

このスキルは、その「骨子を1枚書く」工程を独立させ、**承認が取れるまで描画に進ませない**ためのゲートである。型（テンプレート・枚数・パレット）は骨子から導出するのであって、先に選ぶものではない。

---

## このスキルがやること / やらないこと

**やること**は1つだけ。骨子を1枚（`storyline.md`）にまとめ、人と握る。

**やらないこと**：スライドを描く、pptx を生成する、レイアウト・配色・図形・ガントを設計する。これらはすべて描画スキル（proposal-estimate / deck-composition / pptx-custom 等）の責任。本スキルは「中身の設計図」を承認まで持っていって、描画スキルに引き渡すところで終わる。

> 引き渡しの原則：描画スキルは、承認済みの `storyline.md` を入力として受け取る。骨子が無い／未承認のまま pptx を作り始めてはいけない。

---

## 中核：骨子の5要素

骨子とは、次の5つの問いに答えたもの。これ以上でもこれ以下でもない。フォームを埋める作業ではなく、**問いに答える思考**だと考えること。

### 1. 決裁の構造 — 誰が、いま何を思っていて、Yesに何が要るか

- この資料を見て**最終的に判断する人は誰か**（同席者ではなく、決裁者）。
- その人は**いま何を信じているか**（現状認識・前提・警戒・過去の失敗）。
- **Yesと言うために、何を新しく信じる必要があるか**（＝この資料が動かすべき1点）。

ここが曖昧なまま進めると、誰にも刺さらない「一般論として正しい資料」ができる。最初に固めるべきはここ。

### 2. コアメッセージ — 一文で言い切る

- この資料が伝えたいことを、**主語と述語のある一文**で書く。
- ラベル（「AI活用について」「業務効率化の提案」）は禁止。それは見出しであってメッセージではない。
- テスト：その一文だけ相手に渡して、相手の判断が動くか。動かないなら、まだメッセージになっていない。

> 例（×）「貴社のDX推進について」→（○）「いまの3営業日の見積作成は、当日中に変えられる。最初の2ヶ月で実証します」

### 3. 論理の骨子 — 現在地からYesまでの最小ステップ

- 相手の**現在地（1で書いた認識）から、Yes に至るまでの最小の論理**を、3〜5段で書く。
- 各段は「主張」であること。**スライドのラベルではなく、言い切りの文**で書く。
- 各段は「だから次へ」とつながること。読み上げて、接続詞を足さずに流れるなら骨子は通っている。足したくなったら、その段は欠けているか順序が違う。

> ピラミッド：コアメッセージ（頂点）→ それを支える3〜5の主張（2段目）。横は重複せず漏れなく、縦は「なぜ？」「だから？」でつながる。

### 4. 証拠設計 — 各段に、どの強さの証拠を載せるか

- 骨子の各段ごとに、**相手を納得させるのに必要な証拠レベル**を決める。
  - レベル1：言葉・論理だけで足りる
  - レベル2：実物（サンプルExcel・試算・図）が要る
  - レベル3：動くもの（モック・実アプリ・デモ）が要る
- 相手が目利き・保守的・規制業界なら、コア主張ほどレベルを上げる。借り物の数値で盛らない。無いものは「一緒に測りましょう」と正直に書く。

#### 他社事例を証拠に使うなら、「相手ではこうする」まで骨子に書く

競合・同業他社の事例は、**それ単体では証拠にならない**。証拠になるのは次の3つが揃ったときだけ。

1. **やったこと** — その会社が何をしたか
2. **結果** — 数字で。◯%削減／◯件／◯か月で
3. **相手ではこうする** — 相手の業務名で書いた具体。**ここまで書けて初めて、その事例は骨子の1段になる**

③が書けない事例は、骨子から落とす。「A社はこうしています」で止まる情報は、相手にとって「よその話」でしかなく、判断を1ミリも動かさない。

骨子の段階で③が書けないなら、それは**相手の業務を知らない**ということ。事例をもう1つ探すのではなく、相手の業務（公表資料に書かれた用途・IRで語られた業務・面談で聞いた作業）に戻る。

#### 相手が「自分の数字」を公表している場合は、それを骨子の主語にする

上場企業・中期経営計画を出している相手なら、**論理の出発点は自分の分析ではなく、相手が公表している目標**にする。

- 相手の中計から**売上目標だけでなく財務指標の目標**（ROE・EBITDA比率・Net Debt/EBITDA・自己資本比率 等）を拾う。**指標側が本当の論点になっていることが多い。**
- 「目標」と「直近実績」を並べ、**差を算定する**。この差が提案の存在理由になる。
- 自力で埋まる分を積み上げ、**埋まらない額**を出す。ここから「だから◯◯が必要」が導かれる。
- **相手の指標で測るから、同じ内容が批判ではなく事実の確認になる。** 自分の物差しで「御社は◯◯が弱い」と言うと、その瞬間に提案ではなく評価になる。

数字は必ず一次情報から取る（決算短信・有価証券報告書・決算説明資料）。特に**決算短信の巻末「参考 主な経営指標の推移」**に会社自身が定義した指標が載っていることが多く、ここを読まず推定すると外す。詳細は `proposal-self-review` の A3。

### 5. 落とし穴 — この相手"固有"の地雷

- 一般論ではなく、**この相手だから起きる事故**を列挙する。
  - 既存ツール（置き換え提案に見えると反発する）
  - 規制・守秘（薬機法・個情法・情報セキュリティ）
  - 誇り・専門性（「代替される」と感じさせると終わる）
  - 過去の失敗体験・社内政治
- 各落とし穴に対し、骨子のどこで先回りして受け止めるかを1行で決める。

## ワークフロー

```
0. 入力を確認（相手・目的・既知の情報）。**社内にある一次情報（案件フォルダ・案件メモ・既存モック・議事録）を先に全部読む。**
   「この案件の想定テーマ」を1行で言えてから外部リサーチに進む
1. 5要素を埋めて storyline.md を起草
2. AskUserQuestion で「握りどころ」だけ承認を取る（後述）
3. 承認された storyline.md を確定 → 描画スキルに引き渡す
```

骨子が固まる前にリサーチで時間を溶かさない。リサーチは「5要素を埋めるために必要な分だけ」行う。

---

## 承認ゲート（ここが本体）

`storyline.md` を書いたら、**全文を承認させようとしない**。判断が割れる/方向を左右する点だけを `AskUserQuestion` で握る。典型的には：

- **コアメッセージの方向**（候補を2〜3案。攻め寄り／守り寄り、など軸が違うもの）
- **論理の順序**（未来から見せる順／不安を先に受け止める順 など、相手の感情曲線で割れるもの）
- **証拠レベルの上限**（言葉だけで出すか／実物・モックまで作り込むか＝工数とのトレード）

聞かないこと：色・フォント・枚数・レイアウト（描画スキルの領分。骨子の段階で決めない）。

承認が取れたら `storyline.md` を確定し、ここで初めて描画スキルを呼ぶ。**この順序は飛ばさない。**

## 出力フォーマット（storyline.md）

描画スキルが機械的に読める1枚。これがスキル間の唯一の受け渡し物。

```markdown
# Storyline: {相手} / {目的}

## 1. 決裁の構造
- 決裁者: {誰}
- 現状の認識: {いま何を信じているか}
- Yesに要る確信: {動かすべき1点}

## 2. コアメッセージ
> {一文。言い切り}

## 3. 論理の骨子
1. {主張1} — 証拠Lv{1-3}
2. {主張2} — 証拠Lv{1-3}
3. {主張3} — 証拠Lv{1-3}
（3〜5段）

## 4. 証拠設計
- {主張n}: {必要な証拠の中身。無いなら「一緒に測る」等の正直な扱い}

## 5. 落とし穴と先回り
- {地雷}: {骨子のどこでどう受け止めるか}

## 承認メモ
- 握った点: {AskUserで確定したこと}
- 日付 / バージョン
```

## やってはいけないこと

- **描画から始める** — スライドや pptx を、骨子の承認前に1枚でも作る。
- **型を先に選ぶ** — 「standard_17で」「14枚で」「3フェーズで」と、骨子より先に構成を決める。型は骨子から導く。
- **メッセージがラベルになっている** — 「○○について」で止まっている。主語と述語で言い切るまで進めない。
- **論理が飛んでいる** — 段と段が「だから」でつながらない。接続詞を足して読まないと流れない骨子は未完成。
- **証拠を盛る** — 借り物・架空の数値で段を支える。正直な証拠レベルで設計する。
- **全文承認を求める** — 細部まで承認させて相手を疲れさせる。割れる点だけ握る。
- **相手が公表している目標を使わずに、自分の物差しで課題を断じる** — 提案ではなく評価になる。相手の中計・開示指標を主語にする。
- **数字を二次情報のまま骨子に入れる** — 一次情報（短信・有報・説明資料）まで戻る。短信は巻末の「参考 主な経営指標の推移」まで読む。
- **コアメッセージを事実の要約で済ませる** — 「◯◯は2,700億円、△△は616億円です」は要約。「自力で伸びるのは330億円、不足は1,150億円です」が主張。
- **他社事例を「やったこと」だけで骨子に入れる** — 結果（数字）と「相手ではこうする」が書けない事例は落とす。
- **調査量で骨子の薄さを埋める** — 事例を増やしても、相手の業務に落ちていなければ判断は動かない。

## 補足：なぜテンプレートを「先に選ばない」のか

既存の描画スキルには優れた型（empathy_first / dual_axis / exec-deck-patterns 等）がある。それらは「過去のある案件で骨子から導かれた良い解」だ。最初から型を選ぶと、骨子を考える前に答えが決まってしまい、相手が違っても同じ資料が出る。**型は骨子を引き渡したあと、描画スキル側が骨子に最も合うものを選ぶ**。本スキルの責任は、その選択を可能にする「中身の設計図」を、承認まで持っていくことだけ。
