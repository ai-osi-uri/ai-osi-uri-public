# 業務 AS-IS / TO-BE 作成スキル

業態を問わず、業務プロセスを「現状（AS-IS）」と「あるべき姿（TO-BE）」で定義し、関係者全員で共通認識を持つための **スイムレーン中心の業務フロー資料（pptx）** を作成するスキル。

最終的な成果物は次の構成を持つ pptx：

1. **表紙** — タイトル、サブタイトル（変化の1行サマリ）、想定読者
2. **1行サマリ** — AS-IS / TO-BE を見開きで対比
3. **登場人物** — 4枚の役割カード（数値ハイライト付き）
4. **AS-IS 全体像** — 現状のシステム構成・データフローのアーキ図
5. **TO-BE 全体像** — 将来のアーキ図
6〜7. **全体スイムレーン（任意）** — `overview` セクションを定義した場合のみ。フェーズを横軸に取った AS-IS / TO-BE を別ページで描く
8〜N. **ステップ詳細スイムレーン** — 工程ごとのスイムレーン。デフォルトは「1スライドに上下で AS-IS / TO-BE」、`step.layout: "split"` を指定すると AS-IS / TO-BE を別スライドに分けてドキュメント凡例も付ける
N+1. **横軸の構造変化** — ツール数・データの正・運用ポリシーなどの観点別比較
N+2. **まとめ** — 大きな数字（ビフォー→アフター）と決め台詞

各セルは `label`（アクション）に加えて `doc`（更新/作成するドキュメント）を指定できる。指定すると、セル内にアクションと並べてドキュメント名がイタリックで表示され、「どこで何を触るか」が議論しやすくなる。

## ★ このスキルが大切にしている考え方

業務の AS-IS / TO-BE は、「何のシステムを使っているか」ではなく「**誰が・何を・どうしているか**」を描けて初めて意味を持つ。だからこのスキルでは：

- スイムレーンの**左軸は主体（actor）**で固定する。誰がボトルネックか、誰がただの伝言役になっているかが一目でわかる
- 各セルは **「目的語＋動詞」**で書く（例：「CSVを作成する」「住所を正規化する」）。名詞だけでは「何をしているのか」が伝わらない
- アクション同士のつながりは **矢印**で表現する。下から上に行く矢印（責任の戻り、再依頼、確認の差し戻し）も省略しない
- AS-IS では **人間が"プロトコル変換"している箇所**を強調する。TO-BE では **AI / API / 自動化が肩代わりしている箇所**を強調する

このスキルは単なる資料生成ツールではなく、業務のあり方そのものを見直す「鏡」を作ることを目的としている。

## 全体ワークフロー

```
1. ヒアリング（対話）  →  2. データ構築（JSON）  →  3. pptx 生成  →  4. レビュー
```

各ステップの詳細は以下。

### 1. ヒアリング — AskUserQuestion を使った対話で骨子を固める

ユーザーから渡された情報量によって、ヒアリング項目は変わる。最低限以下を確認する。**1質問1回のチャンクで聞き、4問以上を一度に投げない**こと。

#### 1-A. 業務全体の枠組み（必須・最初に確認）

- **対象業務 / 業態**：何の業務についての AS-IS / TO-BE か（例：「ある電力小売の申込処理業務」「飲食店の食材発注業務」）
- **想定読者**：この資料を誰に見せるか（経営層 / 現場 / 取引先）
- **AS-IS / TO-BE のキャッチコピー**：1行で何が変わるか（例：「人間がコピペで運ぶ運用 → AIが処理し人間が承認1クリック」）
- **業務ステップの数と名前**：4〜6工程に分解する。多すぎる場合は意味のある単位にまとめる

#### 1-B. 登場人物（4役）

役割名・人数規模・主な業務内容。アイコン候補：
- `users`（複数人）, `building`（会社）, `userTie`（管理職）, `userCog`（運営）, `user`（個人）

#### 1-C. AS-IS / TO-BE 全体像

- AS-IS で使われている主要ツール（4つまで） + 外部システム（4つまで）
- TO-BE で使われる主要ツール / プラットフォーム + 外部API・連携先

#### 1-D. ステップごとの詳細（最も重要）

各ステップについて以下を聞く：
- **レーン**：4本（多くて5本）。例：`代理店 / NEXT ONE 営業 / AI Agent / DB`、または `店舗 / 本部 / 仕入先 / 在庫システム` など
- **AS-IS のアクション**：時系列順に5スロットまで。各セルは**目的語＋動詞**で書く
- **TO-BE のアクション**：同上
- **更新するドキュメント**（任意）：各アクションが「どの台帳・ファイル・DBを作成/更新するか」。ドキュメント設計の議論をしたい場合は埋める
- **特筆すべき注釈**：「15:00締切」「成功率60%」「×2-5往復」「当日中必須」など、業務の痛みや特性
- **効果**：このステップを TO-BE 化するとどう変わるか（1行で）
- **レイアウト**（任意）：デフォルトは AS-IS / TO-BE を1スライドに上下で描く。`step.layout: "split"` を指定すると AS-IS / TO-BE を別々のスライドにし、各スライド下部にドキュメント凡例を描く

ユーザーが渡してくれた情報で埋まらない部分だけ追加で質問する。「不備がある」「往復が発生する」など示唆があれば、それを言語化して確認する。

#### 1-E. 全体スイムレーン（任意・強く推奨）

ステップ詳細とは別に、**全工程を1枚に俯瞰する全体スイムレーン**を AS-IS / TO-BE で各1枚作るかを聞く。`overview` セクションを config に追加すると、フェーズ（① 商談 → ② 契約 → ③ 登録 …）を横軸、レーンを縦軸とした全体マップが生成される。各セルにドキュメントも明記できるので、議論の起点として強力。社内設計議論で使うなら入れる、顧客向けの簡易説明なら省略するなどユーザーに確認すること。

### 2. データ構築 — config.json を組み立てる

ヒアリング結果を `references/data-schema.md` に従って JSON に落とす。スキーマの全体像：

```json
{
  "meta": { "title": "...", "subtitle": "...", "audience": "...", "client": "...", "date": "YYYY-MM-DD" },
  "summary":  { "asisHeadline": "...", "asisDetail": "...", "tobeHeadline": "...", "tobeDetail": "..." },
  "people":   [ { "icon": "users", "title": "...", "num": "5名", "desc": "..." }, ... ],
  "asisOverview": { "tagline": "...", "topNote": "...", "midTitle": "...", "midTools": [...], "extSystems": [...] },
  "tobeOverview": { "tagline": "...", "topNote": "...", "midTitle": "...", "stages": [...], "extSystems": [...] },

  "overview": {                                  // 任意：全体スイムレーン
    "phases": ["①商談", "②契約", "③登録", "④請求", "⑤入金"],
    "asis": { "lanes": [...], "actions": [...], "flows": [...], "docs": [...] },
    "tobe": { "lanes": [...], "actions": [...], "flows": [...], "docs": [...] },
    "position": "before-steps"
  },

  "steps": [
    {
      "num": "01", "title": "①取込",
      "layout": "split",                         // 任意："combined"(default) | "split"
      "asis": {
        "subtitle": "...",                       // 任意：split時のみ表示
        "lanes": [...], "slots": 5,
        "actions": [
          { "lane": 0, "slot": 0,
            "label": "CSVを\n作成する",
            "doc":   "［作成］申込CSV (各社様式)",  // 任意：そのアクションが触るドキュメント
            "fill": "RED", "tag": "..." }
        ],
        "flows": [...],
        "docs": [{"name":"...","where":"..."}]   // 任意：split時に下部凡例
      },
      "tobe": { ... 同じ構造 ... },
      "effect": "..."
    }
  ],
  "structure": { "items": [ { "label": "...", "asisStat": "10+", "asis": "...", "tobeStat": "1", "tobe": "..." } ] },
  "summaryEnd": { "headline": "...", "stats": [...], "closingBanner": "..." }
}
```

詳細は `references/data-schema.md` を必ず読むこと。

**3つの拡張機能（後方互換）**：

- `action.doc` を指定するとそのセル内に「アクション + ドキュメント」が並列表示される。指定なしなら従来通りアクションのみ。
- `step.layout: "split"` を指定するとそのステップは AS-IS / TO-BE を別スライドに分けて生成される。指定なしなら従来通り1スライドに上下表示。
- `overview` を定義すると全工程を俯瞰する AS-IS / TO-BE 2枚を生成する。`position: "before-steps"`（デフォルト）で個別ステップの前、`"after-steps"` で後ろに挿入される。

### 3. pptx 生成 — バンドルスクリプトを実行する

```bash
cd /tmp
mkdir -p business-flow-build && cd business-flow-build
cp -r <skill-path>/scripts/* .
npm init -y >/dev/null 2>&1
npm install pptxgenjs react-icons react react-dom sharp 2>&1 | tail -2
node generate_deck.js <path-to-config.json> <output-pptx-path>
```

スクリプトは config.json を読み込み、自動的に：
- ステップ数に応じてスライドを生成（`step.layout: "split"` のステップは AS-IS / TO-BE で2枚生成）
- `overview` セクションが定義されていれば全体スイムレーン2枚（AS-IS / TO-BE）を `position` で指定された位置に挿入
- 各セルに `doc` が指定されていれば「アクション + ドキュメント」を併記
- `docs` 凡例（split時）を下部の色帯で表示
- スイムレーンのレーン・スロット・アクションを描画
- 矢印の上下左右すべての方向を正しく描画（pptxgenjs の負の w/h 問題を回避）
- 注釈タグを上部レーンでは下に、それ以外では上に配置（タイトルバーへの被りを防ぐ）
- AI Agent レーンのアクションはゴールド系で強調

**ページ番号は自動算出される**：従来の固定式（`6 + steps.length`）ではなく、生成順に積み上げ式でカウントする。`overview`/`split` を使うと総スライド数が変わるが、構造変化・まとめのページ番号は自動で正しく振られる。

### 4. レビュー — 視覚的に確認

- 生成された pptx を LibreOffice で PDF 化 → JPEG 化して、各スライドを目視確認
- レイアウト崩れ、矢印の向き、タグの被りをチェック
- 必要に応じて config.json を調整して再生成

## デザイン原則（変更しないこと）

- **配色**：Midnight Executive（紺 `#1E2761` / アイスブルー `#CADCFC` / ゴールド `#F5B700`）。AS-IS 側は赤系、TO-BE 側は緑系を補色で使う
- **フォント**：見出しは Calibri / Georgia、本文は Calibri。日本語の互換性のため Georgia を本文には使わない
- **スイムレーンの主体軸**：必ず左側に役割を固定する
- **セル文言**：「目的語＋動詞」で統一。名詞だけ（例：「CSV作成」）にしない
- **矢印**：単方向は片矢印、往復は双方向（`bidir: true`）。下から上に行く矢印は `flipV` を使って正しく描画する

詳細は `references/design-spec.md` を参照。

## トリガー例

このスキルは以下のような発話で発動する：

- 「○○社の業務をスイムレーンで描いて」
- 「業務の AS-IS / TO-BE を整理してパワポにしたい」
- 「申込処理の現状と将来像を可視化して」
- 「業務再設計の資料作って」
- 「業務分析やりたい、スライドにまとめて」
- 「現状の業務フローを整理して、改善後の姿も描いて」

提案書（initial-proposal / proposal-estimate）の依頼ではないことを確認する。あちらは営業向けの提案資料で、このスキルは業務側の整理が主目的。
