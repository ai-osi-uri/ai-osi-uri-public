# 技術・アーキテクチャ提案の標準構成と作法

## 位置づけ（営業提案との違い）
営業提案（initial-proposal / proposal-estimate）は「自社サービスを売る」もの。本スキルは
「相手の既存構想（グランドデザイン／ADR）を読み、クラウド上でどう実装するか」を示す
技術・デリバリー提案。価格より、課題→解→効果・スコープ・段階ロードマップ・アーキ・
役割・PoC合格基準が主役。起点は自社紹介でなく「相手資料の読解」。

## 標準スライド構成（順序）
1. 表紙
2. 目次
3. **この取り組みの目的（我々の理解）** ← 目的ファースト
4. 解くべき課題（3つ程度・具体例つき）
5. 採用する解（課題→解→効果のトレーサビリティ）
6. 本提案の位置づけ・目的（我々の役割＝実装検証＋PoC）
7. **vスコープ定義（v1 / v2 / v3 を各1枚）** ＝何を作り・含まない・完了条件・期間
8. **アーキテクチャ（v1 / v2 / v3 を各1枚）** ＝段階で「未導入=グレー／追加=NEW」
9. 役割分担（誰がどこを作るか＋立て付け）
10. トレーサビリティ（解→実装コンポーネント対応）
11. 利用シーン / ユースケース（略語は必ず定義）
12. 進め方・アプローチ（設計ギャップの穴埋め論点）
13. スケジュール（ガント。今回スコープの期間を明示）
14. 体制 / お見積もり / 前提条件
15. Next Step

## 必ず守る作法（過去の指摘から）
- **目的ファースト**：固有名詞（gen2等）から始めない。相手の業務課題→目指す状態→だから本取組、の順。「○○とは？」の無限後退を避ける。
- **「壁」でなく「課題」**等、相手に通じる平易な言葉を使う。社内用語・略語（UC, P1〜P3, v1等）はそのスライド内か直前で必ず定義。
- **箇条書きは独立**：各項目は文脈非依存。「だが」等の接続詞や「〜も」の追加助詞を使わない。
- **課題→解→効果の対応**：解を並べるだけでなく「その解でなぜ課題が解けるか（効果）」を必ず示す（解答性）。
- **段階提案**：v1/v2/v3 をスコープ＋アーキの両面で各1枚に分け、「何が増えるか」を見せる。今回の提案範囲（例：v1・約3ヶ月）を明示し、v2/v3は「別途お見積もり」と書く。
- **役割の立て付け**：「相手社＝AIの設計・検討（ノウハウ保有）／自社＝システム構築（インフラ・データ・連携）」のように、なぜその分担かを言語化。
- **インフラ図はクラウド正準**：AWS流（public/private subnet にサーバを置く）を持ち込まない。GCPなら Cloud Run＝サーバーレス、VPC接続＝Serverless VPC Access、外部送信＝Cloud NAT、エッジ＝Google Front End。公式アイコン調＋担当色を箱背景（薄）で表現。
- **トレーサビリティ**：採用した解が構成図のどのコンポーネントに落ちるかを1枚で対応付ける。
