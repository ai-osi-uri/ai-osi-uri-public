# 伴走セッション・レビュースキル（session-review）

> ⚠️ これは **素案（draft v0）** です。今回の児玉さん伴走セッションの文字起こしから
> 学びを抽象化して作成しました。スコープ・出力フォーマット・保存先は運用に合わせて
> 調整してください。

## このスキルは何か / なぜ必要か

自社は、顧客のAI・Cowork導入を「伴走」で支援している。毎回のセッションは
おおむね **「前回宿題の振り返り → 課題をその場でAIと一緒に解く → 次回宿題を設定」**
というリズムで進む。

ところが、その場のディスカッションは流れていきやすい。後から
**(1) 何を決めたのか、(2) なぜその方針にしたのか、(3) 誰が何をいつまでにやるのか、
(4) 他の顧客にも横展開できる気づきは何か** が辿れないと、せっかくの伴走の価値が
個人の記憶に閉じてしまい、蓄積されない。

このスキルは、伴走セッションの文字起こしを読み、上記を構造化したレビューに変換し、
さらに再利用可能なナレッジ（伴走の進め方のコツ／Coworkの実装上の知見）を抽出して
残すことを目的とする。「次回が前回の続きから始められる」状態と「方法論が会社の
資産になる」状態を同時につくる。

## いつ使うか / 使わないか

- **使う**: 顧客のAI/Cowork導入を支援する伴走・コーチング・オンボーディングの
  セッション振り返り。「今日の伴走どうだった？」「宿題と次回準備をまとめて」など。
- **使わない**:
  - 営業・商談の議事録 → `meeting-minutes`（営業管理表の案件行に紐づく）
  - 新規リードの登録 → `new-lead-registration`
  - 知識を Obsidian に保存したいだけ → `obsidian-knowledge-capture`
  - 一般の社内全体会議・定例 → 対象外

## 入力

- **必須**: 伴走セッションの文字起こし（Plaud 等。話者ラベル付き／なしの両対応）。
  - **取得はまず Plaud MCP から**：コネクタ（`list_files` / `get_transcript` 等）が
    利用可能なら、「今日の○○さんの伴走」等の発話から `list_files`（query / date_from /
    date_to）で録音を特定し、`get_transcript` で全文を直接取得する（貼り付け不要）。
  - MCP が無い／見つからない場合のフォールバック：チャット貼り付け → Gmail 転送メール検索 →
    Drive ファイル指定。詳細は meeting-minutes の
    `references/transcript-parsing.md`（共通・正本）に従う。
- **あると精度が上がる**: クライアント名、セッション日、参加者、前回レビュー
  （あれば読み込んで「進捗差分」を取る）。

話者ラベルが匿名（Speaker 1/2…）でも、文脈から **「コーチ側」と
「クライアント側」** を推定して進めてよい。確定できない固有名詞だけ最大1問確認する。

## ワークフロー

### ステップ0: 前提情報の確認（最大1問）

クライアント名・セッション日が文字起こしから判別できなければ、**1問だけ**確認する。
それ以外（参加者の役割、ワークストリームの切り分け等）は推論で埋め、レビュー末尾の
「前提・要確認」に推定であることを明記する。

### ステップ1: 文字起こしをワークストリーム単位で構造化して読む

会話を、課題の塊（=ワークストリーム）ごとに束ね直す。話題は前後しながら飛ぶので、
時系列ではなくテーマで再構成するのがコツ。

> 例（今回のセッション）: ①LINE自動送信スキル ②Google Driveアップロード（8GB制限）
> ③LINE→スプレッドシート顧客登録フロー

各ワークストリームについて「現状 → 論点 → どう進めることにしたか」を掴む。

### ステップ2: 7項目を抽出する

| # | 項目 | 抽出のポイント |
|---|------|----------------|
| 1 | セッション概要 | 日時・参加者・クライアント・全体テーマ |
| 2 | 前回宿題の進捗 | done / in-progress / blocked を明示。詰まりは原因まで |
| 3 | ワークストリーム別の論点と現状 | テーマごとに「何が問題で、いまどこまで」 |
| 4 | 検討した案と採用方針 | 案A/B/C と **「なぜそれを選んだか」**。選ばなかった理由も残す |
| 5 | 決定事項 | 「決まったこと」と「未決のまま持ち越し」を分ける |
| 6 | 宿題 | **担当 / 期限（＝次回まで）/ 完了条件** をセットで |
| 7 | 次回アジェンダ・準備事項 | 次に着手する論点、事前に必要な準備 |

抽出の細かいコツと出力の型は `references/レビューテンプレート.md` を読む。

### ステップ3: 再利用可能なナレッジを抽出する

そのクライアント固有でない、**他の顧客にも横展開できる気づき**を切り出す。2種類:

1. **伴走メソッドの気づき**（教え方・進め方のコツ）
   → `references/伴走メソッド.md` の型に照らし、当てはまる／新規かを判定。
2. **技術ナレッジ**（Cowork / 各種連携の実装上の知見）
   → `references/技術ナレッジ.md` に既出かを確認。新規なら「追記候補」として提示。

固有名詞の奥にある一般パターンを **1〜2行で言語化**して残すのがこのスキルの肝。

### ステップ4: レビューを Markdown で出力する

`references/レビューテンプレート.md` のフォーマットに沿って生成する。

### ステップ5: 保存する（任意・ユーザー確認の上）

- **Obsidian**: `obsidian-knowledge-capture` を使い、本文は議事録（`30_Projects/.../議事録/`）
  として、抽出した横展開ナレッジは Concept（`20_Concepts/`）として保存する。
- **営業管理表**（任意）: 該当クライアントの案件行があれば、`顧客課題メモ` 列に1行だけ追記してもよい。
  `ledger.py find`(company="{企業名}") で`案件ID` 列を引き、
  `ledger.py update`(case_id="{案件ID3桁}", updates={"メモ": "{既存メモ} / {YYYY-MM-DD} 伴走セッション実施（宿題N件）"})
  のように**既存メモへの追記**として更新する（上書きしない）。`ステータス` 列は伴走では動かさない。
  行が見つからない／複数ヒットする場合はスキップし、報告で申し送る。
- 保存後は **透明性レポート**（レビュー何件・新規Concept何件・宿題何件）を返す。

## レビュー品質の原則

- **「決定」と「未決」を曖昧にしない。** 持ち越しは持ち越しとはっきり書く。
- **案比較は結論だけでなく「なぜ」を残す。** 次回同じ議論を最初からやり直さないため。
  「楽だから」「運用負荷が低いから」「コストがかからないから」等の判断軸まで書く。
- **宿題は必ず owner と「次回までに何ができていればOKか」をセットで。**
- **抽象化を恐れない。** 個別の作業ログではなく、再利用できる型として残す。

## 参照ファイル

- `references/レビューテンプレート.md` — 出力フォーマットと記入例
- `references/伴走メソッド.md` — 横展開できる「伴走の進め方」の型（今回の学びを抽象化）
- `references/技術ナレッジ.md` — Cowork/連携の実装ナレッジ（今回の学びを抽象化）
