# PR TIMES 記事作成スキル

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

自社の協業実績を、PR TIMESに掲載するプレスリリース記事として作成する。

## 記事の方針（最重要）

この記事は「実際にやったことを、事実ベースで淡々と伝える」プレスリリースである。

記事で伝えるべきこと:

1. 協業先がどんな課題を抱えていたか（事実として簡潔に）
2. 自社が具体的に何をやったか（実際の活動内容を列挙）
3. それによってどう変わったか（成果や効果があれば）

以下のような抽象的・大げさな表現は使わない:
- 「全社員がAIで自分自身を毎日アップデートし続ける組織への転換」
- 「組織の在り方そのものを変える」
- 「AI導入プロジェクト」「DX推進」のような従来型バズワード

記事の主役は「実際にやった具体的な活動」であり、「組織変革のストーリー」ではない。

## 前提：案件マスタは営業管理表

案件情報の正本は **`{{ledgers.sales}}`**（タブ `取引先管理`、ヘッダは5行目）。
**ディレクトリ経由（openpyxl）で読み書きする。Google Sheets API・GCPサービスアカウントは使わない。**
台帳の触り方・不変条件・列の一覧は
**`../new-lead-registration/references/ledger-access.md` を必ず読むこと**（osi-sales 共通の正本）。

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L columns                       # 列名・ステータス値・パス
python3 $L find --company "{企業名}"      # 表記ゆれを吸収して行を引く
python3 $L find --case-id {案件ID3桁}
```
シートID・タブ名などの組織固有値は `config/osi-sales-settings.md` を参照してください。

- ヘッダは5行目、データは6行目以降
- 主な列: A=取引先 / B=URL / C=メモ（顧客課題・アクション）/ D=主担当 / W=ステータス / X=想定額 /
  Y=獲得日 / **Z=案件ID** / AA=最終接触日 / AB=最終議事録日
- ステータス値は `リード` / `商談中` / `金額提示済み` / `契約済み` / `デリバリー中` / `失注` の6つだけ。
  `KPIダッシュボード` タブが集計しているので**値を勝手に増やさない**
- 列は**ヘッダ行の文字列**で指定する（列レターは使わない）。実際の列名は
  `ledger.py columns` の戻り値 `columns` で確認できる（存在しない列を指定するとエラーで止まる）

## 記事作成の前提条件

記事は契約締結済みの案件のみ作成すること。
営業管理表で該当行を引き、**`ステータス` 列が `デリバリー中` または `契約済み`** の案件だけを対象とする。

```
python3 $L find --company "{企業名}"    # 表記ゆれ（株式会社・促音・記号）は吸収される
python3 $L find --case-id 098           # 案件IDが分かっているならこちらが確実
```

- 候補が1件 → そのまま採用（戻り値の `row` / `案件ID` を保持）
- 候補が複数 → `AskUserQuestion` でユーザに選ばせる（1社で複数案件が走ることがあるため）
- 候補が0件 → 「営業管理表に該当案件がありません」と案内して終了

行の詳細（C列のメモ、Z列の案件ID 等）は `ledger.py read` で取得する。

> **判定条件が変わった点に注意。** 旧運用では案件マスタの「契約書締結ステータス＝締結済み」かつ
> 「商談ステータス＝99.完了」を条件にしていたが、営業管理表には**契約書締結ステータスの列が無い**。
> そのため本スキルは `ステータス` 列のみで判定する。ステータスが `契約済み` でも契約書の締結が
> 済んでいないケースが理論上ありうるため、Step 2 のヒアリングで**開示範囲とあわせて契約締結の
> 事実をユーザーに確認する**こと。

ステータスが `リード` / `商談中` / `金額提示済み` / `失注` の案件について記事を書くと、
実態のない嘘の記事になってしまうため、絶対に避ける。

## ワークフロー

### Step 1: プロジェクト資料の読み込み（必須）

記事の内容は実際にやったことに基づかなければならない。
プロジェクトフォルダを必ず読み、そこから得た情報をベースに記事を構成すること。フォルダを読まずに一般論で記事を書くことは禁止する。

#### プロジェクトフォルダの場所

```
{{paths.root}}/{{paths.projects}}/{{paths.project_naming}}/
```

案件ID は営業管理表の Z列から取得する（例: 案件ID=098, 企業名=土佐病院 → `098.土佐病院`）。
**案件IDが分かればフォルダは一意に決まる**ため、フォルダ URL を台帳に書き戻して二重管理することはしない。

> 一部の案件フォルダは `01_契約書`〜`07_議事録` という別テンプレートで作られている。
> 既存フォルダの構造に合わせて読むこと。

このフォルダ内のすべてのファイルをスキャンする。ファイルが多い場合はGlobツールでファイル一覧を取得し、重要度の高い順に読む。

#### ファイルの優先度と読み方

| 優先度 | ファイル種別 | 読み取り方法 | 把握すべき情報 |
|-------|------------|------------|-------------|
| 1 | 定例資料 (.pptx) | python-pptx | 実際に何をやったか、進捗、課題、成果物 |
| 2 | 提案書 (.pptx) | python-pptx | 提案したスコープ、技術構成、料金体系 |
| 3 | 契約書 (.docx) | python-docx | 契約形態、業務範囲、契約期間 |
| 4 | 議事録・メモ (.md, .txt) | Read | 議論内容、方針決定の経緯 |
| 5 | その他 (.xlsx, .pdf) | 必要に応じて | 補足データ |

python-pptxやpython-docxでテキストを抽出する。マウントフォルダから直接読めない場合は `cat > /tmp/` 経由でコピーしてから処理する。

#### このステップで把握すべき情報

- 協業先の課題: なぜ自社に依頼したのか（資料から読み取れる背景・課題）
- 実際にやったこと: 何を作ったか、何を支援したか（具体的な成果物・システム・施策）
- 定例で議論した内容: どんなテーマでAI活用を検討したか
- 契約形態（CAIO契約、開発契約等）
- プロジェクト期間

ここで読み取った情報はあくまで「仮説」として扱う。次のStep 2（ヒアリング）で必ずユーザーに確認してから記事に反映すること。

### Step 2: ユーザーへのヒアリング（必須・最重要ステップ）

Step 1で読み取った情報をもとに仮説を立て、AskUserQuestionツールでユーザーに確認する。
フォルダにファイルがあっても実際にはやっていない活動が含まれている場合がある。記事に嘘を書かないために、このステップは絶対に省略しない。

#### 確認事項1: 課題感

プロジェクト資料から読み取った課題仮説を提示し、実際の課題感を確認する。

```
例: 「サンプル様の課題は『集客に困っていた』という認識で合っていますか？他にあれば教えてください。」
```

#### 確認事項2: 実際にやったこと

フォルダ内のファイル名やスライド内容から推測した活動リストを選択肢として提示し、ユーザーに確認してもらう。
やっていないものが含まれている可能性があるため、必ず「該当しないものがあれば外してください」「追加があれば教えてください」と伝える。

```
例:
フォルダから以下の活動が推測されました。実際にやったものを教えてください:
□ Instagramターゲットリスト作成
□ チラシ・イベント企画
□ バズリール分析
□ その他（自由記述）
```

#### 確認事項3: 開示範囲

記事で触れてよい情報の範囲（契約の存在、具体的な金額、技術詳細 等）を確認する。
秘密保持条項がある契約が見つかった場合は、協業先の掲載許諾が取れているかも確認する。

あわせて、**契約書の締結が実際に完了しているか**をここで確認する。営業管理表には契約書締結
ステータスの列が無く、W列だけでは締結の完了までは保証できないため、この確認を省略しない。
未締結だった場合は記事作成を中止する。

ヒアリングで確認した内容だけを記事に書くこと。フォルダにファイルがあっても、ユーザーが「やっていない」と言ったものは記事に含めない。

### Step 3: Webリサーチ（精緻な企業情報の取得）

プレスリリースには正確な企業情報が不可欠。WebSearchとWebFetchを使い、協業先企業の情報を精緻に調査する。

#### 必ず調べること（会社概要セクション・リード文に使用）

以下の情報を企業の公式サイト（会社概要ページ、IRページ等）から取得する。推測ではなく、公式サイトに記載された正確な情報を使うこと。

| 項目 | 調べ方 | 使用箇所 |
|-----|-------|---------|
| 正式社名 | 公式サイトの会社概要 | タイトル、リード文、会社概要 |
| 代表者名（フルネーム＋肩書き） | 公式サイトの会社概要 | リード文、会社概要 |
| 本社所在地 | 公式サイトの会社概要 | 会社概要 |
| 設立年 | 公式サイトの会社概要 | 会社概要 |
| 事業内容（公式な表現） | 公式サイトのトップページ / 事業紹介 | 会社概要、協業の背景セクション |
| 主力サービス・プロダクト名 | 公式サイト | サービス紹介セクション |
| 企業URL | 公式サイト | 会社概要 |

#### Webリサーチの手順

1. まず `{企業名} 会社概要` でWebSearchし、公式サイトのURLを特定
2. WebFetchで公式サイトの会社概要ページを読み込み、正式な企業情報を取得
3. 必要に応じて `{企業名} プレスリリース` 等で追加検索
4. プロジェクト資料の情報とWebの情報を突合し、食い違いがあればユーザーに確認

情報が見つからない場合: 公式サイトに記載がない項目はプレースホルダー `（※要確認）` とし、推測で書かない。

#### 記事構成テンプレート

```markdown

← 60〜80文字程度

← {{company.name}}の正式情報 + 協業先の正式情報
```

#### 執筆スタイルルール（厳守）

AI（LLM）が書いた文章には特有のクセがある。以下のパターンは読み手に「AIが書いた文章だな」と一発でバレるので、絶対に使わないこと。人間が書いた普通のプレスリリースのように、事実を淡々と伝える文体で書く。

**禁止パターン1: ダッシュ演出**
「――」（全角ダッシュ2つ）を文中の演出として使わない。

- NG: `「何をすればいいかはわかっている。でも手が回らない」――これがサンプルの課題でした。`
- OK: `やるべき施策は見えていたものの、日々の指導業務と並行して手を回す余裕がない状態でした。`

**禁止パターン2: 本文中の太字**
見出し以外で `**太字**` を使わない。太字は見出しだけに限定する。

- NG: `**集客**に苦戦していました。`
- OK: `集客に苦戦していました。`

**禁止パターン3: 独白調・問いかけ調**
記事中に「」付きの独白やレトリカルな問いかけを入れない。代表コメント欄のプレースホルダーを除き、本文中に台詞調の文は書かない。

- NG: `「施術の品質には自信がある。でも、集客の仕組みが弱い」`
- NG: `なぜ全員がAIを使う組織を目指すのか？`
- OK: `施術品質には定評がある一方、集客面に課題を抱えていました。`

**禁止パターン4: 短文ドラマ（溜め→ドン）**
短い文を畳みかけてドラマチックに見せる書き方をしない。

- NG: `まず作る。見せる。そこから始まる。`
- NG: `考える前に作る。見せてから売る。`（キャッチコピーとしての引用は可。本文の地の文で多用しない。）
- OK: `まず動くものを作って見せ、そこからフィードバックを回すサイクルで進めています。`

**禁止パターン5: 大げさな締め**
記事末尾を壮大なビジョンで締めない。

- NG: `{{company.name_display}}は、すべての企業が「AIで企業価値を高め続ける組織」になることを目指します。`
- OK: `{{company.name_display}}は引き続き、○○の事業成長に伴走してまいります。`

**禁止パターン6: 抽象的な組織変革フレーズ**

- NG: `組織の在り方そのものを変える` `全員がAIで自分をアップデート` `AIが文化になる` `未来から逆算する経営`
- OK: 具体的に何をしたかだけを書く

**禁止パターン7: 見出しの過剰演出**
見出しにサブタイトルを付ける場合は事実の要約にとどめ、ポエムにしない。

- NG: `## 協業の背景 ― ホットペッパー依存からの脱却と自社集客力の強化`
- OK: `## 協業の背景`

**守るべき文体:**

- 「です・ます」調で統一
- プレスリリースとして客観的かつ淡々としたトーン
- 一文は40〜60文字程度。長すぎず短すぎず
- 修飾語は最小限。事実だけで文を構成する
- セクション間のつなぎに余計な前置きを入れない

**重複の排除:**
- サービスの説明 → 「CAIOサービスについて」セクションに集約
- 活動の具体例 → 「実施していること」セクションに集約
- 末尾のサービス紹介 → 2〜3行の要約のみ（本文の繰り返しにしない）
- 同じフレーズが3回以上出ていたら減らす

**プレースホルダーの明示:**
確定していない情報はプレースホルダーとして残し、ユーザーに埋めてもらう。
- 両社代表のコメント → `（※○○様よりコメントをいただき掲載）`
- 未確定の数値 → `（※要確認）`

### Step 5: 営業管理表の `顧客課題メモ` 列に記録を追記

営業管理表には「記事作成ステータス」の列が無いため、**`顧客課題メモ` 列に1行追記する**形で記録を残す。

`ledger.py update`(case_id="{案件ID3桁}") で更新する。書式：

```
PR TIMES記事: 作成済み({YYYY-MM-DD})
```

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L update --case-id 098 --append-memo "PR TIMES記事: 作成済み(2026-07-21)"
```

- **既存メモは消さない。** `--append-memo` は末尾への追記なので、自分で連結しない
- 更新は必ず**案件ID（`--case-id`）で行を特定**する（同名・複数案件で誤爆しないため）
- **`ステータス` 列は変更しない。** 記事作成は商談フェーズを進める行為ではない

### Step 6: 推敲

執筆した記事を通読し、以下を確認する。

```
チェックリスト:
□ タイトルが60〜80文字程度で、何をしたかが分かるか
□ リード文だけで協業の概要が分かるか
□ 協業先の正式社名・代表者名・所在地がWebリサーチで取得した正確な情報と一致しているか
□ 「実施していること」の内容がヒアリングで確認した活動に基づいているか（仮説のまま書いていないか）
□ 各セクション間で内容の重複がないか
□ 同じフレーズが3回以上繰り返されていないか
□ 会社概要が osi-profile.md（company.*）と一致しているか
□ プレースホルダーが明示されているか
□ 記事全体が1500〜2500文字程度に収まっているか
□ 【スタイル】ダッシュ演出（――）が使われていないか
□ 【スタイル】本文中に不要な太字（**）がないか
□ 【スタイル】独白調・問いかけ調の文がないか
□ 【スタイル】短文を畳みかけるドラマチックな表現がないか
□ 【スタイル】大げさな締め・抽象的な組織変革フレーズがないか
□ 【スタイル】見出しが過剰に演出されていないか
```

### Step 7: 出力

完成した記事を Markdown ファイル (.md) としてワークスペースフォルダに保存する。
ファイル名は `{案件ID3桁}_PR_TIMES記事_{企業名}.md` とする（案件IDは営業管理表の Z列から取得）。

例: `098_PR_TIMES記事_サンプル株式会社.md`

保存先: `{{paths.root}}/{{paths.pr_articles}}/`

### Step 8: Slack 通知（slack-notify が利用可能な場合）

記事ドラフト完成を `#marketing` に通知する。`slack-notify` をサブスキル
として呼び出す：

```
slack-notify(
  event_type="pr_article_drafted",
  payload={
    "company": "{協業先正式社名}",
    "id": "{案件ID3桁}",
    "article_url": "{Markdownファイルの Drive または computer:// URL}",
    "article_path": "{{paths.root}}/{{paths.pr_articles}}/{ファイル名}",
    "char_count": "{文字数}",
    "status": "ドラフト完成・代表者コメント待ち"
  }
)
```

slack-notify が未整備、または Slack MCP に投稿系ツールが無い場合は
スキップし、ユーザーへの完了報告のみ行う。
