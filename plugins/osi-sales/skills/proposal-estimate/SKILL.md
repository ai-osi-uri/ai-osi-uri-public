# 提案見積もり作成スキル（atomic）

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

関係構築済みの見込み客や、初回提案後の2回目以降に使う **pptx 単発生成スキル**。初回提案との違いは、**具体的なサービス内容・価格・実行スケジュール**が入ること。相手は「何を・いくらで・いつまでにやってくれるのか」を知りたい段階にいる。

工程は2つ。**先に考える（骨子ゲート）→ あとで描く（pptx生成）。** 骨子の承認が取れるまで pptx は作らない。本スキルの責任範囲は pptx を1ファイル作るところまで（Drive 格納・営業管理表への反映は `proposal-package` 側）。

## いつ使うか

具体的な金額（「初期30万」「月額30万」）／具体的サービス名（CAIO契約・カスタム開発）／スケジュール（「6ヶ月で」「ガント」）／既に面識あり、のいずれかが出ているとき。初回アプローチなら proposal-package の初回ルート（storyline-gate→deck-composition→pptx-custom の3層）。

---

## Step 0: 骨子ゲート（storyline-gate）— ここが本体

**いきなりスライド構成・価格表・ガントに行かない。** まず `storyline-gate` を呼び、この見積提案の骨子を1枚（`storyline.md`）にして承認を取る。見積提案では5要素を次のように埋める：

- **① 決裁の構造** — この金額を承認するのは誰か。いま予算観・他社比較・社内政治はどうか。Yesに要る確信は何か。
- **② コアメッセージ** — 「このスコープを、この価格で、この期間でやり切ると、御社に○○が起きる」を一文で。価格は手段、変化が主語。
- **③ 論理の骨子** — 現状 → 提案スコープ → 進め方 → 期間 → 価格の妥当性 → 次の一歩、を最小の段で。各段は言い切り。
- **④ 証拠設計** — 見積提案の証拠は「価格の内訳・根拠」「ガント・週次定例（毎週何が進むか）」「実物（サンプル・モック）」。コア主張ほど証拠を厚く。
- **⑤ 落とし穴** — 「高い」「内製でできるのでは」「前のベンダーで失敗」「既存ツールと重複」など、この相手固有の price objection を先回りで受ける段を決める。

### 壁打ちは骨子ゲートの中で

価格・期間・強調点のすり合わせ（旧 Step1 の壁打ち）は storyline-gate の5要素ヒアリングに統合する。コツ：

- ユーザーの言葉をそのまま受けず「つまりこういうことですか」と整理して返す
- 曖昧なら「例えばこの形は？」と具体案を出して握る
- 価格の根拠が薄ければ「この設定の意図は？」（割引理由・バンドル割引）を確認する
- 業界特有の規制・制約（薬機法・個情法 等）を確認する

握れたら `storyline.md` を確定。**ここで初めて Step 1 へ。** 枚数・色・レイアウトは骨子段階で決めない。

---

## Step 1: 骨子を「見積・スケジュール」という証拠に翻訳

承認済み骨子の各段を、相手が判断できる具体（価格・期間・進め方）に落とす。ここが見積提案の描く判断の核。

### サービス構成・価格・スケジュールの設計

骨子の③④をもとに提案の骨格を組む。自社でよく使うサービス構成パターン・CAIO の3フェーズモデル・価格帯は `references/service-catalog.md` を参照（「従う型」ではなく、骨子に合わせて選ぶ既存解）。

### ガント／週次ロードマップ

期間が含まれるなら必ず時間軸を見せる。設計の要点だけ本体に：

- 契約全体が長期（例6ヶ月）でも、**最初の約2ヶ月（8週）を1週間単位で詳細化**すると「毎週何が進むか」が具体になり契約判断が前に進む。「全体は月単位の3フェーズ、立ち上げだけ週単位」の二段構えにし、注記で長期契約と矛盾させない。
- 週次定例は「毎週何をしてくれるの？」への回答。相手が一番気にする点。

ガントの実装テクニック（バーの座標計算・クランプ・グリッド・SVG→PNG）は `references/gantt-and-figures.md`。

### 料金スライドの設計（＝伝え方なので本体に残す）

料金スライドは提案で最も注目される。設計思想：

- **数字は大きく明確に**。曖昧にしない。
- **内訳を示す**。何にいくらかを分解。
- **割引の理由を明記**（「○○につき○○万→○○万」）。
- **月額と初期を分離**。ランニングとイニシャルを区別。
- **税別/税込を明記**。

> 例：CAIO契約 20万円/月（6ヶ月契約）／初期費用 0円（オンボーディング含む）

---

## Step 2: 構成する（deck-composition）

骨子と価格・スケジュールの素材が揃ったら、**`deck-composition` スキルを呼んで slide-plan.md（スライド順・各 Action title・1メッセージ・載せる証拠）を作る。** 枚数・順序は骨子から導く。よく使う構成例（表紙／企業理解／課題／提案①〜／CAIO詳細／ロードマップ／週次定例／料金／Next Step）は `references/service-catalog.md` にあるが、**骨子に無い段は作らない・足りない段は足す**。サービス既知の相手には「{{company.name_display}}とは」を省く等、骨子に従って増減する。料金スライドは声出しQAで「いくらで・何が得られるか」が流れることを確認する。

## Step 3: 刷る（pptx / pptx-custom）

slide-plan.md ができたら、**`pptx`（または社内体裁の `pptx-custom`）スキルの SKILL.md を先に読み、その指示に従って描画する。** 本スキルはレイアウト・配色・図形の細部を自前で抱えない。ブランド配色・フォント・サンドイッチ構造・3フェーズの色は `references/brand-design.md`、ガント実装は `references/gantt-and-figures.md`。

---

## Step 4: QA と出力

`pptx` スキルの QA 手順に従い：

1. `markitdown` で内容QA（テキスト抜け・順序・**価格の正確性**）
2. LibreOffice → PDF → 画像化 → サブエージェントでビジュアルQA
3. **料金スライドの数字をダブルチェック**（最重要）
4. ガントのバーが描画領域をはみ出していないか
5. 修正 → 再検証 → 最終 pptx を出力（Drive／営業管理表は proposal-package が担当）

### ユーザーに提示する前の必須ゲート

**`proposal-self-review` の F（機械チェック）を 0 件にするまで提示しない。**

| # | 何を見るか |
|---|---|
| F1 | 金額の**単位漏れ**（「億」「万」で終わっていないか）。`円円` も 0 件 |
| F2 | NG表現（社内ジャーゴン・相手の弱みの断定） |
| F3 | **全章に中扉**があるか（章の数＝扉の枚数） |
| F4 | 目次のページ番号が**最終ビルド後の実測値**か |
| F5 | 隣接2枚で同じ表・同じ指標を繰り返していないか |
| F6 | **全ページを画像化して目で見た**か（省略禁止） |
| F7 | 合計＝内訳の和／同じ数字が前後で食い違っていないか |

加えて A2（メッセージは言い切り／主語は顧客／抽象は Appendix）と A3（数字は一次情報）を通す。
実装コードは `pptx-custom` の「日本語ビジネス文書の絶対ルール」にある。

## このスキルの責任範囲（線引き）

- **考える（骨子・壁打ち）** は storyline-gate に委譲。
- **見積判断（スコープ・価格・期間・何を強調するか）** が本スキルの核。
- **構成（スライド順・Action title）** は deck-composition に委譲。
- **刷る（レイアウト・配色・ガント実装）** は pptx / pptx-custom と references に委譲。
- **Drive 格納・営業管理表への反映・チャット通知はしない**（proposal-package の責任）。

---

## やってはいけないこと

- **骨子の承認前にスライド構成・価格表・ガントを作り始める** — まず storyline-gate。
- **骨子より先に「14枚で」「3フェーズで」と型を決める** — 構成は骨子から導く。
- 料金スライドの数字を曖昧に／検算せずに出す — 最重要のQA。
- 借り物・架空の数値で価格根拠を支える — 根拠は正直に。
