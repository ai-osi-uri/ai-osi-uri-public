# 試作案の書式（現場で起きていそうなこと → 試作案 → 効き目）

first-proposal-lens の「試作案は実現策まで書く」で使う書式。**書式は制約、文例は観測**（条件つき・上書き自由）。

## 1. サイト走査で「現場で起きていそうなこと」を推測する

**推測は「サイトのどこからそう考えたか」と対で書く。** 根拠の無い推測は、相手に「分かっていない」と見抜かれる。

| 見る場所 | 何が読めるか | 推測の型 |
|---|---|---|
| 申込み・会員登録・購入の導線 | IDやフォームが複数ある／同じ情報を2度入れる | 「システムが分かれている → 横断で把握しづらい」 |
| お知らせ・ニュース・更新頻度の高いページ | 更新量と粒度 | 「更新に人手がかかる → 速報性や個別対応に手が回らない」 |
| 採用ページ | 求めている人＝足りない人 | 「◯◯担当が不足 → その業務が属人化」 |
| 問い合わせ・FAQ | 繰り返し聞かれていること | 「一次対応が人に集中」 |
| 料金・プラン・キャンペーン | 一律か個別か | 「全員に同じ施策 → 個人単位の働きかけをしていない」 |

→ 自問：この推測は、相手が「そうそう」と言うか「違う」と言うかのどちらかになるか。どちらにもならない一般論（「DXが遅れている」）は落とす。

## 2. 1件の書式（3段 ＋ 実現策）

```
NN  {試作案の名前（動詞で終える：〜を一本化する／〜を自動化する）}

現場で起きていそうなこと（推測）
  {サイトの◯◯に△△とある}ことから、{現場では□□が起きている}と推測されます。

試作案
  {入力データ}を取り込み、AIが{何を出すか}する{道具の種類：画面／ツール／配信}を試作します。
  {誰（部署・役割）}がそのまま使える形にします。

効き目
  {何が増える／減る}。{測れる指標}で確かめます。

実現策（描画前に必ず埋める）
  1日の流れ：{時刻} {AI／担当者} {やること} を3〜5行。担当者の行には所要時間
  AIが出すものの例：{実際に画面やメールに出る文面を1つ、固有名詞入りで}
  測り方：{配信あり／なしの差分 など、比較の形で}
  最初の目標：{最初の検証期間で到達したい数字と、届かなければ止める条件}
```

**制約**
- **「現場で起きていそうなこと」には（推測）と明記し、確認の場（ワークショップ等）を資料内に書く。** 断定すると評価に見える。
- **試作案には「誰が使うか」を必ず書く。** 使い手が無い道具は作れない。
- **効き目は「〜が期待できます」で終えない。** 何で測るかまで書く。
- **1件あたり、実現策の4項目が埋まらないものは骨子に入れない**（埋まらない＝相手の業務を知らない。件数を減らす方が良い）。

## 3. 件数と粒度の判断

- 要望を聞けていない初回：**3〜5件を並べ、相手に選ばせる**（1件に絞ると外したとき代替が無い）
- 要望を聞けている／課題が特定されている：1〜2件に絞り、実現策を厚くする
- 規制業界・保守的な相手：件数は同じでも、「効き目」の前に「守れること（守秘・責任分界）」を1行足す

## 4. 描画への引き渡し

- 一覧（3列カード：現場で起きていそうなこと／試作案／効き目）を1枚、続けて1件1枚の実現策スライド（左：現場・試作案、右：1日の流れ、下：例文・測り方・目標）。pptx-custom の型D／型E。
- 画面モックは試作案のうち1〜2件だけ（証拠レベル2）。

> 観測（2026-09 / プロ野球球団・要望未聴取の初回・オンライン60分）：3件（ID一本化／来場が途切れそうなファンの呼び戻し／試合データ発信の自動化）＋実現策3枚＋モック2枚で、本編24枚。件数を増やすより、1件ごとの「AIが出すものの例文」を固有名詞入りにした方が具体に見えた。
