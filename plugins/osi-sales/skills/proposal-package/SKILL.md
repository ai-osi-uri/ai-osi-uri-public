# 提案パッケージ生成スキル（proposal-package）— オーケストレータ

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

自社の営業ワークフローにおいて、リードに対する**提案準備の窓口**となる単一スキルです。「初回提案」「見積もり付き詳細提案」のどちらが必要かをフェーズ判定で振り分け、必要な atomic スキル（`new-lead-registration` / 初回3層（storyline-gate→deck-composition→pptx-custom）/ `proposal-estimate`）を順に呼び出して、台帳への起票 → 提案書生成 → Drive 格納 → 営業管理表への反映 → Slack 通知までを一気通貫で実行します。

## 前提：案件マスタは営業管理表

案件情報の正本は **`{{ledgers.sales}}`**（タブ `取引先管理`、ヘッダは5行目）。
**ディレクトリ経由（openpyxl）で読み書きする。Google Sheets API・GCPサービスアカウントは使わない。**
台帳の触り方・不変条件・列の一覧は
**`../new-lead-registration/references/ledger-access.md` を必ず読むこと**（osi-sales 共通の正本）。

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L columns                       # 列名・ステータス値・パス
python3 $L find --company "{企業名}"      # 表記ゆれを吸収して行を引く
python3 $L find --case-id {案件ID3桁}
```組織固有値は
`config/osi-sales-settings.md` を参照してください。

- ヘッダは5行目、データは6行目以降
- 主な列: A=取引先 / B=URL / C=メモ（顧客課題・アクション）/ D=主担当 / W=ステータス / X=想定額 /
  Y=獲得日 / **Z=案件ID** / AA=最終接触日 / AB=最終議事録日
- **セクション見出しは無い**（1案件1行・行は動かさない）。旧gsheetにあった次の区分は、いまはステータス列が表す:
  `既存取引先（契約済み・稼働中）` / `新規契約済み（受注確定・請求未開始）` /
  `案件化（提案中・商談）` / `リード（未提案・新規アプローチ）` / `失注（参考）`
- ステータス値は `リード` / `商談中` / `金額提示済み` / `契約済み` / `デリバリー中` / `失注` の6つだけ。
  `KPIダッシュボード` タブが集計しているので**値を勝手に増やさない**
- 列は**ヘッダ行の文字列**で指定する（列レターは使わない）。実際の列名は
  `ledger.py columns` の戻り値 `columns` で確認できる（存在しない列を指定するとエラーで止まる）
- 月別売上（E〜P）と売上合計（Q）は数式列なので書き込まない

**案件フォルダの URL は台帳に持たない。** 案件IDが決まればフォルダは
案件ID から**引ける**ため、URL を書き戻して二重管理しないこと（事業区分・サブフォルダ名は案件により異なるので、実体は `find` で確認する。ステップ5参照）。
（`URL` 列は顧客の企業サイト用です。）

## なぜこのスキルが必要か

AS-IS では、リード起票（new-lead-registration）の後に主担当が手で：

1. 初回フェーズか見積もりフェーズかを判断する
2. 初回3層（storyline-gate→deck-composition→pptx-custom）または `proposal-estimate` で提案書 pptx を作る
3. Drive の案件フォルダ配下の提案フォルダを開く（無ければ作る）
4. pptx をアップロード
5. 営業管理表のステータスを進める
6. 最終接触日・メモ（アクション）を更新する

をやっている。これが「燃える」ポイントの1つ。`proposal-package` はこの 1〜6 を 1 コマンドにまとめます。

## 設計原則 — オーケストレータとしての責任範囲

このスキルは「振り分けと統合」だけを担当します。

| 責務 | 担当スキル |
|---|---|
| リード起票・フォルダ作成 | `new-lead-registration` |
| **骨子設計（全案件の最初の関門）** | **`storyline-gate`（osi-docs）** |
| **初回アプローチの構成→描画** | **`deck-composition` → `pptx-custom`（osi-docs）。文脈に `first-proposal-lens.md`** |
| 見積もり・スケジュール入り pptx | `proposal-estimate`（内部で3層を実行） |
| **フェーズ判定・呼び分け・Drive 格納・営業管理表の更新・Slack 通知** | **`proposal-package`（本スキル）** |

つまり「pptx を作るロジック」「リードを起票するロジック」自体は本スキルに書かない。本スキルが太るとサブスキルとの責務が曖昧になるので、ロジックの加筆は必ず該当 atomic スキル側に行うこと。

## ワークフロー

### ステップ0: 内部の一次情報を先に読む（最優先・省略禁止）

**外部情報を調べ始める前に、社内にすでにある情報を全部読む。**

顧客について**最も一次的な情報は、決算公告でも業界レポートでもなく、自分たちが聞いた話**である。ここを飛ばして公開情報から組み立てると、**題材そのものを外した提案書**ができる。

必ず読むもの（存在するものは全部）：

| 場所 | 何が書いてあるか |
|---|---|
| `{{paths.projects}}/{{paths.project_naming}}/` **配下を再帰で一覧** | 既存の提案書・モック・調査・受領資料 |
| `{案件ID}_案件メモ_{企業名}.gdoc` | **想定テーマ・初回ヒアリング内容・技術所見**。ここに提案の題材が書かれている |
| `01_提案・見積/` の既存ファイル | すでに出した提案・**動くモック**（あれば、それが次回の主役） |
| `05_受領資料/` | 先方からもらった資料 |
| 営業管理表の メモ列・獲得チャネル・最終議事録日 | 経緯 |
| 議事録（`meeting-minutes` の出力） | 商談で何を話したか |

`.gdoc` / `.gsheet` はポインタファイルなので中身が空に見える。**Drive コネクタの `read_file_content` に `doc_id` を渡して本文を読む**こと（ファイルをただ `ls` しただけで「無い」と判断しない）。

**チェック：この案件の「想定テーマ」を1行で言えるか。** 言えないまま外部調査を始めない。

> 実例：三井物産流通グループの案件で、案件メモに「製品在庫管理システムの新規開発（ATP＝将来入庫予定を含む引当が最重要）」と書かれ、動くモックまで置かれていたにもかかわらず、公開情報だけで「AI伴走」の提案書を作ってしまい全面的に作り直しになった。**フォルダを開いていれば防げた。**

### ステップ0.5: 「何を作るべきか」を1行で決める（initial / estimate の判定より前）

**ステップ0 で読んだ内容から、作るべき成果物を1行で言えるまで、次に進まない。**

本スキルのフェーズ判定（ステップ1.5）は `initial` か `estimate` の2択だが、
**実際の案件は、そのどちらでもないことがある。** ステップ0 を読んだ結果、次のいずれかなら判定表に入れない：

| ステップ0 で見えた状態 | 作るべきもの |
|---|---|
| **すでに納品・進行中**（04_請求 に成果物がある） | 初回提案書ではなく、**完成に向けた確認と、この先の使い方** |
| **議事録やメモに「次に出す」と書かれた宿題がある** | まずその宿題。**約束した資料が未着手のまま新しい提案を作らない** |
| **契約の外で事が動いている**（再販・第三者提供など） | 既存契約の延長ではなく、**その事象を受け止める別枠の提案** |
| 既存提案・動くモックがある | それを主役にした次フェーズ。ゼロから作り直さない |
| 上記に当てはまらない | ステップ1.5 の判定表へ |

→ 自問：**この資料を、相手はいま受け取って嬉しいか。** 相手の現在地とズレた種類の資料は、
どれだけ体裁が良くても差し戻しになる。

> 実例（2026-09）：納品済みの映像制作案件に初回提案書を作ろうとして、フォルダを開いて気づき、
> 「完成に向けた確認」に切り替えた。別の案件では、面談メモに「条件のたたき台を今週中に出す」と
> 書かれた宿題が未着手のまま残っていた。**どちらもステップ0 を読まなければ題材ごと外していた。**

### ステップ1: 入力からリードを特定する

ユーザーの発話から、対象リードを特定する手がかりを抽出してください：

- **案件ID**（例：「案件ID 122」「122番」）
- **企業名**（例：「サンプル」「サンプル社」「株式会社サンプル」）

営業管理表を検索して該当行を特定します。

```
python3 $L find --company "{企業名}"    # 表記ゆれ（株式会社・促音・記号）は吸収される
python3 $L find --case-id 122           # 案件IDが分かっているならこちらが確実
```

- 候補が1件 → そのまま採用（戻り値の `row` / `案件ID` を保持）
- 候補が複数 → `AskUserQuestion` でユーザに選ばせる（1社で複数案件が走ることがあるため）
- 候補が0件 → **その場で登録に進む**（次節「ステップ1-B」へ）

### ステップ1-B: リードが未登録だった場合の自動補完

ユーザーには中断させず、対話だけで登録 → 提案準備まで一気通貫で進めます。

1. `AskUserQuestion` で確認：
   ```
   「{企業名} は営業管理表にまだ登録されていません。今この場で登録してから、提案パッケージを作成しますか？」
   選択肢:
   - はい、登録してから提案準備に進む（推奨）
   - 一旦中断、登録は後で別途 new-lead-registration を実行
   ```

2. 「はい」が選ばれた場合：
   - `new-lead-registration` スキルをサブエージェントとして呼び出し、リード情報収集 → 案件ID採番 → 営業管理表への行追加（`ledger.py append`）→ Drive プロジェクトフォルダ作成までを丸ごと任せる
   - 必要な追加情報（主担当、企業 HP、顧客課題、面談日等）が不足していれば、`new-lead-registration` 側が `AskUserQuestion` で取得する
   - サブスキルが完了したら、採番された**案件ID**と追加された行番号を受け取り、本スキルの **ステップ 1.5 に進む**

3. 「一旦中断」が選ばれた場合：
   - 「次回 `○○社の新規リード登録` などと話しかけてください。登録後にもう一度本スキルを呼べばそのまま提案準備に進めます」とガイド
   - 終了

この設計により、**ユーザーは「○○社の提案パッケージ作って」とだけ言えば、リード未登録でも完結**します。new-lead-registration を別途呼ぶ必要はありません。

### ステップ1.5: 提案フェーズ判定（initial / estimate の振り分け）

ステップ4 を**初回ルート（3層：storyline-gate→deck-composition→pptx-custom）**にするか **estimate ルート（proposal-estimate）**にするかをここで決めます。判定は以下の優先順位で行ってください。

#### A. ユーザー発話から明示シグナルを拾う

| シグナル | 判定 |
|---|---|
| 「見積もり」「価格」「料金」「○○万円」「○○円」「ガントチャート」「スケジュール入り」「実施計画」「契約」「CAIO 契約」「yourrecord 導入提案」「フェーズ別計画」など金額・期間・具体サービス名を含む | **estimate** |
| 「初回提案」「初回アプローチ」「まずは挨拶」「ご紹介用」「未来像を見せる資料」「アポ取り用」など、まだ価格・期間に踏み込まない | **initial** |
| 上記いずれも明示なし | → B へ |

#### B. 営業管理表 ＋ Drive 案件フォルダの状態から推定

`ledger.py read` / `ledger.py find` で取得した行の **`ステータス` 列** と、
案件フォルダ `{{paths.projects}}/{{paths.project_naming}}/` の中身を突き合わせて判定します。

| `ステータス` 列 | 判定 |
|---|---|
| `リード`、または `商談中` かつ `01_提案・見積` に pptx が無い | **initial** が有力 |
| `商談中` かつ `01_提案・見積` に既に提案 pptx がある | **estimate** が有力 |
| `金額提示済み` / `契約済み` / `デリバリー中` | **estimate** |
| `失注` | 再アプローチか確認したうえで **initial** |

補助シグナル：

- `顧客課題メモ` 列や `最終接触日` 列から、既に提案済みかどうかを読む
- `顧客課題メモ` に「金額」「初期費用」「月額」「契約期間」などの記述あり → **estimate**
- `ステータス` が `商談中` 以上まで進んでいる → **estimate** 寄り

#### C. 判定が割れる／確信が持てない場合は AskUserQuestion で1問だけ確認

```
「{企業名} 様向けの提案書、どちらを生成しますか？」
選択肢:
- 初回提案書（未来像中心、価格・スケジュール未記載 / 初回3層で生成）
- 見積もり付き詳細提案書（サービス内容・価格・ガントチャート入り / proposal-estimate を使用）
```

判定結果は内部変数 `proposal_kind` に `"initial"` または `"estimate"` として保持し、**ステップ4 でサブスキルの呼び分けに使う**。判定の根拠（ユーザー明示／台帳＋フォルダから推定／質問回答）も後続のステップ8 の結果報告に含めると、主担当が判定ロジックを後から追跡できる。

### ステップ2: 案件情報を取得する

`ledger.py read`（または `ledger.py find` で行を引いてから `ledger.py read`）で対象行を取得し、以下を抽出：

| 項目 | 列 | 用途 |
|---|---|---|
| 取引先 | A | フォルダ名・提案書の宛名 |
| URL | B | 企業サイト（リサーチの起点） |
| メモ（顧客課題／アクション） | C | 案件概要・課題・背景情報 |
| 主担当 | D | 提案書の作成者欄／「{主担当メンバー}からのご紹介」の記述 |
| ステータス | W | フェーズ判定（ステップ1.5 B） |
| 想定額 | X | 見積もりレンジの当たり |
| 獲得日 | Y | 経過期間の把握 |
| **案件ID** | **Z** | フォルダ番号（3桁ゼロ埋め）。**案件フォルダはこれで引ける**（事業区分・サブフォルダ名は案件により異なる） |
| 最終接触日 | AA | 前回接触からの経過。ステップ6 で更新する |
| 最終議事録日 | AB | 商談履歴の有無 |

行オブジェクトには `__row`（行番号）が付いてくるので、そのまま `update --row` に渡せます。

案件ID が空の場合は、Drive の `{{paths.projects}}/` 配下（事業区分フォルダは案件による）からフォルダを探して補完し、
見つからなければ new-lead-registration の採番手順（`ledger.py next-id`）に従って採番したうえで `案件ID` 列に書き戻します。

### ステップ3: Drive 親フォルダを確保する

Google Drive で `{{paths.projects}}/{{paths.project_naming}}/` を探します。
**案件フォルダの親は `{{paths.projects}}` だが、事業区分ごとに分かれている組織もある。**名前で決め打ちせず、案件IDで探すこと。

```
例: 案件ID=122, 企業名=サンプル → {{paths.projects}}/122.サンプル/
```

**案件IDが分かればフォルダは引ける**ため、フォルダ URL を台帳に書き戻して二重管理することはしません。

存在しない場合は **この場で作成** します（new-lead-registration が忘れられていても困らない設計）。

テンプレート構造を `{{paths.project_template}}/` から複製：

- `01_提案・見積/`
- `02_契約/`
- `03_制作・成果物/`
- `04_請求/`
- `05_受領資料/`

複製は Drive MCP の `copy_file` を使い、各サブフォルダを順に作成。

> 既存案件の一部は `01_契約書`〜`07_議事録` という別テンプレートで作られている。
> 既存フォルダがある場合は**その構造に合わせる**こと。

### ステップ4: 提案書を生成する（フェーズで振り分け）

ステップ 1.5 で確定した `proposal_kind` に応じて、以下のとおりサブスキルを呼び分けます。

#### proposal_kind == "initial" の場合

初回は固定テンプレを廃し、**storyline-gate → deck-composition → pptx-custom の3層**で組む。

1. 骨子（storyline-gate）
   - 入力: `取引先名` / `URL` / `顧客課題メモ` / `紹介元` と `営業担当` / 想定読者(初期値=経営層)
   - 文脈として本スキル同梱の `references/first-proposal-lens.md` を読み込む（世界観・目的=60分アポ獲得・リサーチ観点）
   - **骨子の前に、`references/prototype-case-format.md` の書式で試作案（現場で起きていそうなこと／試作案／効き目＋実現策）を3〜5件出す。** 未来像だけの骨子は storyline-gate で差し戻される
   - storyline-gate が企業リサーチ → 5要素を埋め → storyline.md を起票
   - 承認ゲート ＝ v2 ゲート①。方向性（コアメッセージ＋論理）と証拠レベル(proof_level)をここで握る
2. 構成（deck-composition）
   - 承認済み storyline.md ＋ レンズのアーク選択を入力に slide-plan.md を生成
3. 描画（pptx-custom）
   - slide-plan.md を描画し `/tmp/proposal_<ID3桁>_<企業名>_<日付>.pptx` を出力

出力 pptx パスを本スキルが受け取り、以降（ステップ5 アップロード）は現行どおり。

#### proposal_kind == "estimate" の場合

`proposal-estimate` スキルをサブエージェントとして起動。入力情報として以下を渡す：

- 企業名・担当者名・関係性
- 提案サービス（yourrecord / CAIO / カスタム開発 等）— ユーザー発話から拾う、不足なら estimate 側が壁打ちで詰める
- 価格設計（初期費用・月額・割引条件）— 同上。営業管理表の `想定額(税込)` 列を当たりとして渡す
- 期間・契約形態 — 同上
- 営業管理表 `顧客課題メモ` 列の案件背景

サブエージェントは壁打ちを経て、`/tmp/proposal_estimate_<ID3桁>_<企業名>_<日付>.pptx` を出力します。

> **骨子ゲート（storyline-gate）は proposal-estimate 内で実行される**ため、本スキルでは別途走らせない（二重実行しない）。

#### 共通の取り決め

- どちらのケースも、サブエージェントが返す **出力 pptx パス** を本スキル側で受け取り、ステップ5 でアップロード対象として使う
- サブスキル内で完結している作業（リサーチ、config 構築、QA 等）は本スキルでやり直さない
- サブスキルが失敗した場合は、本スキルもエラー終了し営業管理表のステータスは更新しない（部分成功を作らない）

### ステップ5: Drive に提案書をアップロード

`01_提案・見積/` 配下に pptx をアップロードします。

> **この note は、本ファイルのフォルダパス規約とファイル名規約を上書きする。**
> 規約は初期値であり、**実体が違えば実体に合わせる**。
>
> **経路の選び方（分岐する。無条件に cp ではない）**
>
> 1. **案件フォルダがセッションの接続フォルダに見えているか** を確認する。見えていれば `cp`。
> 2. 見えていなければ、従来どおり Drive コネクタの base64 アップロードを使う。
>
> **原則：納品物の品質を、運搬経路の都合で下げない。** 通らないなら画質ではなく経路を変える。
>
> なぜ cp を優先するか：コネクタの `create_file` はファイル全体を base64 にして1回の呼び出しに載せる方式のため、
> 通るかどうかは**バイト数**で決まる。**上限は公表されておらず環境依存**なので、閾値を覚えない。
>
> > 観測（2026-09）：写真2枚入り・約290KB の pptx が上限超過で失敗し、cp に切り替えて解決した。1点しか測っていない。
>
> **実フォルダ名は案件ごとに違う。** `01_提案・見積` は規約上の名前で、実体は `01.提案` のこともあり、
> 案件フォルダの親（`{{paths.projects}}`）は組織や事業区分で分かれることがある。**必ず実物を確認してから置く**：
> ```bash
> find "<接続フォルダ>" -maxdepth 3 -type d -name "*{企業名}*"
> ```
> **上書き事故を防ぐ。** `cp` は同名ファイルを黙って潰す。本スキルは v2-1 で「既存は別バージョン名で退避」と定めているので、
> **`cp -n` を使い、ファイル名に日付を入れて版を分ける**。
> ```bash
> cp -n "<生成した pptx>" "<接続フォルダ>/<事業区分>/<案件フォルダ>/<提案フォルダ>/<ファイル名>_{YYYYMMDD}.pptx"
> ```
> 同フォルダに既存の提案書があれば、**その命名に合わせる**（下の規約より現場の並びを優先）。
>
> **URL は同期後に取得する。** cp には戻り値の URL が無い。Drive 同期が回ってから
> `search_files(title contains '{ファイル名}')` で引く。同期前に報告する場合は、ステップ8 に
> **「Drive 同期待ち（ローカル格納済み: <パス>）」**と明記し、URL 欄を空のまま通さない。

ファイル名は案件IDから引けるよう、フェーズに応じて：

```
proposal_kind == "initial":  {案件ID3桁}_提案書_{企業名}_{YYYYMMDD}.pptx
proposal_kind == "estimate": {案件ID3桁}_提案見積_{企業名}_{YYYYMMDD}.pptx

例: 122_提案書_サンプル_20260721.pptx
例: 122_提案見積_サンプル_20260721.pptx
```

アップロード後、Drive ファイルの shareable URL を取得（cp 経路の場合は上記のとおり同期後に `search_files` で引く。同期前なら「Drive 同期待ち」と明記する）。

### ステップ7.5: 提示前の自己レビューゲート（必須・省略禁止）

成果物をユーザーに提示する**直前**に、`proposal-self-review` を必ず通す。**ここを飛ばすと、ユーザーがレビュアー役をやることになる**（過去、それで骨子が v9 まで往復した）。

通す順は `A（中身）→ A2（書き方）→ A4（相手は明日から何をするか）→ B（構成）→ C（体裁）→ D（証拠）→ E（表現・トーン）→ F（機械チェック）`。

**A4 は独立したゲートとして必ず通す。** ここが提案書と調査報告を分ける唯一の線で、実運用で一番落ちる。
自問の型は「この資料を閉じた相手の口から出る最初の一言は何か」。**「へえ、他社はそうなんだ」なら失敗**、「じゃあ、まず◯◯からやろうか」なら成功。

**特に F は 0 件を確認するまで提示しない。**

| # | 何を見るか |
|---|---|
| F1 | 金額の**単位漏れ**（「億」「万」で終わっていないか）。`円円` も 0 件 |
| F2 | NG表現（社内ジャーゴン・相手の弱みの断定） |
| F3 | **全章に中扉**があるか（章の数 ＝ 扉の枚数） |
| F4 | 目次のページ番号が**最終ビルド後の実測値**か（手書きのまま放置していないか） |
| F5 | 隣接2枚で同じ表・同じ指標を繰り返していないか |
| F6 | **全ページを画像化して目で見た**か |
| F7 | 合計＝内訳の和／同じ数字が前後スライドで食い違っていないか |
| F8 | **表の最終行が下のカードに隠れていないか**（画像で確認。折り返しで行が伸びる） |

A2 で特に落としやすいのは次の4つ。**該当が1つでもあれば書き直してから提示する。**

- メッセージが事実の要約になっている（「◯◯は2,700億円、△△は616億円です」）
- 主語が提案側になっている（「本日の位置づけ」「我々から提案します」）
- 抽象（型・分類・フレーム）が本編に残っている → Appendix へ
- 見出しが「〜について」「だから◯◯はこうする」になっている

A4 で特に落としやすいのは次の5つ。**該当が1つでもあれば作り直してから提示する。**

- 他社事例を「やったこと」だけで載せ、**結果（数字）が無い**
- 事例のあとに「**相手ではこうする**」が無い、または「業務効率化が期待できます」で止まっている
- **事例の枚数 > 相手の具体の枚数**（＝調査報告になっている）
- 業務の**一覧**を並べて具体を書いたつもりになっている（一覧は網羅性の提示）
- 効果に**測り方**が無い／目標値に**算出根拠**が同じ画面に無い／最初の2週間の**日程・止める条件**が無い

直せない／ユーザーの判断が要る点（価格方針、痛い事実を主題にするかどうか）は、**「ここは確認が必要」と明示して**添える。黙って通さない。

## エラーハンドリング

- **リードが見つからない** → ステップ1-B に進み、対話でリード登録 → 提案準備に続行
- **`ledger.py find` が複数ヒット** → `AskUserQuestion` で選ばせる。以降の更新は必ず `case_id` で行う
- **`案件ID` 列が空** → Drive の案件フォルダから補完、無ければ採番して `案件ID` 列に書き戻す
- **`ledger.py update` が「複数行が該当」で失敗** → `company` ではなく `case_id` を指定して再実行
- **既に同フェーズの提案書が `01_提案・見積` にある** → 「既に提案書があります。再生成しますか？」と確認
- **フェーズ判定が割れる** → ステップ1.5 C の `AskUserQuestion` で確認（無音で勝手に決めない）
- **初回3層 / proposal-estimate がエラー** → エラー内容をユーザーに返し、営業管理表は更新しない（部分成功を作らない）
- **cp 経路が使えない**（接続フォルダに案件フォルダが見えない） → Drive コネクタの base64 アップロードにフォールバック
- **Drive アップロードがエラー** → ファイルサイズが原因なら cp 経路を再検討。それ以外はリトライ1回、それでも失敗ならエラー報告

## デザイン原則

- **単一責任**：本スキルは「振り分け＋統合」のみ。pptx 生成・リード起票のロジック追加は必ず該当 atomic スキル側へ

- **ユーザーに毎回確認**：上書き前提のアクション（Google Drive 上書き、ステータス上書き、フェーズ判定が割れる場合）は事前確認
- **URL を二重管理しない**：案件フォルダは`案件ID` 列から引ける。台帳は「状態」だけを持ち、成果物の実体と URL は Drive 側に置く

# 【v2 追補】ループ型・証拠レベル・ゲート②（この節が上位ルール）

> 本節は v2 で追加された**正式な上書き指示**。上の本文（v1）と矛盾する場合は **本節を優先**する。
> 趣旨：提案を「pptxを作る直線」から「ディスカッション起点 → 実アプリ → デモ → 調整のループ」に拡張し、
> 人間の確認を「方向性＋証拠レベル」「価格・文面」の2ゲートに集約する。

## v2-0. ステップ0：方向性ディスカッション準備（推奨・前出し）

発話に「経営メンバーと相談」「方向性をまず決めたい」「壁打ち」が含まれる、または商談ステータスが初期段階の場合、
ステップ1の前に `discussion-prep` をサブスキルとして呼ぶ。戻り値（決まった方向性＋証拠レベルの叩き台）を
`proposal_direction` / `proof_level(暫定)` として受け取り、v2-2 ゲート①へ渡す。方向性が既に決まっている場合はスキップ。

## v2-1. 配管確認の無音化（ステップ1B / 1.5 / 3 / 6 を上書き）

以下は**事前に質問せず黙って実行**し、ステップ8の完了報告でまとめて提示する（後から戻せる操作のため）。

- 1B「登録しますか？」→ 黙って起票し報告で通知
- 1.5C「初回/見積もりどちら？」→ 営業管理表の`ステータス` 列＋案件フォルダの中身から推定して進む。割れた時のみ1問
- 3「Drive上書き？」→ 黙って格納（既存は別バージョン名で退避）
- 6「ステータス上書き？」→ 黙って更新し差分を報告

聞いてよいのは v2-2 ゲート① と v2-4 ゲート② だけ。

## v2-2. ゲート①：方向性 ＋ 証拠レベル（AskUserQuestion）

> **ゲート① ＝ storyline-gate の承認に一本化する。** 方向性は storyline の②コアメッセージ・③論理に、証拠レベル(proof_level 1/2/3) は storyline の④証拠設計にマップする。下の proof_level 表はそのまま判断材料として残す。discussion-prep（v2-0）は storyline-gate の前段（社内で方向を決める下ごしらえ）という位置づけで不変。

(1) 方向性：discussion-prep の結論があれば提示して確認。無ければテーマ/読者/重点を2-3問。

(2) 証拠レベル：案件シグナル（取引規模・相手の本気度・困りごとの具体度・経営メンバーのGOの有無）から
**推定して提示**する。デフォルトは固定せず毎回推定し、選ぶのはユーザー。

| proof_level | 見せ方 | 推定が向く条件 |
|---|---|---|
| 1 | 未来像pptxのみ | 探りの初回 / 規制業界 / 相手が固い |
| 2 | pptx＋画面モック | 具体性は要るがフルビルドは早い |
| 3 | 実アプリをデプロイ | 本気・大型・経営メンバーのGO |

結果を `proposal_kind`(initial/estimate) と `proof_level`(1/2/3) に保持。

## v2-3. ビルド分岐（ステップ4を proof_level で拡張）

- level 1：初回は3層（storyline-gate→deck-composition→pptx-custom）/ estimate は proposal-estimate で pptx のみ（現行どおり）
- level 2：上記 pptx ＋ 実物Excel/モック機構（deliverable-artifacts。osi-docs に保全し deck-composition/pptx-custom から使用）で実物を1-2点添える
- level 3：`create-app`（osi-deploy）をサブエージェントで起動し、デモ用の**動く最小アプリ**を1機能に絞って構築。
  本番課金・実データ連携はしない。APP_URL を受け取り提案資料にデモリンクとして埋め込む。

サブスキル失敗時は部分成功を作らず停止（v1原則を踏襲）。アプリ構築ロジックは deploy-app に委ね、本体に書かない。

## v2-4. ゲート②：価格・文面・約束（ステップ6とステップ7の間に挿入）

AIが提示（ユーザーの手間を消す部分）：

- **価格3案**：守りの最小 / 標準 / 攻めの上位。各案に「この客にこの数字を出す根拠」1行
- **文面2版**：数字をそのまま出す版 / 対面に回して匂わせる版
- **約束ラインの素案**：このデモで何を見せ、次に何を持ち帰るか

`AskUserQuestion` で「どの価格案／どの文面／約束ラインOK」を確認。**送信そのものはユーザーが行う**（桁が動く話は人間が出す）。
決まった価格は営業管理表の `想定額(税込)` 列に、約束ラインは `顧客課題メモ` 列に追記し、ステータスを `金額提示済み` に更新する
（`ledger.py update`(case_id=...)）。文面・条件の詳細な記録は Drive 案件フォルダ側の成果物として残す。
