# 商談議事録自動化スキル

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: osi-core の `getting-started/assets/osi-profile.example.md`。getting-started スキルが質問して作る）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

自社の営業ワークフローにおいて、録音した商談の文字起こしを
構造化された議事録に変換し、**議事録の正本を Drive の docx として格納**したうえで、
**議事録から営業状況を判断して**案件マスタ（営業管理表）の状態を更新するスキル。

## なぜこのスキルが必要か

AS-IS では、Plaud で録音した文字起こしを主担当が手で読み込み、

1. サマリを書き起こす
2. 次アクションを抽出する
3. 重要な発言をピックアップして memo
4. docx に整形して Drive にアップロード
5. 台帳のメモ欄に次アクションを1行書く
6. 案件ステータス・確度・金額・次アクション・期日を、商談の結果に合わせて更新する

をやっている。これが商談 1 件あたり 30 分〜1 時間。しかも 6 は商談の帰りに触らないと二度と触られず、
台帳が実態から離れていく。
このスキルなら「今日の○○社の録音を議事録にして」の一言で、会社の議事録DB（秘書の置き場）か
Plaud MCP から文字起こしを直接取得して全自動化する（貼り付けも従来どおり可）。営業状況は AI が判断して
「こう書きます」と見せ、人は OK を出すだけにする。

## 前提：案件マスタは営業管理表

案件情報の台帳は **`{{ledgers.sales}}`**（タブ `取引先管理`、ヘッダは5行目）。
**ディレクトリ経由（openpyxl）で読み書きする。Google Sheets API・GCPサービスアカウントは使わない。**
台帳の触り方・不変条件・列の一覧は
**`../new-lead-registration/references/ledger-access.md` を必ず読むこと**（osi-sales 共通の正本）。

> **正本が別の場所にある会社がある。** `{{ledgers.sales_rules}}`（営業管理表の運用ルール）に
> 「正本は DB（秘書など）。xlsx は書き出し」と書かれていれば、**書き込みは正本に対して行い、xlsx は触らない**
> （xlsx を直しても正本に反映されず、次の書き出しで消える）。正本への書き方は運用ルールに従う。
> 詳しくは `references/sales-status-update.md` の「1. 正本を確かめる」。

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L columns                       # 列名・ステータス値・パス
python3 $L find --company "{企業名}"      # 表記ゆれを吸収して行を引く
python3 $L find --case-id {案件ID3桁}
```
シートID・タブ名などの組織固有値は `config/osi-sales-settings.md` を参照してください。

- ヘッダは `{{ledgers.sales_header_row}}` 行目（既定5行目）、データはその次の行から
- このスキルが触る列（getting-started が作る営業管理表の列名）: `案件ID` / `取引先名` / `ステータス` / `確度` /
  `次アクション` / `次アクション期日` / `最終接触日` / **`議事録`**（議事録ファイルのリンクまたはパス）/ `顧客課題メモ` /
  金額まわり（`想定額` / `課金形態` / `想定開始月` / `想定期間`）/ 窓口（`窓口氏名` / `窓口メール`）/
  保留・失注（`失注/保留日` / `失注/保留理由` / `再アプローチ月`）。実際の列名は台帳のヘッダが正
- **セクション見出しは無い**（1案件1行・行は動かさない）。段階はステータス列が表す
- ステータス値は営業管理表の「マスタ」タブの値が正（既定は `リード` / `商談中` / `提案中` / `金額提示済み` /
  `受注` / `契約済み` / `デリバリー中` / `保留` / `失注` / `終了` の10値）。集計が壊れるので**値を勝手に増やさない**
- 列は**ヘッダ行の文字列**で指定する（列レターは使わない）。実際の列名は
  `ledger.py columns` の戻り値 `columns` で確認できる（存在しない列を指定するとエラーで止まる）。
  既存台帳で列名が違う（例：`議事録` 列が無い）ときは、無い列の更新は飛ばして報告に書く
- 数式の入った列（売上集計など）には書き込まない

**議事録の本文は台帳に持たない。** 議事録の正本は案件フォルダ
`{{paths.projects}}/{{paths.project_naming}}/03_制作・成果物/` に置いた docx で、
台帳（営業管理表）は「状態」（ステータス・確度・次アクション1行・期日・金額・窓口・最終接触日・議事録リンク）だけを持ちます。

## 接続が無いときの動き（先に判定する）

`osi-profile.md` の `connectors.*` と、実際に見えているツールで判定する。**どれが無くても議事録は作れる。**

| 無いもの | 動き |
|---|---|
| 会社の議事録DB（`secretary.project_ref` が無い／`supabase_execute_sql` が無い） | Step 2-A を飛ばし、Plaud MCP（Step 2-B）から取る |
| Plaud（`connectors.plaud: false` またはツールが無い） | 議事録DBがあればそこから取る（Step 2-A）。無ければ文字起こしは貼り付け・ファイル（txt/docx）で受ける（Step 2-C） |
| Google Drive（ツールが無い） | 連結フォルダの案件フォルダ `{{paths.projects}}/{{paths.project_naming}}/03_制作・成果物/` に**ローカル保存**するだけ。Drive URL の取得・書き戻しは省略し、台帳の `議事録` 列にはフォルダからの相対パスを入れる |
| Gmail | 2-C の Gmail 経路を飛ばす |
| Slack（`connectors.slack: false` またはツールが無い） | 通知（Step 8.5）を飛ばし、報告に「通知：なし（Slack 未接続）」と書く |
| 営業管理表の正本に書く手段 | Step 8 の「こう書きます」の表を作って見せるところまで行い、書けなかった旨と表を報告に残す（止まらない） |

連結フォルダが Drive の同期フォルダなら、ローカル保存＝Drive 保存になる（アップロードは要らない）。

## 重要：このスキルの責任範囲

Claude（あなた）が **「文字起こしの構造化」と「営業状況の判断」** を担当する。
**docx の整形は `scripts/build_minutes.py` に完全に任せる**。

つまり Claude はワード文書生成コードを書かない。代わりに、

- 議事録DB・Plaud MCP から取得した（または貼り付けられた）文字起こしを読み、
- サマリ・次アクション・重要発言・営業状況の判断を抽出して JSON にし、
- スクリプトで docx を生成し、
- 案件フォルダ（Drive が繋がっていれば Drive）に格納して、
- 営業状況は「こう書きます」と見せて OK をもらってから営業管理表の正本に書く。

## ワークフロー

```
1. 案件特定（営業管理表を検索 — proposal-package と同じロジック）
2. 文字起こしを取得（会社の議事録DB（秘書の置き場）→ Plaud MCP の順に直接取得が基本／貼り付け・Gmail転送・Drive はフォールバック）
3. テキストを構造化（サマリ / 次アクション / 重要発言 / 営業状況の判断）
4. ユーザーに構造化結果を確認（必要に応じて修正）
5. docx 生成（scripts/build_minutes.py）— 出力先は最初から案件フォルダの 03_制作・成果物/
6. 保存先の確認（連結フォルダに直接書く。Drive が繋がっていればリンクを取る）
7. 営業管理表の `顧客課題メモ` 列に議事録1行を追記
7.5 `最終接触日` と `議事録` 列を自動更新
8. 営業状況の更新（ステータス・確度・次アクション・期日・金額・窓口・保留/失注）— 書く内容を見せて OK で書く
8.5 通知（Slack が繋がっていれば。無ければ飛ばす）
9. 結果報告
```

## Step 1: 案件特定

ユーザーの発話から対象案件を特定する：
- 案件ID（「案件ID 098」「98 番」）
- 企業名（「サンプル株式会社」「サンプル社」）

営業管理表を検索して該当行を特定する：

```
python3 $L find --company "{企業名}"    # 表記ゆれ（株式会社・促音・記号）は吸収される
python3 $L find --case-id 098           # 案件IDが分かっているならこちらが確実
```

- 候補が1件 → そのまま採用（戻り値の `row` / `案件ID` を保持）
- 候補が複数 → `AskUserQuestion` でユーザに選ばせる（1社で複数案件が走ることがあるため）
- **発話に案件の指定が無い**（文字起こしだけ貼られた等）→ `osi-core:jev-judge` で当てる。営業管理表の進行中の案件名を
  criteria にし、choice「この議事録はどの案件の打ち合わせ記録ですか？」を 1 回かける（検証済み: 自信 0.9 以上なら 98% 正解）。
  自信 ≥ 0.9 → その案件で進める旨を 1 行で伝えて続行。未満 → 上位 3 候補を `AskUserQuestion` で選ばせる。
- 候補が0件 → 「営業管理表に該当案件がありません。先に `new-lead-registration` を実行してください」と案内（議事録単独で完結はしない）

続けて対象行の全項目を（正本から）取得し、**`顧客課題メモ` 列の既存文言**・
**`最終接触日` 列と `議事録` 列の現在値**・**ステータス／確度／次アクション／期日／金額／窓口の現在値**を保持しておく。
Step 7・7.5・8 でこれらを使う（既存メモの追記、日付の巻き戻し防止、「いま → こう書く」の表）。

以降の更新は必ず**案件ID（`case_id`）で行を特定**すること（同名・複数案件で誤爆しないため）。

## Step 2: 文字起こしの取得

> 取得の詳しい手順（SQL・ツール名・候補の見せ方）は `references/transcript-parsing.md` の「1. 取得チャネル」が正本。
> ここでは順番と判断だけを書く。

### 2-A: 会社の議事録DB（秘書の置き場）から取る（秘書がある会社ではプライマリ）

`osi-profile.md` に `secretary.project_ref` があり、会社のリモート MCP（URL でつなぐコネクタ）の `supabase_execute_sql` が見えていれば、
まずここを見る。秘書の置き場の `public.minutes` には、会社に届いた議事録が**全員分**たまっている
（Plaud の自動転送メール・Gemini のメモ・議事録パートナーの文字起こし）。Plaud につながっていなくても、
自分以外のメンバーの録音でも取れるのが利点。

1. **候補を探す**：`meeting_date`（「今日の」「昨日の」→ 日付）と `subject` / `account`（企業名・話題）で
   `select` し、本文は取らずに件名・録った人・長さだけ見る。
   - 候補が 1 件 → 即決
   - 複数 → 件名・会議の時刻（日本時間に直す）・録った人・長さを添えて `AskUserQuestion`。
     相手の名前は件名に出ないことが多いので、迷うときは本文の冒頭 1,000 字を見て誰との会議か確かめる
   - 0 件 → 2-B へ（録音が終わってから届くまで数分かかる。Plaud 側にはすぐある）
2. **本文を取る**：`id` で `body` を取る（話者ラベル付きの全文。Plaud の文字起こしと同じもの）。
   長時間の録音は 10 万字を超えることがあるので、必要なら分けて取る。要約せず全文を読む。
3. `partner_todos`（議事録パートナーの ToDo）は **参考情報に留める**。構造化は Step 3 で全文から行う。
4. **読むだけ。** `insert` / `update` / `delete` はしない。`minutes_private`（載せない指定の議事録）は読まない。

### 2-B: Plaud MCP で直接取得（秘書が無い会社ではプライマリ）

Plaud MCP コネクタ（ツール名に `plaud` を含む `list_files` / `get_file` /
`get_transcript` / `get_note` / `login` 等）が利用可能なら、貼り付けを待たずに直接取りに行く。

1. **録音の特定**：`list_files` を使う。
   - キーワード（`query`）：企業名・録音名の一部（大文字小文字不問）
   - 日付（`date_from` / `date_to`、YYYY-MM-DD）：「今日の」「昨日の」「5/6 の」を変換
   - 候補が複数 → `AskUserQuestion` で選ばせる（録音名・開始時刻・長さを添える）
   - 候補が 0 件 → 検索条件を緩めて再検索し、それでも無ければ 2-C へフォールバック
2. **文字起こしの取得**：`get_transcript` で全文（タイムスタンプ・話者ラベル付き）を取得。
   話者ラベルがあるので、貼り付けより話者推定の精度が上がる。
   `get_transcript` が空を返すときは `get_file` の `source_list`（文字起こし）を読む。
3. `get_note`（Plaud の AI 要約）は **参考情報に留める**。サマリ・次アクションの構造化は
   Step 3 で Claude 自身が全文から行う（Plaud 要約の転記で済ませない）。
4. **認証エラー（401 / Not authenticated）** → `login` ツールで再サインインを促してから再試行。
5. 1本の録音に商談以外の雑談・別の会議が混ざっていることがある。対象の商談の区間だけを使う。

### 2-C: フォールバック（議事録DB・Plaud のどちらにも無い／道具が無い場合）

優先順：
1. **チャットへの貼り付け**：従来どおり Plaud アプリからのコピペを受け付ける
2. **Gmail 転送メール**：Plaud から Gmail に自動転送されている場合、Gmail 検索
   （`search_threads` で `from:plaud` や録音名・日付）で本文の文字起こしを取得する
3. **Drive ファイル**：ファイル名指定があれば `read_file_content` で取得（Drive が繋がっていなければ、連結フォルダ内のファイルを直接読む）

どれも無ければ `AskUserQuestion` で「Plaud の文字起こしを貼り付けてください
（または録音名・日付を教えてください）」と促す。

> 取り込み後の特徴対処・話者推定の詳細は `references/transcript-parsing.md` を参照
> （session-review / shodan-prep と共通の作法）。

## Step 3: テキスト構造化

文字起こしを以下の 4 セクションに整理する。**このステップが Claude の主要責任**。

### サマリ（必須・3-5 点）

「議事録を読まない人でも、3 点読めば何が起きたか分かる」レベルに圧縮。
- 相手の最大の関心事
- 決まったこと / 決まらなかったこと
- 次のステップ

時系列ではなく **重要度順**。

### 次アクション（必須）

「誰が・いつまでに・何を」を明示。曖昧なものは省く。
JSON では：

```json
{
  "todo": "見積もり提案書（自社サービス 標準プラン）を作成",
  "due": "2026-05-13",
  "owner": "自社担当"
}
```

期限は YYYY-MM-DD 形式が読み取れる場合のみ。曖昧な場合は「次回打ち合わせまで」等の文字列でも OK。

担当が「弊社」「先方」と曖昧な場合は、文字起こしから読み取れる人名を優先。読み取れなければ会社名の方を入れる。

### 相手の重要発言（必須）

「あとで提案書に使えるキーワード」を中心に、原文に忠実に引用。
- 課題の核心を表す発言
- 意思決定の根拠になる発言
- 価格や期間に関する具体的な発言

3-5 件が目安。多すぎると埋もれる。

### 営業状況の判断（必須）

この商談で営業状況がどう動いたかを判断し、Step 8 で書く内容（列ごとの「いま → こう書く」と根拠の発言）を作る。
判断の決まり（段階ごとに埋める列・次アクションの書き方・見せ方）は
**`references/sales-status-update.md` に従う**。会社ごとの列名・選択肢は運用ルールと台帳が正。

- 対象：ステータス・確度・次アクション（1文）・次アクション期日・金額まわり・窓口・保留/失注の3列
- 根拠は議事録の明確な発言・合意だけ。動きが無ければ「変えない」と判断してよい（近況交換・技術の話だけの回など）
- ステータスは営業管理表の「マスタ」タブの値だけ（`ledger.py columns` で確認できる）

## Step 4: ユーザー確認

構造化した JSON を簡潔にチャットに表示し、ユーザーに「この内容で議事録化しますか？」と確認。
修正点があれば反映してから次へ。営業状況の判断はここでは見出しだけ示し、細かい確認は Step 8 で行う。

## Step 5: docx 生成

```bash
python3 scripts/build_minutes.py <minutes.json> \
  "{{paths.root}}/{{paths.projects}}/{案件フォルダ}/03_制作・成果物/{YYYYMMDD}_議事録_{企業名}.docx"
```

- 出力先は**最初から案件フォルダの `03_制作・成果物/`**（`/tmp` などに作ってから移さない。移し忘れ・消失の元）。
  minutes.json は作業用なので、スクラッチ（outputs）に置いてよい
- `meta.own_company` に `{{company.name_display}}`（無ければ `{{company.name}}`）を渡す。フッターが
  「{相手社名} × {自社名}」になる。渡さなければ相手社名だけが出る（スクリプトは特定の社名を持たない）
- `meta.accent_hex` に `{{brand.accent_hex}}`（無ければ `{{brand.primary_hex}}`）を渡すと見出し色が自社の色になる。
  空なら既定の濃紺

## Step 6: 保存先の確認

格納先（Step 5 で直接書いた場所）：
```
{{paths.projects}}/{{paths.project_naming}}/03_制作・成果物/
```

ファイル名：`{YYYYMMDD}_議事録_{企業名}.docx`

例：`20260506_議事録_サンプル株式会社.docx`

- `03_制作・成果物/` フォルダが存在しない場合は作成する
- 連結フォルダが Drive 同期フォルダでなく、Google Drive コネクタが繋がっている場合だけ、Drive の同じ場所にアップロードして URL を取る
- Drive が繋がっていない → ローカル保存で完了。URL は取らない（Step 7.5 はパスを書く）

## Step 7: 営業管理表の `顧客課題メモ` 列に1行追記

**議事録の正本は Drive の docx**（Step 6）であり、本文を台帳に写すことはしない。
営業管理表には「この案件が次に何をするか」が一目で分かる**1行だけ**を残す。

`ledger.py update`(case_id="{案件ID3桁}") で `顧客課題メモ` 列を更新する（正本が別にあれば正本に追記する）。書式：

```
{YYYY-MM-DD} 議事録: {次アクションの最重要1件}
```

例：`2026-07-21 議事録: 見積もり提案書（自社サービス 標準プラン）を自社担当が7/24までに作成`

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L update --case-id 098 \
  --append-memo "{YYYY-MM-DD} 議事録: {次アクション最重要1件}"
```

- **既存メモは消さない。** `--append-memo` は上書きではなく末尾への追記なので、自分で連結しない
- 追記するのは1行だけ。サマリ・重要発言の転記はしない（それは docx にある）
- 次アクションが1件も抽出できなかった場合は `{YYYY-MM-DD} 議事録作成` とだけ書く
- 台帳に同じ案件IDの行が複数あると `--case-id` で一意に引けない（「複数行が該当」で止まる）。その場合は `find` の結果から `--row` で行番号を指定し、重複は報告に書いて人に直してもらう

## Step 7.5: 最終接触日 / 議事録リンクの自動更新

議事録を記録したら、営業管理表の日付列を **自動で** 前進させる。これは「議事録の鮮度」と
「解約予兆（放置案件）」を一目で見えるようにするための土台で、ここを人手に委ねると必ず更新漏れが
起きる。だから Step 8 の営業状況の更新（要確認）とは違い、**確認は取らずに自動で行う**。

更新する値（いずれも議事録の日付 = `meta.date`）：
- **`最終接触日`** ← `meta.date`（商談した＝接触したため）
- **`議事録`** ← 最新の議事録の場所（Drive URL が取れていれば URL、無ければ `{{paths.projects}}` からの相対パス）

```bash
python3 $L update --case-id 098 \
  --data '{"最終接触日": "{meta.date}", "議事録": "{Drive URL または 案件フォルダからの相対パス}"}'
```

> 既存台帳に `議事録` 列が無ければ、その列は `--data` から外す（`ledger.py columns` で確認）。
> 議事録を作った事実は `--append-memo` で顧客課題メモにも残る。

Step 7 と同じ行への更新なので、`--data` と `--append-memo` をまとめて1コールにしてよい。

**日付を巻き戻さないこと（重要）**。過去の商談を後から議事録化する場合、`meta.date` が
既存の `最終接触日` の値より **古い** なら、その列は `updates` に含めない（新しい場合のみ前進させる）。
Step 1 で取得した現在値と比較して判断する。空なら無条件でセットする。

> 列名は営業管理表のヘッダ文言（`最終接触日` / `議事録`）で指定する。
> 存在しない列のエラー が返ったら、`ledger.py read` の `columns` で実際のヘッダ文言を確認すること。

## Step 8: 営業状況の更新（書く内容を見せて OK で書く）

Step 3 の「営業状況の判断」で変える列があれば、`references/sales-status-update.md` の「4. 見せ方」に従い、
**変わる列だけを「列｜いま｜こう書く」の表で見せ、根拠の発言を添えて** `AskUserQuestion` で確認する。

- 選択肢：「この内容で書く」「直して書く」「ステータスは変えず他だけ書く」「書かない」
- `受注` など後ろの工程（契約書づくり・担当への通知）が動き出す値は、そのことを表の下に一言添える
- OK が出たら、正本（運用ルールで確かめた置き場）に1回でまとめて書く。書いた人・経路を残せる正本なら残す
- 直しが来たら、直した表をもう一度見せてから書く
- 変える列が無い（近況交換だけ等）→ 確認を出さずに「営業状況：変更なし」と報告に書く

守ること：
- 値は台帳の選択肢（ステータス・確度・理由）だけ。増やさない
- **進んだ方向にだけ動かし、勝手に巻き戻さない**（`失注` は明確な発言がある場合のみ）
- 次アクションは「誰が何をするか」の一文。経緯の長文を書かない（経緯は docx）
- **行は動かさない。** 列を変えるだけでよい（セクションという概念は無い）

## Step 8.5: 通知（任意・Slack が繋がっている場合だけ）

`connectors.slack: true` で Slack のツール（`slack_send_message` 等）が見えているときだけ、
議事録ができたことを投稿する。**投稿先は固定しない**：案件チャンネルが分かればそこ、
分からなければ `AskUserQuestion` で投稿先を聞く（聞いても決まらなければ投稿しない）。

投稿文の型：
```
{企業名}（案件ID {ID3桁}）の議事録を作成しました
- 議事録: {Drive URL または 案件フォルダ内のパス}
- 次アクション: {最重要1件}（{期限}・{担当}）
```

Slack が無い・投稿先が決まらない → 飛ばして、結果報告に「通知：なし」と書く。

  - `顧客課題メモ` 列に「{YYYY-MM-DD} 議事録: {次アクション}」を追記
  - 営業状況: {変えた列の「いま → 書いた値」}（書いた / 書かない / 変更なし）

## 構造化のコツ

### 文字起こしの特徴と対処

> 文字起こしの取り込み・特徴対処・話者推定は、**`references/transcript-parsing.md`**
> （meeting-minutes / session-review / shodan-prep 共通の作法・正本）に従う。

要点（詳細は上記 reference）：句読点が少ない（意味の塊で読む）／発言者ラベルが曖昧
（meta.attendees と文脈から人名推定）／数字・固有名詞は怪しい（「(原文ママ)」注記、数字は
勝手に変えない）／長い独白は 1 行に圧縮。

### サマリの粒度の判断

- **良いサマリ**: 「先方の最大の課題は属人化。ベテランの定年退職が 2027 年に集中することが判明」
- **悪いサマリ**: 「営業の話をした」「DX について議論した」（具体性ゼロ）
- **悪いサマリ**: 「13:00-13:15 で挨拶、13:15-13:30 で課題ヒアリング、…」（時系列の引き写し）

### 重要発言の選び方

- 「これがあれば次の提案書が書ける」と思える発言を選ぶ
- 数字や固有名詞が含まれる発言は採用優先度高
- 「うちは○○なんですよね」のような自社観を表す発言は採用

### 営業状況を動かす判断

- 動かす: 商談の結果、明らかに次の段階に進んだ／止まった／終わった発言・合意があった時
- 動かさない: 単なる近況交換、技術的な意見交換だけだった時（最終接触日と次アクション・期日だけ見直す）

## やってはいけないこと

- スクリプト本体（`build_minutes.py`）の編集 — フォーマットは config 側で制御
- 議事録の本文（サマリ・重要発言・文字起こし）を営業管理表に写す — 正本は Drive の docx。台帳には `顧客課題メモ` の1行と状態だけ
- `顧客課題メモ` 列を上書きする — 既存文言は残し、必ず**追記**する
- 数字を勝手に変更する — 怪しければ「(原文ママ)」と注記する
- 営業状況（ステータス・確度・次アクション・期日・金額・窓口・保留/失注）を見せずに書く — 必ず Step 8 の表で OK をもらう
- 正本が別にあるのに書き出しの xlsx を直す — 反映されず、次の書き出しで消える
- ステータスや理由に「マスタ」タブ以外の値を入れる — 集計が壊れるので値を増やさない
- 最終接触日の更新で日付を巻き戻す — 既存値より新しい時のみ前進させる（過去分の遡及入力で鮮度を壊さない）。なお日付更新そのものは自動でよい（営業状況と違い確認不要）
- 営業管理表に対象案件がない時に、勝手に行を追加してから議事録化する — 本スキルの責務外。先に `new-lead-registration` を呼ばせる
- 数式の入った列（売上集計など）に書き込む
- 議事録DB（秘書の置き場）に書き込む・`minutes_private` を読む — 議事録DBは読むだけ

## エラーハンドリング

- **案件が見つからない（`ledger.py find` が0件）** → 「営業管理表に該当案件がありません。先に `new-lead-registration` を実行してください」と案内して終了
- **`ledger.py find` が複数ヒット** → `AskUserQuestion` で選ばせる。以降の更新は必ず `case_id` で行う
- **`ledger.py update` が「複数行が該当」で失敗** → `company` ではなく `case_id` を指定して再実行
- **`案件ID` 列が空** → Drive の `{{paths.projects}}/` からフォルダを探して補完し、`案件ID` 列に書き戻す
- **存在しない列のエラー が返る** → `ledger.py read` の `columns` で実際のヘッダ文言を確認して指定し直す
- **正本に書けない（道具が無い・権限が無い）** → Step 8 の表を報告に残し、どこに書けなかったかを書く（止まらない）
- **議事録DBに該当が無い（届くまでの時間差・秘書に流れていない録音）** → 2-B の Plaud MCP へ。両方に無ければ 2-C
- **`supabase_execute_sql` が権限エラー・置き場が違う** → `secretary.project_ref` を確かめる。直らなければ 2-B へ（止まらない）
- **Plaud MCP が 401 / 未認証** → `login` ツールでサインインを促して再試行。直らなければ 2-C へフォールバック
- **Plaud に該当録音が無い** → 条件を緩めて再検索 → 無ければ貼り付け / Gmail / Drive へフォールバック
- **文字起こしテキストが空** → `get_file` の文字起こしを読む。それも空なら AskUserQuestion で再取得を促す
- **案件フォルダ／`03_制作・成果物/` が無い** → その場で作成
- **Drive・Slack・Gmail が繋がっていない** → 「接続が無いときの動き」の表のとおり、ローカル保存・通知なしで完了させる（止まらない）
- **既に同日の議事録がある** → 「上書きしますか？」と確認
