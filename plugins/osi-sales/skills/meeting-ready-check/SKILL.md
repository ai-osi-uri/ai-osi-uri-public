# meeting-ready-check — 商談準備の確定チェック

> **組織固有値はプロファイルから読む。** 本文の `{{members.*}}` `{{paths.*}}` は、連結フォルダ直下の
> `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。

## 目的

営業の責任者（`{{members.owner}}`）が当日その場に出て、**pptx とノートを見ればそのまま喋れる状態**（＝確定）を、
前日の夜までに作る。「作業はしたが、確定したかどうか分からない」状態をなくす。

失敗の型（これを防ぐためにある）：
- 資料もデモもあるのに、誰がどこを話すかが決まっていない
- 成果物がチャットの中にだけあり、あとから探せない
- 責任者が「これでいく」と言う場面がなく、確定の印がどこにもない
- 骨子を固める前に資料やアプリを作り始め、責任者に一段ずつ上の段へ引き戻されて全部作り直しになる

## 準備物を作る前の順番（理解 → 骨子 → 具体 → 見せ方 → 作る）

いきなり pptx やアプリを作らない。各段で次の問いを**自分に立てて答えてから**次の段へ進む。
責任者に聞かれてから考えるのでは遅い（聞かれた時点で、その段が抜けていたということ）。

1. **理解：この場の主役は誰で、何を持ち帰りたいか**
   - 議事録はツールポータルを先に見る。それで終わらせず、録音（Plaud など）・メール・これまでに作った資料やアプリ
     （GitHub・Vercel・案件フォルダ・過去のチャット）まで見る。相手の言葉・頼まれたことは複数の記録で確かめる。
   - 資料を持って社内で上に説明するのが相手側の人なら、目的は「その人がそのまま話せること」になる。
     こちらの提案を聞かせる場にせず、相手の話を一緒に仕上げる場にする（主語・量・言い方もそれに合わせる）。
   - 相手のいまの状態（前向きか、時間が無いか、何を突っ込まれるのが不安か）を書き出し、進め方に反映する。
2. **骨子：一段抽象化した主張を、1枚ごとに「タイトル／メッセージ」の対で書く**
   - 相手が会話の中で使ったたとえ・言い回しを、そのまま題名や提案の名前にしない。
     読む人（その先の決裁者）に届く高さまで抽象化した言葉にする。
   - 抽象（何が問題で、何を提案するか）→ 具体（その証拠として作ったもの）の順にする。
   - 抽象の言葉は、聞かれたら具体の場面で言い直せるところまで詰めておく。
   - 骨子を文字で責任者に見せ、了承をもらってから資料に起こす。
3. **具体：業務を「今の業務（想定）→ 起きていること → こうする」で書く**
   - まず「何をする仕事か」（抽象）を置き、工程はその下に置く。
   - 推測で書いたところは「想定」「仮説」と明記し、「進める上で確認したいことと現在の仮説」を1枚にまとめる。
4. **見せ方：デモは各ページの主張の証拠として差し込む**
   - デモを独立した時間にしない。どのページの、どの主張を証明するかを1対1で決め、1主張1場面に絞る。
   - 言っていることと見せるものが食い違っていないかを確かめる
     （例：「社内で動く」と言いながら外の AI を使っている所はないか）。食い違うなら、ノートに正直な答え方を書く。
   - デモは見せやすさを優先する：URL を開けば動く、ボタンを押すだけで見本のデータが入る、見本のデータはダウンロードもできる。
   - ボタン名・画面の順番は、実際の画面で確かめてからノートに書く。
5. **作る：決まりを飛ばさない**
   - アプリは要件定義を書いてから create-app の原則（オブジェクト主体など）で作る。急いでいても飛ばさない（飛ばすと作り直しになる）。
   - 公開中のデモを直すときは、通しで確かめてから差し替え、壊れたら戻す。会議の直前に間に合わなければ差し替えない。

### 能動の決まり

- 能動とは作業量ではなく、目的から逆算して自分で問いを立て、先に決めること。
- 自分で決めてよいこと（ノートの書き直し・社内の段取り・元に戻せる変更）は聞かずに進める。
  責任者に聞くのは、判断が本当に要ることだけにする。
- 頼まれていなくても、相手が当日必要になるもの（想定問答・持ち帰って再現するための台本など）は先に用意する。
- 振り返りで気づいたことは、言葉で答えて終わりにせず、その場でこのスキル（または該当するスキル）に抽象化して書き足すところまでを1セットにする。

## 準備物の形（必ずこの形）

| 準備物 | 中身 | 相手に渡すか |
|---|---|---|
| 相手に見せる pptx | 提案書そのもの。ノートは空 | 渡してよい |
| 話す内容入りの社内用 pptx | 同じスライドの各ノートに、話す内容を入れたもの。ファイル名に「話す内容入り（社内用）」 | **渡さない**（ノートに社内の注意も書くため） |

- **Word や Google ドキュメントの進行メモは作らない。** 話す内容は pptx のノートに入れる。
- 確認完了の基準は **「責任者がその pptx とノートで、そのまま喋れるか」**。
- 当日開くもの（デモアプリの URL など）は、ノートではなく**スライド本体**に入れる（相手にも見せる・押して開ける）。

### ノートの書き方（スライドごと）

```
【経過時間〜 担当者】
（話し言葉の文。責任者がそのまま口に出せる文にする）
――（その場で相手に聞く質問。選択肢・数字・名前で答えられる形）
〔画面操作の合図や、担当の切り替え〕
〔社内メモ：相手に言わないが気をつけること〕
```

- 表紙の次に「本会議の目的」のページを置き、**背景 → 目的 → アジェンダ**の型で言い切る（型は deck-composition の 0-3）。
  背景は状況の説明ではなく「なぜ今日この話か」の論理で、経緯（直前の場の結論と宿題）と予定（合意している予定の上の現在地）から目的を導く。導くのに必要な前提が欠けていれば、その前提を作ることを目的にする。
  進め方（アジェンダ）は目的から決める。
- 相手に決めてもらうことは、最後のスライドで質問の形にして、その場で答えを埋められるようにする。
- 相手に見せる版に、こちらの勝ち筋や相手の内情の分析は書かない（ノートの社内メモにだけ書く）。

## 対象

- 会社の秘書が毎朝カレンダーから取り込んだ、**営業管理表にあるお客さまとの打ち合わせ**（自分の商談も定例も）。
  どれが対象かは秘書が決める。`secretary_prep`（action=find）で出てこない予定は、秘書の対象外か、まだ取り込まれていない（今日入れた予定は翌朝に載る）。
- **予定がまだ無い会議も準備を始めてよい。** 日程が決まっていない・営業管理表にまだ載っていない相手との会議は、`secretary_prep`（action=create）で会議を起こす
  （`account`・`title`、決まっていれば `date`・`time`）。日程は未定でよく、カレンダーに予定が入ると毎朝の取り込みでその会議につながり、準備はそのまま引き継がれる。
  営業管理表に無い相手は、**本人に「リードとして登録してよいか」を確かめてから** `new_lead: true` を付ける。日程未定のあいだは前日17時の知らせは出ない。
- 見える範囲は秘書と同じ：営業担当・AIコンシェルジュ担当の案件だけ（全件を見る人は秘書の設定で決まる）。
- 秘書の無い会社では、責任者が主催し相手が社外の予定（予定名に「様」「さん」、または社外の参加者がいる）を対象にし、
  判定に迷う予定は勝手に入れず「対象にしますか？」と聞く。

## 段階（秘書の段階をそのまま使う）

| 秘書の段階 | 意味 | だれが進めるか |
|---|---|---|
| 未着手 | まだ何もない | — |
| AIの草案あり | 秘書が前回までの議事録から背景・目的・話す内容の草案を書いた（打ち合わせの数日前から自動） | 秘書 |
| 話す内容が決まった | 本日の目的を決め、pptx（相手に見せる版・話す内容入りの社内用）を置いた | 担当者（Claude が代わりに書いてよい） |
| 確認済み | 確認役（`{{members.owner}}`）が見て補足した | 確認役 |
| 確定 | 「これでいく」と明示的に了承された | 確認役（同席しない打ち合わせは担当者） |

- **Claude が自分で進めてよいのは「話す内容が決まった」まで。** 確認済み・確定は、確認役か担当者が会話の中で
  「これでいく」「OK」とはっきり言ったときだけ、その言葉を `said` に入れて進める（秘書の側でも、言葉が無ければ止まる）。
- 確認のあとに目的・話す内容を直すと、秘書が「話す内容が決まった」に戻す（確認のやり直し）。

## 状態と置き場所

新しい表もカレンダーの書き込みも作らない。**会社の秘書の「会議の準備」が正本**（管理画面の「会議」タブで、横が日付・縦がお客さまの一覧で見える）。

1. `secretary_prep`（action=find、`date`＝打ち合わせの日、`account`＝相手先）で打ち合わせを探し、`session_id` を得る。
2. `secretary_prep`（action=get）で、秘書の草案（背景・本日の目的・話す内容）と前回までの議事録の件名を見る。
3. 準備物を作って案件フォルダに置いたら、`secretary_prep`（action=save）で書く：
   - `background`：背景（「本会議の目的」のページの背景と同じ中身。経緯と予定から、なぜ今日この話か。状況の説明・共有済みの前提は書かない。2〜4文の文章で）
   - `purpose`：本日の目的（その場で合意したいこと。1〜2文）
   - `talk`：話す内容（番号付き 3〜6 行。社内用 pptx のノートの要約。相手に言わない注意は書いてよい：秘書の画面は社内だけ）
   - `materials`：`[{label:"相手に見せる版", url:<Drive のリンク>}, {label:"話す内容入り（社内用）", url:…}, {label:"デモ", url:…}]`
   - `stage`：`decided`
- 成果物は必ず `{{paths.projects}}` の案件フォルダの `01_提案・見積/YYYYMMDD/` に置く。チャットの中だけに置かない（秘書には開けるリンクで渡す）。
- Drive のコネクタで送れない大きさのファイルは、手元の同期フォルダ（device の道具）に書き込む。書き込めないときは、そのことを報告に書く。
- **カレンダーの予定の説明欄は書き換えない**（社外の参加者に通知が飛ぶ・置き場が二つになる）。会議の URL などは秘書がカレンダーから読む。

### 秘書が無い会社（`secretary_prep` が使えない・会社の台帳が無い）

カレンダーの予定の説明欄の先頭に、次の形で残す（既存の説明・会議 URL は消さない。社外の参加者がいる予定は変えずに報告だけ。
更新するときは通知を出さない設定にする）。

```
【準備】③確認待ち（M/D 更新）
確認の基準：「pptx＋ノート（話す内容）」で、そのまま喋れるか
置き場：<案件フォルダの日付フォルダへのリンク>
・<相手に見せる版のファイル名>
・<話す内容入り（社内用）のファイル名>
アプリ：<デモの URL（あれば）>
```

## 手順

1. 対象の日（指定が無ければ翌日）の打ち合わせを `secretary_prep`（find）で拾う。頼まれた会議が見つからなければ、create で起こしてから進める。
2. 打ち合わせごとに今の段階と中身を見る（get）。過去のチャット・案件フォルダの日付フォルダも見る。
3. 足りない段階を進める。
   - 準備物が無い → 上の「準備物を作る前の順番」で理解・骨子・具体・見せ方まで固め、骨子に責任者の了承を得てから、
     自社の営業スキル（proposal-package 等）の手順で pptx を作る。
   - ノートが無い → 背景と本日の目的を決め（「本会議の目的」のページ）、上の「ノートの書き方」で各スライドのノートを書き、社内用 pptx を作る。
   - 置いたら save で「話す内容が決まった」にする。
   - 確認待ち → 責任者に見せるのは**相手に出す完成物そのもの**（2つの pptx）。項目に分けた素材にしない。
     補足・修正をもらったら反映し、両方の pptx を作り直して置き直し、save し直す。
     「これでいく」と言われたら、その言葉を `said` に入れて確定（同席する打ち合わせは確認済み→確定）。
4. 一覧を返す。確定以外を目立たせる。

```
明日の打ち合わせ準備（秘書の「会議」タブと同じ）
・15:00 ○○様　話す内容が決まった — 見てほしいもの：話す内容入り（社内用）pptx
・11:00 ○○さん　AIの草案あり — pptx が未作成
```

5. 区切りで `secretary_report` にも報告する（準備物ができた・確定した）。
6. 準備の途中で責任者に引き戻された点（段の抜け・言葉のずれ・作り方の決まりの飛ばし）は、終わる前にこのスキルへ抽象化して書き足す。

## 知らせ

- 前日17時に、確定していない打ち合わせを、秘書が担当者と確認役へ LINE で知らせる（秘書の仕事。このスキルから送らない）。
- 秘書が無い会社だけ、予定タスク（日曜〜木曜の夜）で翌日分に上の手順を実行する。予定タスクの指示文には
  「このスキルを読み込んで従う」とだけ書き、決まりはこのスキル側に持つ。メールや LINE は送らない。

## やってはいけないこと

- 確認役・担当者の了承の言葉なしに確認済み・確定にする
- 骨子（タイトル／メッセージ）を固めて了承を得る前に、pptx やアプリを作る
- 相手が会話で使ったたとえを、そのまま提案の題名・名前にする
- デモを主張と切り離して、機能紹介の時間にする
- アプリを要件定義・create-app の原則を通さずに作る
- 話す内容を Word・Google ドキュメントの別ファイルにする（pptx のノートに入れる）
- 社内用 pptx（ノート入り）を相手に送る・共有する
- 成果物をチャットの中だけに置く
- 秘書がある会社で、準備の状態をカレンダーの説明欄に書く（置き場を二つにしない）
