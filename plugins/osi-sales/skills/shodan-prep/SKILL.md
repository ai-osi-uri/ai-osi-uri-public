# 商談準備Skill（初回チェックリスト連動）

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

自社の営業ワークフローで、商談の **質のばらつき** を潰すためのスキル。

期待値ズレ（酔鯨・FRESH ROOM の失敗）やセキュリティ失注（OK 社）の多くは、「初回で握るべき
ことを握れなかった」ことから起きる。このスキルは、その"握るべきこと"を **初回チェックリスト**
として一元管理し、商談前は準備、商談後は振り返りで使う。両者を 1 つのスキルにすることで、
回すたびにチェックリストが賢くなる設計になっている。

```
商談 前 ──▶ PREP モード：顧客リサーチ → 論点・期待値質問・チェックリストを準備
                 │
              （商談）
                 │
商談 後 ──▶ EXTRACT モード：Plaud文字起こし → 握れた/失敗を採点 → チェックリストを育てる
                 ▲                                                      │
                 └──────────────────────────────────────────────────────┘
                            （育ったチェックリストが次回の準備を強くする）
```

---

## 重要：このスキルの責任範囲

- **やる**：商談前の準備物（論点・期待値質問・チェックリスト）の生成／商談後のチェックリスト採点・更新。
- **やらない**：議事録 docx の生成（→ `meeting-minutes`）、提案書 pptx の生成（→ `initial-proposal`
  / `proposal-package`）、リード起票（→ `new-lead-registration`）。
- 知識の本体は `references/initial-checklist.md`。**毎回これを読み込んでから**論点生成・採点を行う。

---

## モード判定

ユーザーの発話から、どちらのモードかを最初に判定する。

| 合図 | モード |
|---|---|
| 「準備して」「論点出して」「何を握ればいい」「期待値質問」「明日の商談」（＝これから商談） | **PREP** |
| 「終わった」「文字起こし」「振り返り」「握れた/失敗を抽出」「チェックリスト更新」（＝商談済み） | **EXTRACT** |
| 「チェックリスト見せて」「今の項目は？」 | **VIEW**（チェックリストをそのまま提示） |

迷う場合は `AskUserQuestion` で「これからの商談の準備ですか／終わった商談の振り返りですか」を 1 問だけ確認。

## PREP モード（商談 *前* の準備）

### Step P1: 対象リードの特定

ユーザーの発話から対象を特定する（meeting-minutes と同じロジック）：
- 案件ID（「案件ID 122」）／企業名（「セーフティ&ベル」）

案件情報の正本は **`{{ledgers.sales}}`**（タブ `取引先管理`、ヘッダは5行目）。
**ディレクトリ経由（openpyxl）で読み書きする。Google Sheets API・GCPサービスアカウントは使わない。**
台帳の触り方・不変条件・列の一覧は
**`../new-lead-registration/references/ledger-access.md` を必ず読むこと**（osi-sales 共通の正本）。

```bash
L=../new-lead-registration/scripts/ledger.py
python3 $L columns                       # 列名・ステータス値・パス
python3 $L find --company "{企業名}"      # 表記ゆれを吸収して行を引く
python3 $L find --case-id {案件ID3桁}
```
（ヘッダは5行目、データは6行目以降。組織固有値は `config/osi-sales-settings.md` を参照）。

```
python3 $L find --company "{企業名}"    # 表記ゆれ（株式会社・促音・記号）は吸収される
python3 $L find --case-id 122           # 案件IDが分かっているならこちらが確実
```

- 候補が複数 → `AskUserQuestion` で選ばせる（1社で複数案件が走ることがある）。
- ヒットしたら `ledger.py read` で該当行を読み、**準備に効く列**を押さえる：

  | 列 | 内容 | 準備での使いどころ |
  |---|---|---|
  | C | メモ（顧客課題／アクション） | 案件背景・これまでの経緯・前回の宿題 |
  | D | 主担当 | 「{主担当メンバー}からのご紹介」の文脈 |
  | W | ステータス | 初回か再訪かの判定（`リード` なら初回想定） |
  | AA | 最終接触日 | 前回接触からの経過。空きが長ければ再導入の一言を用意 |

  ステータス値は `リード` / `商談中` / `金額提示済み` / `契約済み` / `デリバリー中` / `失注` の6つ。

- **過去の議事録**は Drive の案件フォルダ
  `{{paths.projects}}/{{paths.project_naming}}/03_制作・成果物/` にある議事録 docx を参照する
  （`最終接触日` 列で、直近の接触があるかどうかの当たりを付けられる）。
  既に商談歴があるなら、それを踏まえた準備にする。
- 台帳に未登録でも PREP は実行可能（新規アプローチ前提）。その場合は「まだ営業管理表に未登録です。
  必要なら後で `new-lead-registration` で起票できます」と一言添える。

### Step P2: 顧客リサーチ

`WebSearch` / `mcp__workspace__web_fetch` / `Agent` ツールで企業を調べる。観点は initial-proposal と
共通（事業概要・組織規模・経営理念・最近の動向・業界特性・DX 状況・地域特性）。
- 採用ページ＝組織課題の宝庫。IR・中期経営計画があれば経営課題が明確。
- **業種を特定**しておく（後で `initial-checklist.md` 末尾の「業種別の追加論点」を上乗せするため）。
- 既に Drive の `03_制作・成果物/` に過去議事録があれば、Web より優先してそこから論点を拾う
  （生の声が一番強い）。営業管理表の `顧客課題メモ` 列も同様に優先する。

### Step P3: チェックリストを顧客別に"翻訳"する

`references/initial-checklist.md` を読み込み、各項目を **この顧客の言葉・文脈** に翻訳する。
汎用の質問をそのまま並べない。リサーチで分かった事業・課題・業種を質問に織り込む。

- 例（汎用）「最初に取り組むテーマを 2〜3 個に絞ると？」
- 例（翻訳後・多店舗飲食）「全店舗のシフト作成と、本部への日報集計。最初に楽にするならどちらからですか？」

業種が金融・医療・飲食・士業なら、末尾「業種別の追加論点」を必ず上乗せする。

### Step P4: 準備シートを出力

`assets/prep-sheet-template.md` の形式で、商談準備シートをチャットに提示する（必要なら md ファイル化）。
構成：
1. **この商談のゴール**（1 行。例「対象テーマを 2〜3 個に握り、次回デモ日を確定する」）
2. **顧客サマリ**（リサーチ要点 3〜5 点）
3. **この顧客で特に外せない論点**（チェックリストから重要度上位を 3〜5 個、翻訳済みで）
4. **期待値質問リスト**（そのまま口に出せる質問文。カテゴリ A〜F 順、顧客別に翻訳済み）
5. **想定される懸念と切り返し**（特にセキュリティ C。OK 社型の失注を先回りで潰す）
6. **初回チェックリスト（当日チェック用）**（◎△×－ を付けられる素の一覧）

過去議事録がある再訪商談の場合は、冒頭に「前回の宿題・積み残し」を必ず置く。

### Step P5: 任意の保存

ユーザーが希望すれば、準備シートを Drive に置く：
```
Drive/{{paths.projects}}/{{paths.project_naming}}/01_提案・見積/  もしくは 05_受領資料/
ファイル名：{YYYYMMDD}_商談準備_{企業名}.md
```
（保存するかは聞いてから。準備はチャット提示だけで完結することも多い。）

## EXTRACT モード（商談 *後* の振り返り・チェックリスト育成）

ここが「過去議事録から握れた/失敗を AI 抽出」の実体。最初の 3〜5 件はこのモードで投入し、v0 を育てる。

### Step E1: 文字起こしの取得
**まず Plaud MCP で直接取得**：コネクタ（`list_files` / `get_transcript` 等）が利用可能なら、
企業名・日付から `list_files` で録音を特定し `get_transcript` で全文を取得する（貼り付け不要。
401 なら `login` で再サインイン）。無ければフォールバック：チャット貼り付け → Gmail 転送メール
検索 → Drive ファイル名指定（`read_file_content`）。空なら `AskUserQuestion` で促す。
取り込みの作法は meeting-minutes の `references/transcript-parsing.md`（共通・正本）に従う。
- どの案件・いつの商談か（ID / 企業名 / 日付）も合わせて確認。
- それが **初回商談かどうか** を確認（初回チェックリストは"初回で握るべきこと"が対象）。

### Step E2: チェックリストで採点
`references/initial-checklist.md` の全項目（A1〜F2＋業種別）について、文字起こしを根拠に採点する。

各項目につき：
```
- 項目ID（例 A1）：◎ / △ / × / －
  根拠：「（文字起こしからの該当発言・場面を短く引用）」
  ×・△ の理由：時間切れ / 相手が答えを持たない / こちらが切り出せなかった / 等
```
採点は `extraction-guide.md` の判定基準に従う。憶測で ◎ を付けない。発言の裏付けがない項目は △ か、
明確に飛ばしたなら × にする。

### Step E3: 抽出サマリの提示
- **握れた（◎）**：N 項目
- **取りこぼし（×／△）**：M 項目（← ここが学び。なぜ握れなかったか付き）
- **チェックリストに無かった新しい論点**：この商談で出た、既存項目に当てはまらない"握るべきだった
  こと"があれば候補として提案（業種特性・相手固有の論点など）。これが v0→v1 の主な追加源。

### Step E4: チェックリストの更新提案（ユーザー確認のうえ反映）
`AskUserQuestion` で「以下をチェックリストに反映しますか？」と確認してから `references/
initial-checklist.md` を編集する。更新の型は `extraction-guide.md` を参照。**勝手に上書きしない**。
- 新項目の追加（新カテゴリ or 既存カテゴリへ）
- 既存項目の「防ぐ失敗」「期待値質問例」への実例追記（実際の失敗・刺さった質問を反映）
- 業種別論点への追記（業種タグ付き）

更新したら冒頭の版表記を上げる（v0 → v1…）。複数件をまとめて投入する場合は、全件採点してから
共通する取りこぼしパターンを束ねて反映すると、過学習（1 件に引っ張られすぎ）を避けられる。

### Step E5: 任意の連携
- 商談の議事録そのものが欲しい → `meeting-minutes` を案内（このスキルは作らない）。
- 採点で出た次アクションを営業管理表に残したい → ユーザー確認のうえ、
  `ledger.py update`(case_id="{案件ID3桁}", updates={"メモ": "{既存メモ} / {次アクション}"}) で
  `顧客課題メモ` 列に**追記**する（上書きしない）。`ステータス` 列は本スキルでは動かさない。

## VIEW モード
`references/initial-checklist.md` の現在の項目を、カテゴリ別に簡潔に提示する。版表記も添える。

---

## 設計思想（なぜこの形か）

- **準備と振り返りを 1 スキルに**：別々だとチェックリストが更新されず陳腐化する。同じファイルを
  読み書きする 1 スキルにすることで「使うほど賢くなる」ループが回る。これが現状診断 B2 の狙い。
- **チェックリストは"採点軸"であり"質問の素"でもある**：同じ項目が、前は質問生成に、後は採点に使える。
- **小さく始めて育てる**：v0 は知識ベースの初版。完璧を待たず、3〜5 件回して精度を上げる前提。
- **過学習を避ける**：1 件の特殊事情で項目を増やしすぎない。複数件で繰り返し出た取りこぼしを優先して反映する。

---

## やってはいけないこと
- 議事録 docx を作る（→ meeting-minutes）／提案書 pptx を作る（→ initial-proposal）。役割が違う。
- 文字起こしの裏付けなしに ◎ を付ける（振り返りの価値が消える）。
- `references/initial-checklist.md` をユーザー確認なしに書き換える。
- 1 件の商談に引っ張られてチェックリストを過剰に肥大化させる。
- 汎用の質問文をそのまま並べる（必ず顧客別に翻訳する）。
