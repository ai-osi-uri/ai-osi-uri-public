# 抽出ガイド：Plaud 文字起こし → 握れた/失敗の採点とチェックリスト更新

EXTRACT モードで使う。`initial-checklist.md` を採点軸に、文字起こしから「初回で握れた／失敗した」を
判定し、その学びをチェックリストに還元するための基準書。

---

## 1. 採点の基準（◎ / △ / × / －）

判定は **文字起こしの中の発言・場面** を根拠にする。読み取れないものは憶測で埋めない。

| 記号 | 意味 | 付ける条件 |
|---|---|---|
| ◎ 握れた | 相手と合意・確認が取れた | 該当論点に触れ、**相手の同意・回答・合意**が文字起こしに現れている |
| △ 一部 | 触れたが詰め切れず | 話題には出たが、結論・合意まで至っていない／曖昧なまま流れた |
| × 失敗 | 握るべきを握れず | 握るべき論点だったのに **触れていない**、または触れたが明確にすれ違った／後で火種化しうる |
| － 対象外 | そもそも論点でない | その商談の性質上、当該項目が不要（例：技術的な意見交換だけの回） |

### 迷ったときの原則
- 「相手が"はい/こうです"と返した記録があるか」で ◎ と △ を分ける。こちらが一方的に説明しただけなら △。
- 沈黙・スルーは ×（握れていない）。「次回話す」と先送り合意があれば △。
- Plaud 特有のクセ（句読点が少ない・話者ラベルが曖昧・聞き間違い）に注意。数字や固有名は怪しければ
  「(原文ママ)」と注記し、採点の根拠には弱めに扱う。

---

## 2. 採点の出力フォーマット

```
## 採点結果（{企業名} / {商談日} / 初回 or 再訪）

### カテゴリA 期待値・スコープ
- A1 まず取り組むテーマを2〜3個に特定：◎
  根拠：「まずは提案書づくりと議事録、この2つからで」（相手・中盤）
- A2 できる/できないの線引き：△
  根拠：AIの限界に触れたが相手の同意は曖昧。理由＝こちらの説明で終わり、確認を取らなかった
- A3 成果の時間軸：×
  理由：時間切れで触れられず。次回への積み残し
...（全カテゴリ）

### この商談で出た「チェックリストに無い論点」
- （例）相手が「現場が触れるか不安」と複数回。"現場の AI リテラシー懸念"は既存項目に無い → 追加候補
```

---

## 3. サマリの出し方

採点後、必ず次の 3 つを短く出す：
1. **握れた数 / 全項目数**（例：6 / 18）
2. **取りこぼし（×・△）の一覧**と、その理由の傾向（時間切れが多い／セキュリティを毎回飛ばす、等）
3. **新論点の候補**（チェックリストに無かったが"握るべきだった"こと）

この「取りこぼしの傾向」と「新論点」が、チェックリストを育てる燃料。

---

## 4. チェックリスト更新の型（必ずユーザー確認のうえ反映）

`initial-checklist.md` を編集する際の決まった型。`AskUserQuestion` で承認を得てから書く。

### 型① 既存項目に"実例"を足す（最頻・推奨）
既存項目の「防ぐ失敗」や「期待値質問例」に、実際に起きた失敗・実際に刺さった質問を追記する。
新項目を増やすより、既存を厚くするほうが過学習を避けられる。

```
### A3. 成果が出るまでの時間軸を合意したか
- 防ぐ失敗：…（既存）。【実例：FRESH ROOM では初月の到達点を握らず「思ったほどでは」と早期解約】
- 期待値質問例：
  - …（既存）
  - 【追加・刺さった質問】「1ヶ月後この会議が"あって良かった"と思える状態を一緒に決めませんか？」
```

### 型② 新項目を追加する（複数件で繰り返し出たときだけ）
1 件だけで出た論点は「観察」に留め、2 件以上で再出したら正式項目に昇格させる。

```
### A6. 現場メンバーの AI リテラシー不安を受け止めたか   ← 新規
- 握れた状態：現場が触れるか不安、に対して伴走の仕方（最初は一緒に画面共有で）を示し相手が安心している。
- 防ぐ失敗：意思決定者は乗り気でも現場が使わず形骸化。
- 期待値質問例：「現場の方が"これなら触れそう"と思える入り方を一緒に設計しませんか？」
- 初出：{企業名}({日付}) / 再出：{企業名}({日付})
```

### 型③ 業種別論点に足す
業種タグを付けて末尾「業種別の追加論点」に追記。

```
- **製造（例：◯◯製作所）**：図面・技術情報の社外持ち出し規定、現場のITリテラシー差、多能工化との接続。
```

### 更新後
- 冒頭の版表記を上げる（v0 → v1）。
- 何を・なぜ足したかを 1 行で変更履歴的に残すと、後で振り返りやすい（任意で末尾に「## 変更履歴」）。

---

## 5. 複数件をまとめて投入するときの進め方（v0 を育てる初回バッチ）

代表 3〜5 件（成功＋失敗を混ぜる）を投入する想定。おすすめ手順：
1. **全件を先に採点**（1 件ずつ §2 の形式で）。この時点ではチェックリストを書き換えない。
2. **横断で集計**：どの項目が複数件で × だったか／どの新論点が複数件で出たかを束ねる。
3. **束ねた学びだけを反映**：1 件特有の事情ではなく、繰り返し出たパターンを優先して §4 の型で反映。
4. 成功案件（契約に至った）で ◎ が多い項目は「効いている握り」。その項目の期待値質問例を、
   実際に使われた言い回しで強化する（勝ち筋の言語化）。

これで「1 件に引っ張られすぎる過学習」を避けつつ、v0 → v1 を確実に前進させられる。
