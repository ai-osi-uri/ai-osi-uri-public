# contract-docusign-send セットアップ

**既定の経路なら、設定はほぼ要りません。**Claude のコネクタ一覧から
**公式の DocuSign コネクタをボタン1つで接続する**だけです。Integration Key も
RSA 秘密鍵も要りません（DocuSign 自身が公開しているアプリのため）。

契約書そのものは、**人が DocuSign の画面にドラッグして下書きを作ります。**
公式コネクタは手元のファイルを受け取れないためで、これは仕様です（2026-08-20 に確認）。
人はどのみち送信ボタンを押すために DocuSign を開くので、増える手間はドラッグ1回です。

---

## 1. 公式 DocuSign コネクタを接続する（各自・1回）

Claude の設定 →［コネクタ］から DocuSign を探して接続し、DocuSign にログインして許可します。
接続できたら、チャットで「DocuSign の利用者情報を見せて」と言うと確認できます。

## 2. 契約書を送るとき

1. Claude が内容チェックと署名者の確認をする
2. **人が DocuSign を開き、［今すぐ開始］から契約書を追加して、下書きのまま閉じる**
3. Claude が下書きを拾って、署名者・署名欄・件名・CC を整える
4. **人が内容を確認して送信する**（Claude は送信しません）

---

## 3.（任意・上級者向け）ファイルの受け渡しまで自動にする

自前コネクタ `ai-osi-uri-finance` の `ds_create_envelope` は、台帳フォルダのファイルを
base64 で直接送るので、手元のファイルをそのまま封筒にできます。**ただし DocuSign の
Integration Key が必要**です。

**本番アカウントでは Key を発行できません。**DocuSign の画面に「実稼働環境では作成できません。
開発者アカウントで作成し Go-Live を経て移行してください」と明記されています。つまり、

1. 開発者アカウントを作る（無料・即時）
2. アプリを登録する（下の「アプリ登録で外すと後で効いてくる選択」を見てから）
3. リダイレクト URI に **`ds_setup_info` が出すものを全部**登録する
4. Go-Live を申請して本番へ移す（2025年に「API20回」要件は撤廃済み）
5. コンソールの［DocuSign］画面で Key を保存し、「つなぐ」を押す

**ここまで通す価値があるかは、契約の件数次第です。**送信は結局どのみち人が押すので、
自動化で浮くのは「ドラッグ1回」だけです。件数が少ないうちは 1〜2 の運用で足ります。

### アプリ登録で外すと後で効いてくる選択

どれも登録画面では小さな選択肢に見えますが、間違えると運用に入ってから効いてきます。

- **App Type は「Native OS Application」。Single-Page Web Application を選ばない。**
  SPA だと更新トークンが24時間で切れ、毎日つなぎ直すことになります。Native なら30日です
- **client secret は作らない。**認可コード + PKCE で通すので不要で、
  作れば「配布物に秘密を持たせない」という前提が崩れます
- **リダイレクト URI は1本では足りない。**コネクタは接続のたびに空いているポートを
  実行時に選ぶため、候補を全部登録しておく必要があります。**候補は増える可能性があるので、
  手で数えず `ds_setup_info` が出したものをそのまま登録してください**
- **Integration Key は秘密ではありません**（OAuth の公開 client_id）。
  設定ファイルやリポジトリに置いても差し支えありません。秘密なのは refresh token の方です

### Key を誰が持つか

**利用者ひとりひとりに Key を作らせない**設計です。DocuSign 自身も ISV 向けに
「顧客に integration key を作らせるな」と案内しています。したがって、

- 配布されたコネクタに **既定の Key が入っていれば、利用者の設定は不要**です
- 自組織の DocuSign アカウントで独自に運用したい場合だけ、`ds_set_integration_key`
  （コンソールの［DocuSign］画面）で上書きします。**既定値より優先されます**

**この手順書に特定の Key や、特定の組織の申請状況は書きません。**古くなりますし、
配布先ごとに違うためです。自組織の Key と申請状況は、経理設定
（`osi-finance-settings.md`）と台帳側の共有設定に記録してください。

---

## 4. 接続が切れたとき（自前コネクタを使っている場合）

接続は **30日以上まったく使わないと切れます**（使うたびに30日先へ延びるので、
月に1回でも送っていれば切れません）。切れたら同じことをもう一度やるだけです。

「DocuSign の接続が切れています」と出たら → 「DocuSign につないで」と言って許可を押す。

---

## 補足

### 別のアカウントでつなぎ直したい

「DocuSign の接続を解除して」（`ds_disconnect`）→ もう一度「DocuSign につないで」。

### 送信者は誰になるか

**許可を押した本人**です。DocuSign 上の送信履歴にもその人が残ります。
経理担当以外がつなぐ必要はありません。

## 変更の経緯

> **2026-08-20: 既定の経路を「公式 DocuSign コネクタ＋人がアップロード」に戻しました。**
>
> 手元のファイルを自動で DocuSign に載せる道を、実地で全部当たって塞がっていることを確認しました。
> 公式コネクタは `remoteUrl` かテンプレートしか受けない（**公開URLでの封筒作成は成功を確認**、
> 非公開 Drive は `NO_DOCUMENT_RECEIVED`）。Claude in Chrome の代行アップロードは
> `file_upload` がこの環境で使えない。Drive コネクタは「リンクを知っている全員」を作れない。
> 本番 DocuSign アカウントでは Integration Key を発行できない。
>
> **一方で、ファイル以外は公式コネクタで全部できます**（受信者・署名欄・件名・下書き保持・
> 後からの修正・送信・リマインド・取り消し）。そして元々「送信は人が押す」原則なので、
> 人が DocuSign を開くことは変わりません。**増える手間はドラッグ1回**という結論です。
>
> 自前コネクタ（base64 直送）は消していません。開発者アカウントと Go-Live を通した組織は
> そちらが最短です。

> **2026-08-18: JWT 方式から認可コード方式（PKCE）に変えました。**
>
> 以前は利用者ごとに DocuSign でアプリを登録し、RSA キーペアを生成し、秘密鍵の PEM 全文を
> 設定欄に貼る必要がありました。「トークンが失効しない」ことを理由に選んだ方式でしたが、
> **重すぎて社内の誰も設定を終えられず、2026-08 時点で一度も使われていませんでした。**
> 失効しない代わりに誰も始められないのでは、失効するより悪いという判断です。
>
> 旧方式の設定が入っている環境では、引き続き JWT で動きます（手を止めないため）。
>
> **2026-08-17: AWS（S3 ステージング）が不要になりました。**契約書は自前コネクタが読んで
> base64 で DocuSign に直接送るため、一時ファイルも一時公開URLも作りません。
> 旧手順は `_旧版_S3方式_20260817/` にあります。
