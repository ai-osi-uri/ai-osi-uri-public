# contract-send（契約書チェック → AI電子契約で送付）

> **組織固有値はプロファイルから読む。** 本文の `{{paths.*}}` `{{ledgers.*}}` `{{company.*}}` `{{members.*}}` は、連結フォルダ直下の `osi-profile.md`（雛形: `config/osi-profile.example.md`）の値に置き換えて解釈する。無ければ会社名・案件フォルダ・台帳の有無・使うコネクタを質問して先に作る。値をここに直書きしない。

契約書を「丸腰で送らない」ためのバックオフィス・ゲート。渡された契約書を
**人がレビューしやすい形に整理 → 承認 → 署名者確認 → AI電子契約の下書き → 宛先と書類を見せて OK → 送付**まで一気通貫で行う。

契約は重要文書なので、**誤送信を絶対に起こさない設計**を最優先する。

## 電子署名の道具は AI電子契約（2026-11-02〜）

- 自社から送る電子契約は **AI電子契約（esign_*）だけ**を使う。**DocuSign では新しく送らない**（移行した）。
  人が「DocuSign で送って」と言っても、AI電子契約で送ることを一言伝えて進める。
- DocuSign で**送付中**の契約は、DocuSign の中で最後まで終わらせてよい（`ds_get_envelope` で状態を見る・`ds_save_documents` で締結済みを置き場に戻す）。新しい封筒は作らない。
- 先方の電子契約（DocuSign・クラウドサインなど）で**届いた**契約に署名するのは、先方の画面で人が行う（このスキルは内容チェックだけ）。
- AI電子契約の画面は `https://sign.ai-osi-uri.info`（議事録の ToDo の「契約へ進む」からも入れる）。人が画面で送るときも、このスキルのチェック（Step 2）を先に通してよい。

## 役割と非役割

- やる：契約書の取り込み → 4観点チェックの提示 → 署名者抽出・確認 → AI電子契約の下書き → 宛先と書類を見せて OK → 送付 → 送付の記録。
- やらない：契約書の新規作成（= `osi-finance-contract-draft`・`nda-creation`）／受領契約の請求スケジュール化（= `osi-finance-contract-intake`）／法的助言（弁護士ではない旨を添える）。

## 最重要ルール：OK をもらう前に送らない

- `esign_create` は**下書き**を作るだけで、相手には届かない。
- 送る前に、**件名・宛先（全員の名前とメール）・書類のファイル名・署名の順番・期限**をそのまま本人に見せ、はっきり「OK」「送って」をもらう。
- `esign_send` には、見せた宛先（`expect_emails`）と書類のファイル名（`expect_files`）を必ず渡す。契約の中身と1つでも違えば道具が止める。
- 1 回の OK で送るのは 1 通。直したら、直した内容をもう一度見せる。
- 宛先メールは人が確認・確定する（推測で送らない）。試すときは相手先ではなく自分宛を使う。
- 取り消し（`esign_cancel`）も元に戻せない。本人の OK をもらってから `confirm:true` で呼ぶ。

## 前提

- まず `esign_status` を呼ぶ。`enabled:false` なら、運営に「管理コンソールの会社 →『電子契約』でオンにしてもらう」よう伝えて止まる。
- 書類は PDF。docx は先に PDF にする（下の Step 1）。1 ファイル 15MB まで・10 個まで。
- 書類は会社の書類の置き場に `files_put` で上げ、`esign_create` の `files` に相対パスで渡す（小さいものは `documents` に base64 でもよい）。

## ワークフロー

### Step 0. 参照情報（自社情報）の確認 — 初回必須・汎用配布対応

このスキルは複数の組織・担当者に配布される前提。**契約処理に入る前に、必ず `references/issuer-info.md` の「設定状態」を確認する。**

- 「設定状態」が `未設定`、空欄、またはプレースホルダのまま →
  **そこで停止**し、利用者に自社情報（正式法人名・法人番号・本店所在地・代表者・電話・インボイス番号）を確認する。
  可能なら法人番号公表サイト（https://www.houjin-bangou.nta.go.jp/）または gBizINFO（https://info.gbiz.go.jp/）で
  **法人番号と社名・住所を照合**し、一致を確認したうえで `issuer-info.md` を更新（`設定状態: 確認済み（YYYY-MM-DD / 出典）`）してから先へ進む。
- 「設定状態」が `確認済み` → Step 1 へ。契約書の自社欄と issuer-info が食い違う場合は「要確認」で人に提示する。

> 目的：配布先が初期設定なしで使い始め、他社名のまま契約書を送ってしまう事故を防ぐ。社名は表記ゆれ（全角/半角・スペース・ハイフン）に特に注意。

### Step 1. 契約書の取り込み

- 形式が docx の場合、**チェック用のテキスト**を抽出し、**送付用の PDF**を作る。
  ```bash
  pandoc "<契約書.docx>" -t plain                                         # チェック用
  soffice --headless --convert-to pdf --outdir <作業ディレクトリ> "<契約書.docx>"   # 送付用
  ```
- すでに PDF ならそのまま使う。PDF にできない環境では、人に PDF にしてもらう（AI電子契約は PDF だけを受ける）。

### Step 2. 内容チェック（4観点）→ 人レビュー提示

`references/contract-checklist.md` のチェックリストに沿って読み取り、**表形式で論点を提示**する。

1. **基本項目の整合**：当事者（甲/乙）の正式名称・住所・代表者、自社情報（`references/issuer-info.md` と一致するか）、契約日、署名欄の有無。
2. **金額・期間・条件**：報酬額・契約期間・更新条件・支払条件などの数値と抜け漏れ。
3. **リスク条項**：責任制限・損害賠償・解約・知財帰属・秘密保持・準拠法/管轄など、自社に不利な点。
4. **雛形との差分**：自社標準雛形と比較し、変更・追加・削除箇所。**雛形は台帳の「雛形マスタ」タブから引く**（パスを直書きしない）。区分で NDA／受注用／発注用を選ぶ。

> 出力は「問題なし／要確認／要修正」のラベル付きで簡潔に。Claude は弁護士ではないため、
> リスク指摘は「確認を促す」トーンに留め、最終判断は人に委ねる。

### Step 3. 署名者の抽出と確認（必須ゲート）

- 契約書末尾の署名欄（甲・乙ブロック）から**署名者の氏名・会社名・肩書**を抽出する。自社の名義・代表者は `references/issuer-info.md` から取る。
- **自社も署名するなら、自社の署名者も署名する人に入れる**（AI電子契約は「署名する人」全員がそろうと締結する）。
- **メールアドレスは契約書に無い**ため、`AskUserQuestion` で各署名者のメールを確認する（営業管理表があれば候補提示）。
- 送り方を確かめる：全員に同時（既定）か、上から順番に（例：相手 → 自社）。期限（既定 14 日）。

### Step 3.5. 送付方向の選択（必須）

`AskUserQuestion` で送付方向を確認する。

- **自社から送る**：Step 4 へ。
- **先方が送る**（先方の電子契約で届く）：自社は送り手にならない。**下書きは作らない。**
  - Step 2 のチェック結果と Step 3 の署名者情報を整理して人に渡す。必要なら「先方に送付を依頼する文面」の下書きを作り、見せてから送る（メールは本人の OK をもらってから）。
  - 届いた契約への署名は、先方の画面で人が行う。締結後の取り込みは `osi-finance-contract-intake`。Step 6 へ。

### Step 4. 下書きを作る（自社から送る場合）

1. 送付用の PDF を `files_put` で置き場に上げる（例 `03.契約書/送付前/<相手先>_<契約名>_<YYYYMMDD>.pdf`）。`files_list` で相対パスを確かめる。
   業務委託契約書と NDA のように 2 通を一緒に送るときは、両方を上げて `files` に並べる（1 通の依頼で両方に署名してもらえる）。
2. `esign_create` を呼ぶ：
   - `title`：件名（相手のメールの件名にも出る）。例 `<契約名>（<自社名>）`。既定の名前やファイル名のままにしない。
   - `files`：上げた PDF の相対パス。
   - `signers`：名前・メール・会社。順番に送るなら `order`。署名欄を本文の決まった場所に押すなら `field`（`doc`=何番目の書類〈0 始まり〉・`page`=ページ〈1 始まり〉・`x`・`y`=ページの左上を 0、右下を 1 とした割合で、署名欄の左上の位置）。省略すると、締結の PDF の最後に足す「署名欄」のページにまとめて押す（本文に重ねない）。
   - `message`・`signing_order`・`expires_in_days`・`counterparty`・`amount`・`contract_date`（相手・金額・契約日は締結後に探す手がかり。電子帳簿保存法の検索の決まり）。
   - 議事録の ToDo から来た契約なら `meeting_id`・`todo_id` を渡す（締結すると、その ToDo が完了になる）。
   - `cc`：署名はしないが、締結したら締結済みの PDF を受け取る人（先方の担当者・自社の経理など。署名する人と同じアドレスは入れない）。
   - `remind_every_days`：署名がまだの人に何日ごとに自動で催促するか（朝 9 時台）。本人に聞いて、特に指定が無ければ 3。
3. 返ってきた契約 ID・宛先・書類を控える。

### Step 5. 見せて OK をもらい、送る

1. 次をそのまま本人に見せる：件名／宛先（順番・名前・会社・メール）／CC／書類のファイル名／メッセージ／署名の期限／自動の催促の間隔。
2. 本人の「OK」「送って」をもらったら、`esign_send(id, expect_emails, expect_files)` を呼ぶ。
3. 届けられなかったメールがあれば（返事の `mails[].sent:false`）、その宛先を本人に伝える。
4. 送ったあとは、件名・宛先・書類・契約 ID と、契約の画面の URL（`https://sign.ai-osi-uri.info/<契約 ID>`）を報告する。

送ったあと：状態は `esign_get`・`esign_list`、未署名の人への催促は `esign_remind`（同じ人へは 24 時間に 1 回まで。期限切れなら 7 日延びる）、締結済み PDF は `esign_download`（10 分だけ開けるリンク）。
- 宛先のメールの打ち間違い：`esign_update_signer`（誰を・どう直すかを本人に見せ、OK のあと `confirm:true`。前のリンクは使えなくなり、新しいアドレスに依頼が届く）。取り消して作り直さない。
- CC の入れ替え：`esign_set_cc`。自動の催促の間隔の変更・停止：`esign_set_reminder`（0 で止める）。

### Step 6. 記録

- 締結済みの PDF は、締結したときに自動で `03.契約書/締結済/` に置かれる（`esign_get` の `company_path`）。手で移さなくてよい。
- 契約の台帳（契約マスタ）に載せる・請求予定に展開するのは `osi-finance-contract-intake` に渡す（相手・金額・期間・契約 ID を添える）。
- 格納先の考え方は `references/storage-and-naming.md`。

### Step 7. 出力サマリ

1. チェック結果サマリ（問題なし/要確認/要修正の件数と主な論点）
2. 送付した件名・宛先・書類・契約 ID（または「下書きを作成済み、OK 待ち」）
3. 契約の画面の URL
4. 注意点（Claude は弁護士ではない旨、リスク指摘は要確認レベル）

## 留意

- **誤送信防止が最優先。** 宛先と書類を見せて OK をもらうまで送らない。宛先メールは人に確認させる。
- 金額・当事者・期間が契約書から判然としない場合は推測せず人に確認する。
- 署名の証明書は、いまは自社で発行したもの（相手の Acrobat では「信頼されていない署名者」と出る）。相手に聞かれたら「改ざんされていないことは確認できる。認証局の証明書への切り替えを予定している」と伝える。
- 機密保持契約（NDA）・業務委託・レベニューシェア等、種別に応じて雛形の比較対象を変える。
- このスキルはプラグインのソースであり、案件情報をここに保存しない。成果物は outputs か会社の書類の置き場へ。
- **配布物なので、自社名・代表者名・フォルダパス・口座などの組織固有値をこのファイルに書かない。**
