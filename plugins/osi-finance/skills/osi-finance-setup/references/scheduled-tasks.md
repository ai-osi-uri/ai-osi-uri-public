# 自動実行（スケジュールタスク）の定義

**これが7本の正本です。**登録・更新するときは、ここの `cron` と `prompt` をそのまま使ってください。

---

## 大前提：スケジュールはプラグインでは配れません

プラグインが同梱できるのは `skills` / `agents` / `hooks` / `mcpServers` / `lspServers` /
`outputStyles` / `userConfig` だけで、**`schedules` や `cron` に相当するフィールドは存在しません。**
`hooks` にも**時刻で発火するイベントはありません**（すべて「セッションが始まった」
「ツールを使った」などの出来事に反応する仕組み）。

スケジュールタスクは **ユーザー単位・マシン単位** の設定で、
`~/Documents/Claude/Scheduled/{taskId}/SKILL.md` に置かれます。
**そのフォルダにファイルを置いても登録はされません**——cron はそのファイルの中に無く、
アプリ側の管理領域にあります。登録は `create_scheduled_task` を通す必要があります。

したがって **配布できるのは「定義」だけで、「登録」は各自が実行します。**
このファイルがその定義です。

---

## 設計の鉄則：プロンプトに手順を書かない

**各タスクのプロンプトは「◯◯スキルに従って実行する」＋そのタスク固有の絞り込み、だけにする。**
手順・フォルダパス・台帳のID・勘定科目の判断・自社情報は、**一切書かない。**

### なぜか（実際に起きた事故）

2026-08-12 にフォルダ構成を移行したところ、**スケジュール4本が静かに壊れました。**

- 2本は消えたフォルダ（`31.請求管理/…`）を見に行くよう書かれていた
- 1本は「台帳は Google スプレッドシートが正本」として古いスプレッドシートIDを渡していた
  （台帳はローカルの xlsx に変わっていた）
- 1本は前払費用の振替金額が特定月ぶんだけ直書きされ、期限切れになっていた
- 3本は古いスキル名（`keiri-*`）を呼んでいた

**リポジトリを更新しても直りません。**スケジュールはリポジトリの外にあり、
プラグインを配り直しても各自のマシンの古い定義は残ります。
**発見は 2026-08-17 で、移行から5日間、誰も気づいていませんでした。**

一方、スキルに委譲していたタスクは無傷でした。**スキルを直せば追随するからです。**

### 判定基準

プロンプトを書き終えたら、次を自問してください。

- フォルダ名・パスが書かれていないか
- 台帳のID・シート名以外の場所情報が書かれていないか
- 自社名・登録番号・口座・代表者名が書かれていないか
- スキル側に同じことが書かれていないか（**重複は片方だけ古くなる**）

ひとつでも当てはまるなら、それはスキル側か設定ファイルに置くべき情報です。

## 7本の定義

すべて **検出・提示まで**で、送金と台帳の確定書き込みはしません。

| taskId | cron | 呼ぶスキル |
|---|---|---|
| `osi-finance-daily-sync` | `0 7 * * *` | **（なし・暫定で手順を持つ）** |
| `osi-finance-daily-contract-detect` | `20 8 * * *` | `osi-finance-contract-intake` |
| `osi-finance-daily-payment-detect` | `25 8 * * *` | `osi-finance-payment-detect` |
| `osi-finance-monthstart-invoice-draft` | `30 9 1 * *` | `osi-finance-invoice` |
| `osi-finance-monthly-ar-close` | `0 9 2 * *` | `osi-finance-ar-sync` |
| `osi-finance-monthstart-close` | `0 9 3 * *` | `osi-finance-monthly` |
| `osi-finance-monthend-payment-list` | `0 9 25 * *` | `osi-finance-payment-detect` |

> **cron はローカル時刻で評価されます**（UTC ではない）。
> 実際の発火は負荷分散のため数分ずれます。分単位の精度を前提にしないでください。

> `osi-finance-daily-sync` **だけ対応するスキルがありません。**暫定で手順をプロンプトに
> 持っています。**将来 `osi-finance-invoice` 側に取り込み、ここを数行にするのが望ましい状態です。**
> 未解決の負債として明示しておきます。

### 1. `osi-finance-daily-sync` — 毎朝7:00 ／ **既定では自動実行しない**

> **⚠ 2026-08-17 に自動実行から外しました。**実装を読んだ結果、今の運用では機能しないと判断しました。
> **登録するかどうかは、下を読んでから決めてください。**
>
> `sync_ledger` は請求書SaaS の3つのフラグを見てステータスを進めますが、
>
> | 判定 | 見ているもの | 今の運用では |
> |---|---|---|
> | 送付済 | `email_sent` | **立たない。**SaaS のメール送付機能は使わない方針（送付はメール下書き一本。二重送信を避けるため） |
> | 入金済 | SaaS 側の入金状態 | **立たない。**入金は銀行明細を見て人が台帳に付ける運用で、SaaS には記録していない |
> | 請求済 | `posted`（発行済） | **立つが、逆向きに働く** |
>
> 3つ目が問題です。`posted` は請求書を作った瞬間に立つため、**「まだ送っていない請求書を
> 請求済にしろ」と毎日提案してきます。**「送信は人が押してから請求済にする」という運用と
> 逆です。プレビューどまりなので事故にはなりませんが、**毎朝ノイズが出ます。
> ノイズが出る報告は読まれなくなります。**
>
> 価値があるのはメールの送信済み確認（「送ったのに台帳が下書き済のまま」の検出）だけですが、
> 意味があるのは月初の数日で、しかも**要確認事項の「下書きのまま止まっている請求」が
> 同じ行をすでに出しています。**
>
> **必要なときはコンソールの「▶ 今すぐ」で手動実行してください。**
> 自動に戻すなら、少なくとも `posted` → 請求済 の判定を外してからにしてください。

**description**: 毎朝7:00、請求ステータスの差分をプレビュー報告（請求書SaaS＋メール送信済み確認・台帳は書き換えない）

**prompt**:

```
OSI Finance の日次タスク：請求ステータスの差分チェック（プレビューのみ）。

⚠ このタスクだけ、対応するスキルがまだありません。手順をここに書いているのは暫定です。
将来 osi-finance-invoice 側に取り込み、ここは数行にするのが望ましい状態です。

前提：Finance コネクタを使う。台帳はローカルの xlsx で、タブ名だけで引ける。
spreadsheet_id は指定しない（そのような設定はもう無い）。メールコネクタも使う。

手順：
1. health_check を実行する
2. 請求書SaaS の接続が ok なら sync_ledger を { tab: "月次請求スケジュール", dry_run: true }
   で実行する。ok でなければ同期はスキップし、その旨を報告に含める（メール確認は続行）
3. 「月次請求スケジュール」から 請求ステータス=下書き済 の行を抽出する。0件ならスキップ
4. 各行について送信済みメールを検索する（in:sent に請求書番号。ヒットしなければ
   宛先または取引先名と「請求書」で過去14日以内）。見つかった行を
   「下書き済 → 請求済 の更新候補」とする
5. 差分を簡潔に報告する

原則：
- 台帳には書き込まない（提案まで）。dry_run は true のままにし、明示的な指示があるまで false にしない
- 判別できないものは「未送付または要確認」とし、憶測で送付済みと判定しない
- ステータスをダウングレードしない／送金しない
```

### 2. `osi-finance-daily-contract-detect` — 毎朝8:20

**description**: 毎朝8:20、新しく締結された契約の取りこぼしを検出し、台帳への起票案を報告（自動書込みなし）

**prompt**:

```
OSI Finance の日次タスク：新しく締結された契約の取りこぼし検出。

osi-finance-contract-intake スキルに従って実行してください。
対象は過去2日以内に締結・受領された契約です。

このプロンプトに手順・フォルダパス・台帳の場所・自社の情報を書かないでください。
すべてスキル本体と設定ファイルが持っています。ここに直書きすると、フォルダ構成が
変わったときに気づかないまま古くなります（実際に起きました）。

原則：
- 台帳への自動書き込みはしない（起票案の提示まで）
- 金額・期間が読み取れないものは推測せず「要確認」とし、出所（メールのIDやファイル名）を併記する
- 報告は日本語で簡潔に。新規が無ければ「新規契約なし」だけでよい
```

### 3. `osi-finance-daily-payment-detect` — 毎朝8:25

**description**: 毎朝8:25、新着の受領請求書（振込払い）の取りこぼしを検出し、支払予定の起票案を報告（自動書込み・送金なし）

**prompt**:

```
OSI Finance の日次タスク：受領請求書（振込払い）の取りこぼし検出。

osi-finance-payment-detect スキルに従って実行してください。対象は過去2日以内の新着です。

このプロンプトに手順・フォルダパス・台帳の場所・支払先の情報を書かないでください。
すべてスキル本体と設定ファイルが持っています。

原則：
- 振込で払う受領請求書のみが対象。カード払い（自動課金SaaS含む）は会計側のカード連携が
  自動仕訳するため対象外（台帳に起票しない。証憑の保存だけ）。理由は二重計上を防ぐため
- 台帳への自動書き込みはしない／送金もしない（起票案の提示まで）
- 毎月固定の定期支払は、当月分が未起票なら「起票漏れの疑い」として警告する
  （請求書の到着に依存させない）
- 読み取れない項目は数字を捏造せず、出所を併記する
- 新着が無ければ「新着の受領請求書なし」だけでよい
```

### 4. `osi-finance-monthstart-invoice-draft` — 毎月1日9:30

**description**: 毎月1日9:30、請求日が到来した未請求分の請求書を発行し、PDF格納とメール下書きを作成して台帳を「下書き済」に更新（送信はしない）

**prompt**:

```
OSI Finance の月次タスク：当月の請求書ドラフト発行。

osi-finance-invoice スキルに従って実行してください。

対象の絞り込み（このタスク固有）：
「月次請求スケジュール」から 請求ステータス=未請求 かつ 請求日 ≤ 当月末 の行。
過去の請求日で未請求のまま残っている行も必ず含めてください。前月末日付の請求など、
月初1日の実行では拾い漏れるものがあります。

採番規則・税抜への変換・取引先や部署の解決方法・格納先・自社情報を、ここに書かないでください。
すべて osi-finance-invoice スキルと設定ファイルが持っています。重複は片方だけが古くなる原因です。

原則：
- 発行前に必ず dry_run で1回確認できる形で提示する
- メールは送信しない（下書きまで）。人が下書きを確認して送る
- 「請求済」への遷移はこのタスクでは行わない（人がコンソールのボタンで進める）
- 番号未付与の一括案件（検収後請求・完了時請求など）は、完了・検収の確認が取れるまで
  発行せず要確認として報告する
- 対象0件、または既に下書き済／請求済なら、作成せず現状を報告する
- 台帳が Excel で開かれていて書き込めない場合は、誰が開いているかを含めて報告する
```

### 5. `osi-finance-monthly-ar-close` — 毎月2日9:00

**description**: 毎月2日9:00、前月分の売上(AR)計上漏れを検出してレビュー用に提示（承認後に計上）

**prompt**:

```
OSI Finance の月次タスク：前月分の売上（AR）計上漏れの検出。

osi-finance-ar-sync スキルに従って実行してください。対象月は実行日の前月です。

手順・台帳のID・勘定科目や税区分の判断ルール・会計年度・自社情報を、ここに書かないでください。
すべてスキル本体と設定ファイルが持っています。

原則：
- 未計上を一覧で提示し、承認を得てから計上する。自動では確定しない
- 提示には金額合計と、計上後の当月営業利益の見込みを添える
- 二重計上を防ぐため、同じ請求書IDの売上計上が既にあればスキップする
- 台帳の備考に「会計計上=手動按分済・自動AR計上の対象外」とある行は全額自動計上しない。
  按分ぶんは「未計上の要確認」として必ず挙げる
- 曖昧な科目・税区分は確定せず、人（必要なら税理士）に確認する
- 入金消込は本タスクの対象外（売上計上のみ）。送金・支払は行わない
```

> **前払費用の振替のような「特定月だけの処理」をここに書かないでください。**
> 以前このタスクには社宅家賃の振替が金額つきで2ヶ月分だけ直書きされており、
> その2ヶ月が終わった時点で**残っているのに意味を持たない記述**になっていました。
> 期間限定の処理は台帳側で管理します。

### 6. `osi-finance-monthstart-close` — 毎月3日9:00

**description**: 毎月3日9:00、前月分の月次経理クローズを実施し差分と要対応点を報告（仕訳確定・送金・台帳確定書込みはしない）

**prompt**:

```
OSI Finance の月次タスク：前月分の月次経理クローズ。

osi-finance-monthly スキルに従って実行してください。対象は実行日の前月です。

進め方（スキル側の順序）：
① 口座連携明細の取込確認 → ② カード／銀行明細の仕訳化レビュー → ③ 台帳と会計SaaS の突合
（計上漏れ・不一致の検出）→ ④ 残高試算表で検算 → ⑤ 月次サマリの報告

③の前に、必ず①をやってください。連携が止まっていると、突合しても「漏れが無い」ように
見えてしまいます。

原則：
- 自動での仕訳確定・送金・台帳の確定書き込みはしない。検出した差分・計上漏れ・要対応点を
  レビュー用に一覧で報告するに留める
- 会計仕訳の正本は会計SaaS の口座連携明細、台帳は資金管理（誰にいくらいつ）という前提
- 差が出たときは「どちらが正しいか」を決めてから直す。画面や台帳を数字に合わせにいかない
- 手順・勘定科目・税区分の判断辞書をこのプロンプトに書かない（スキル側が持つ）
```

### 7. `osi-finance-monthend-payment-list` — 毎月25日9:00

**description**: 毎月25日9:00、当月末に支払予定（振込払い）の受領請求書を抽出し振込リストとして報告（自動送金・確定はしない）

**prompt**:

```
OSI Finance の月次タスク：月末の振込リスト作成。

osi-finance-payment-detect スキルの判断基準に従って実行してください。

やること：
支払管理台帳の「月次支払管理」から、当月末に支払予定（振込払い）の受領請求書を抽出し、
支払先・金額・振込期日・振込先口座を一覧化して報告する。
台帳に未起票の受領請求書があれば、支払予定の起票案として併せて提示する。

原則：
- 振込で払うものだけが対象。カード払い（自動課金SaaS含む）は会計側のカード連携が
  自動仕訳するため除外する
- 自動送金・台帳の自動確定はしない。振込は人が実行する
- 源泉徴収の対象がある支払は、徴収額を引いた振込額を併記する。納期限は原則、
  支払った月の翌月10日（納期の特例なら年2回）
- 振込先口座や支払先の情報をこのプロンプトに書かない（台帳の支払先マスタが正本）
```

## 登録・更新・削除のしかた

**コンソールの「自動実行」画面にボタンがあります。**押すと Cowork が開いてプロンプトが入り、
承認すると実行されます。ボタンが無い環境では、チャットで下のように頼んでください。

| やること | 頼み方 | 使うツール |
|---|---|---|
| 今の状態を見る | 「OSI Finance の自動実行の状態を見せて」 | `list_scheduled_tasks` |
| 登録する | 「OSI Finance の自動実行を登録して」 | `create_scheduled_task` |
| 最新に更新する | 「OSI Finance の自動実行を最新に更新して」 | `update_scheduled_task` ／ 無い分は `create` |
| まとめて削除する | 「OSI Finance の自動実行を全部やめて」 | `delete_scheduled_task`（**一覧を見せて承認を取ってから**） |

**taskId が `osi-finance-` で始まるものだけを対象にしてください。**
他の人の別タスクを巻き込まないための線引きです。
（2026-08-17 に `keiri-*` から改名したのは、この線引きを成立させるためです）

### 止めるときは削除でよい。ただし「更新」で削除+再作成をしないこと

**止める＝削除**でよい（2026-08-17 ユーザー判断）。定義そのものはこのファイルに残るので、
再登録できるためです。

**ただし、既にあるタスクの内容を直すときは `update_scheduled_task` を使ってください。
いったん削除して作り直さないこと。**

理由は**ツールの許可がタスクに保存されている**ためです。削除すると許可も消え、
次の無人実行が許可待ちで止まって**報告が届かなくなります**（気づきにくい壊れ方です）。

| やること | 使うもの |
|---|---|
| 内容や時刻を直す | `update_scheduled_task` |
| 使わなくする | `delete_scheduled_task` |
| 消したものを戻す | `create_scheduled_task` → **そのあと「Run now」を1回** |

**削除は必ず一覧を見せて承認を取ってから実行してください。**
2026-08-17 に「全部やめる」ボタンで7本が消え、実行履歴と許可が失われました。
消えること自体は想定どおりでも、**何本消えるかを見せていなかった**のが問題でした。

### 登録したら「Run now」を1回

**無人実行の前に、手動で1回走らせてください。**初回はコネクタの許可ダイアログが出るため、
先に通しておかないと、無人実行が許可待ちで止まります。

### 更新を忘れないために

**スキルを直したときは、このファイルとの整合を確認してください。**
スケジュールが薄ければ、ほとんどの場合は何もしなくて済みます。
それが薄く保つ理由です。

## アプリが閉じているとき

**スケジュールはアプリが開いている間だけ走ります。**
閉じている時刻に予定があった場合は、**次に起動したときに走ります。**
「毎朝7:00の報告が昼に届いた」はこれです。異常ではありません。
