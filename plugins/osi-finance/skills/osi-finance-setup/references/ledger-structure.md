# 台帳の構造（2026-08-18 再編）

**どのスキルも、台帳を読む前にここを見てください。**
「どの情報がどこにあるか」と「何が正本か」を決めた文書です。

---

## ファイルの分け方

```
{台帳フォルダ}/
├── 共通マスタ.xlsx      取引先マスタ ／ 雛形マスタ      ← 受注にも発注にも属さないもの
├── 請求管理台帳.xlsx    契約マスタ ／ 月次請求スケジュール ／ 発行者設定
├── 支払管理台帳.xlsx    支払先マスタ ／ 月次支払管理 ／ 月次支払スケジュール ／ 経費一覧 ／ 源泉徴収管理
└── 仕訳台帳.xlsx        仕訳帳 ／ 勘定科目マスタ ／ 月次サマリ
```

**タブ名は台帳をまたいで一意です。**`sheets_*` はタブ名だけで引けるので、
どのファイルにあるかを気にする必要はありません。`spreadsheet_id` は原則指定しないでください。

### なぜ「共通マスタ」を分けたか

取引先は受注にも発注にも属しません。以前は取引先マスタが請求管理台帳の中にあり、
**支払管理台帳が請求管理台帳を見ないと支払先の名前を解決できませんでした。**
受注側だけが特権を持つ非対称な形だったので、中立なファイルに切り出しました。

雛形マスタも同じ理由です（受注用と発注用が両方入っているのに請求側にありました）。

> ファイルを1つに統合しなかったのは、**Excel のロック**のためです。
> 誰かが台帳を開いている間は書き込みが拒否されるので、1ファイルにすると
> 「支払を見ている人がいるだけで請求書の発行が止まる」ことになります。

## 取引先ID は `P-001` 形式（文字列）

**必ず `P-` で始まります。**`001` のような裸の数字にはしません。

### なぜ記号を付けたか

**Excel は `141` を数値に変換し、`001` は文字列のまま残します。**
桁の頭がゼロかどうかで型が変わるため、同じ列に文字列と数値が混ざり、
**厳密に比較すると引けなくなります**（2026-08-18 に実際に発生。契約12件・支払先27件が
参照切れ判定になった）。見た目では区別できないのが最悪の点です。

識別子は計算に使わないので、数値である必要がありません。記号を1つ入れるだけで、
型の揺れが構造的に起きなくなります。

**新しい取引先IDを採番するときも `P-` を付けてください。**
番号自体は案件連番の続き（2026-08-18 時点の最大は `P-158`）。

## 何がどこにあるか（正本）

| 知りたいこと | 見るタブ | 備考 |
|---|---|---|
| 会社の正式名称・住所・法人番号・インボイス登録番号 | **取引先マスタ** | 契約マスタにも同名の列が残っているが正本ではない |
| 請求書の宛先（To/CC） | **取引先マスタ** | 契約マスタ側に値があればそちらを優先（この契約だけ宛先が違う場合の上書き） |
| 契約の金額・期間・支払サイト・方向（受注/発注） | **契約マスタ** | |
| 振込先口座・源泉徴収の要否・支払サイクル | **支払先マスタ** | 会社の名前は持たない。`取引先ID` で取引先マスタを引く |
| 契約書の雛形 | **雛形マスタ** | 区分（受注用/発注用/共通/廃止）で選ぶ。パスを直書きしない |
| 請求・入金の状態 | 月次請求スケジュール | |
| 支払予定・支払実績 | 月次支払スケジュール ／ 月次支払管理 | |

### 関係

```
取引先マスタ（会社そのもの・1社1行）
   ├── 契約マスタ（受注）  → 月次請求スケジュール → 請求・入金
   ├── 契約マスタ（発注）  → 月次支払管理        → 支払予定・支払
   └── 支払先マスタ（振込先口座・支払条件）
```

**受注と発注は取引先の下で対称です。**同じ会社に両方があっても取引先マスタでは1行
（2026-08-18 時点で11社が該当）。

**支払先マスタに対応するものが受注側に無いのは、業務が非対称だからです。**
払うときは相手の口座が要りますが、もらうときは相手の口座を知る必要がありません
（相手が当社の口座に振り込むため）。受注側で必要なのは宛先メールで、それは取引先マスタにあります。

## 欠損は「空欄」で表す。文字で書かない

**「まだ分からない」を `要確認` `不明` `未定` `(要確認)` のような文字で書かないでください。**
空欄にして、**理由は `備考` に書く**。

### なぜか

判定する側が、その文字を知らないと「値が入っている」と扱ってしまいます。
2026-08-18 に実際に起きました——契約マスタの `Toアドレス` に `(要確認)` と入っていたため、
「契約側に値があれば優先」の規則が働き、**取引先マスタにある正しいアドレスが覆い隠され、
請求書の発行が止まっていました。**

> この「契約側を優先」という規則そのものを 2026-09-06 に廃止しました。契約マスタから
> `請求先To` `Toアドレス` `CC` `CCアドレス` の4列を削除し、宛先は取引先マスタだけが持ちます。
> 同じ情報を2箇所に置くかぎり、片方だけ直されるのを規則で防ぐことはできませんでした。

書き方は増え続けます（`要確認` `要確認?` `(要確認)` `未確認` …）。
そのたびに判定側へ条件を足すことになり、必ずどこかが漏れます。
**空欄は1種類しかないので、漏れようがありません。**

### 書き方

| | 悪い | 良い |
|---|---|---|
| 区分が未確認 | `区分 = 要確認` | `区分 = （空欄）` ／ `備考 = 区分が未確認。源泉徴収の要否に関わるので支払前に確かめる` |
| 相殺の可否が未定 | `相殺可否 = 要確認` | `相殺可否 = （空欄）` ／ `備考 = 相殺可否は未確認（先方と合意が取れていない）` |

**「空欄なら埋めればいい」と誰かが親切に埋めてしまわないよう、備考に理由を残すのが要点です。**
理由の無い空欄は、推測で埋められます。

## 台帳を読むときの約束

1. **`取引先ID` で引く。**会社名で突き合わせない（表記ゆれで必ず失敗する。
   `eGrid`／`イーグリッド`、`うぐいす`／`ウグイス` のような例が実在した）
2. **`取引先ID` が空の行は、そこで止めて人に報告する。**推測で埋めない
3. **ヘッダーは1行目とは限らない。**支払先マスタは3行目、月次支払管理は4行目。
   `sheets_get_values` が返す `header_row` を使い、行番号を決め打ちしない
4. **旧IDは `旧取引先ID`／`旧支払先ID(V-)` 列に残してある。**
   過去の資料に `901` や `V-012` が出てきたら、そこから辿れる

---

## 支払先ID（`V-`）は残してある

支払先マスタと月次支払管理は `支払先ID`（`V-001` 形式）で繋がっています。
**取引先IDに置き換えていません。**書き換えると過去の支払実績の紐付けが切れるためです。

対応は支払先マスタの `取引先ID` 列にあります。`V-` → `P-` はここで引いてください。
