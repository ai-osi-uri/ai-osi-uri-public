# osi-finance-invoice（月次 請求書発行 → Gmail下書き）

> **組織固有値（社名・登録番号・住所・振込先・税率・採番ルール・Drive ルート／フォルダ名・台帳ファイル名）は
> `config/osi-finance-settings.md`（テンプレ：`config/osi-finance-settings.example.md`）を参照する。** 実値版が無ければ作成を案内。

請求管理台帳の請求予定から請求書を作り、人が送る一歩手前（下書き）まで用意する。

## 役割と非役割

- やる：当月の未請求予定 → **MFクラウド請求書で発行**（AI OSI URI Finance 拡張の `mfi_*`）→ **MF公式PDF**を送付請求書フォルダ（設定の `送付請求書/YYYY-MM/`、例: `02.送付請求書/YYYY-MM/`）格納 → Gmail下書き作成 → 台帳ステータス更新。
- やらない：メール送信（人が実行）／契約取込・スケジュール展開（= osi-finance-contract-intake）／入金確認・消込（別ワークフロー）。
- **自動送信・自動確定はしない。** 下書き作成までで止め、人の確認を待つ。
- **送付経路は Gmail 一本。MF のメール送付機能は使わない。** MF は「採番・適格請求書フォーマット・PDF生成」だけを担う。両方から送れる状態にすると同じ請求書が2回届くため、経路は1つに固定する（MF に送付先メールを登録してあるのは、MF画面で宛先を確認できるようにするためと、将来の切り替え余地を残すため）。
- **請求書の発行と会計計上は分離。** 売上のMF計上（(借)売掛金/(貸)売上+仮受消費税）は `osi-finance-ar-sync` が担う（発行＝即計上にはしない）。

## 前提コネクタ

- **AI OSI URI Finance 拡張**（`mfi_create_partner` / `mfi_create_billing` / `mfi_get_billing_pdf` / `sheets_*`）＝発行と台帳の読み書き。発行には MF を **data.write スコープ**で接続しておく（osi-finance-connect 参照）。
- Google Drive（公式PDFの格納）、Gmail（下書き作成）。
- 請求書PDFは**MFが生成**（自前PDF生成はしない）。発行者情報・採番・支払条件は `osi-finance-settings` を参照。
- 任意：既存下書きへの確実な添付に Claude in Chrome（ブラウザ操作の `file_upload`）、本文パーソナライズに Obsidian（`obsidian-knowledge-consult`）／Plaud／Drive。無ければ手動・汎用にフォールバック。

## 台帳アクセス

- 台帳は**設定した台帳フォルダにあるローカルの xlsx**。`sheets_*`（`sheets_read_schedule` / `sheets_get_values` / `sheets_update_status` / `sheets_update_values`）は**タブ名だけで引ける**（どのファイルにあるかは拡張が解決する）。ID の指定は不要。
- 使うタブ：「月次請求スケジュール」「契約マスタ」「**取引先マスタ**」「発行者設定」。
- **ヘッダーは1行目とは限らない。** 列はヘッダー名で解決し、行番号を決め打ちしない。

### 会社の情報は「取引先マスタ」が正本（2026-08-18〜）

> 台帳全体の構造・何が正本か・ID の決まりは
> [`osi-finance-setup/references/ledger-structure.md`](../osi-finance-setup/references/ledger-structure.md) に
> まとめてある。迷ったらそちらを見る。

**正式名称・住所・郵便番号・請求先To/CC は「取引先マスタ」を見る。**
契約マスタの `取引先ID` で引く。取引先マスタは**共通マスタ.xlsx** にあるが、
`sheets_*` はタブ名だけで引けるので `spreadsheet_id` は指定しない。

**`取引先ID` は `P-001` 形式の文字列。**裸の数字ではない。
`P-` を外したり、数値として扱ったりしないこと（Excel が `141` を数値に変換し、
`001` は文字列のまま残るため、記号が無いと同じ列に型が混ざって引けなくなる）。

**契約マスタにも同じ列が残っているが、そちらは正本ではない。**
1社で契約が5本あれば正式名称が5回書かれることになり、社名変更や移転のときに
片方だけ直してズレる。実際、契約が複数ある取引先は4社ある。

**引き方（この順で決める）**

1. 契約マスタの行から `取引先ID` を取る
2. 取引先マスタで同じ `取引先ID` の行を引く → 正式名称・住所・請求先To/CC を得る
3. **契約マスタ側に値が入っていれば、そちらを優先する**（この契約だけ宛先が違う場合の上書き）
4. どちらも空なら**止めて人に聞く**。推測で埋めない

**`取引先ID` が空の契約は、その場で止めて報告する。**取引先マスタを引けないため、
宛名の無い請求書ができる。2026-08-18 時点で空の契約は0件なので、空があれば異常。

### 止めるのは「正式名称が無いとき」だけ（2026-08-18 変更）

**メールアドレスが無くても発行する。**以前はメールが無いと発行を止めていたが、これは誤りだった。

| 欠けているもの | どうするか | なぜ |
|---|---|---|
| **正式名称** | **止める** | 適格請求書の記載事項（交付を受ける事業者の名称）。**書類として成立しない** |
| **メールアドレス** | **発行する** | 請求書の記載事項ではなく、**届け方の問題**にすぎない。郵送でも成立する |

メールが無い場合も、**PDF・番号・台帳行を作り、Gmail 下書きも宛先を空のまま作る。**
人が下書きを開いて宛先を入れて送る。**宛先が空の下書きは Gmail が送信を拒否する**ので、
誤送信にはならない（安全側に倒れる）。要確認事項の「請求先メールが未設定」でも拾われる。

> 「番号だけ振られて中身の無い請求書ができる」という理由で止めていたが、**中身はある。**
> 取引先・金額・期間は契約で確定していて、メールアドレスとは無関係。
> 番号に穴が空くのは請求書自体を取り消したときで、メールの有無とは関係がない。
>
> 請求書SaaS 側の制約も無いことを確認済み（2026-08-18）。取引先を `email: null` のまま
> 登録でき、実際にそうなっている取引先が2社ある。SaaS のメール送付機能は使わない方針なので、
> メールは発行に影響しない。

### 宛名（`請求先To`）が空のときは会社名宛にする

`請求先To` が空なら **`{正式名称} 御中`** とする。人名を推測して補わない。

**メールアドレスの綴りから人名を起こさないこと。**`shibata-yasuko@…` を「柴田泰子様」と
書くような補完はしない。実際、契約の窓口と請求の宛先が別人の取引先がある
（そういう場合は宛名を空にし、経緯を取引先マスタの備考に残してある）。
- Excel で台帳が開かれていると書き込みは拒否される（`台帳が Excel で開かれています…`）。開いている人に閉じてもらう。

## 発行者情報（組織固有値・osi-finance-settings 参照）

発行者ブロック（社名・登録番号・住所・振込先・税率・手数料負担）は組織固有値。
**優先順位：台帳シート「発行者設定」→ `config/osi-finance-settings.md` → `references/invoice-issuer.md`（汎用レイアウト）。**
実値はスキルに直書きせず、上記から読み込む（具体値の一覧と差し込みキーは invoice-issuer.md を参照）。

## 手順

### 1. 請求予定を抽出（一括／単票）
- **一括モード（既定）**: 台帳「月次請求スケジュール」から `対象月 = 当月（または指定月）` かつ
  `請求ステータス = 未請求` を取得。
- **単票モード**: 請求書番号（INV-xxx）または「取引先×対象月」の指定を受けた場合は**その1行だけ**を
  対象にする（コンソールの「📧 Gmail下書きを作る」行ボタンからの実行を想定）。
- 各行に**契約マスタ**（契約固有：件名素・金額・支払サイト・取引先ID）と、
  その `取引先ID` で引いた**取引先マスタ**（会社の属性：正式名称・住所・請求先To/CC）を結合する。
  同じ列が両方にある場合は**契約マスタ側が入っていればそちらを優先**（上の「引き方」を参照）。
- **同じ請求書番号の行は1通にまとめる（重要）。** 台帳は **1請求書 = N行**。1通に複数明細を載せるとき、明細ごとに行を作って同じ番号を振る運用になっている（例：NITOH の `INV-2026-07-016` は3行、京橋・REIT も2行ずつ）。**行ごとに発行すると同じ相手に複数通が飛ぶ。** 請求書番号でグルーピングし、**1グループ = MF の1請求書（`items[]` に N 明細）** とする。未採番の行は「取引先 × 対象月」でまとめてから採番する。
  - 裏返しとして、**「同一番号が複数行＝採番重複」という検知を入れてはいけない**（正常な合算請求を毎回誤検知する）。
  - **代わりに額面で検算する。** グループの合計額が、発行済み請求書の額面（MF側 or 送付済みPDF）と一致するかを見る。
    一致しないときだけ止める。行数では判定しない。
  - **グループが複数の対象月にまたがる場合は、対象月を摘要・明細名に必ず残す**（例「CAIO業務 2026年4〜6月分」）。
    残さないと、会計側（`osi-finance-ar-sync` / `osi-finance-journal`）が計上月を決められず、
    同じ請求書を月をまたいで二重計上する事故につながる。

### 2. 採番（osi-finance-settings の AR 採番ルール）
- 採番形式は `osi-finance-settings` の `AR_NUMBERING`（例：`INV-YYYY-MM-連番3桁`）。
- **`YYYY-MM` は請求月（＝対象月の翌月）であって、対象月ではない。** 対象月 2026-08 の請求書は `INV-2026-09-003`。
  対象月で採番すると既に発行済みの番号とぶつかる。
- 連番は**その請求月内**の発行順（既存の最大連番+1）。採番済み番号は台帳「請求書番号」に書き戻し、欠番・重複を出さない。
- **合算請求は1グループで1番号**（同じ番号が複数行に付くのは正常。手順1参照）。

### 3. 請求書を MF クラウド請求書で発行（正本PDFはMF生成・AI OSI URI Finance 拡張）
> **発行エンジンは MoneyForward クラウド請求書（`mfi_*` ツール）。** 自前PDF生成はしない。
> MFが採番・適格請求書フォーマット・PDFを担い、台帳は正本として番号/状態/リンクを保持する。

1. **取引先の解決**：`mfi_list_partners` に**取引先マスタの `正式名称`**（例「株式会社FIXER」）を渡して検索する。`略称` は使わない（「eGrid」「MOOS」のような表記で、法人格が付いていないため検索に当たらない）。
   - **部署は1社に2つある（罠）。** MF は取引先を作ると空の既定部署を自動生成するため、`departments` には「空の部署」と「`person_dept: "本社"` かつ送付先メールを持つ部署」が並ぶ。**必ず後者の `id` を `department_id` に使う。** 先頭を機械的に取ると、宛先の無い請求書ができる。
   - 見つからなければ `mfi_create_partner`（name＝正式名称、dept_name＝`"本社"`、email＝請求先To、cc_emails＝CC。**CC が複数なら半角カンマ区切り**。台帳に全角読点で並んでいることがあるので変換する）で作成し、返り値の `department_id` を使う。
   - 担当者名は MF に入れない（請求書PDFの宛名に印字され、台帳に社内メモが混ざっている行があるため）。担当者宛にするのは Gmail の本文側。
2. **品目の組み立て**：台帳の `請求額(税込)` から税抜単価を算出（既定10%なら `price = round(税込 / 1.1)`、`excise = "ten_percent"`、`quantity = 1`、`name = 件名`）。軽減/非課税はその税区分を使う。源泉が要る取引先は `is_deduct_withholding_tax`。
3. **プレビュー**：`mfi_create_billing` を `dry_run:true` で1回呼び、`would_post` の中身（department_id・billing_date・due_date・billing_number＝台帳INV・items）を人に提示して確認を取る（金額・宛先・期日）。
4. **発行**：確認後 `mfi_create_billing`（`dry_run:false`）。
   - `billing_date`/`due_date` は `osi-finance-settings` の `AR_PAYMENT_TERMS`（請求日＝対象月翌月1日、支払期限＝翌月末）。
   - `billing_number` に**台帳の請求書番号(INV)をそのまま指定**（台帳とMFの番号を一致させる）。
   - 返り値の `billing_id` / `billing_number` / `pdf_url` を控える。
5. **MFが使えない場合のフォールバック（暫定）**：MF を data.write で接続できない等で `mfi_*` が使えないときに限り、自前PDFを暫定生成してよい。**HTML→PDF（weasyprint + Noto Sans CJK JP を埋め込み）＋ ghostscript 軽量化**で作る（reportlab の非埋め込みCIDフォントは英数字・数字が □ 化して金額が読めないため不可。生成後は `pdftoppm` で画像化し目視検証）。適格請求書要件・採番はMF正本に劣るため、MF発行に戻せるようになったら差し替える。

### 4. 公式PDFを Drive に格納（正本はDrive）
- `mfi_get_billing_pdf`（id または pdf_url）で**MF生成の公式PDF**を base64 取得。
- **マウント済みの Drive 共有ドライブ（ローカル同期フォルダ＝FS）** に base64 をデコードして書き出す：
  `{請求管理ルート}/{送付請求書}/YYYY-MM/{INV}_{取引先}_{件名短縮}.pdf`（同期で Drive に反映。直アップロードより安定）。
- **`YYYY-MM` は請求月＝請求書番号と同じ月。対象月ではない。** 対象月2026-07分の `INV-2026-08-001` は
  `02.送付請求書/2026-08/` に置く。2026-08 まで対象月フォルダに置く運用が混ざっており、2026-08-31 に
  請求月基準へ統一した（42ファイル移動）。ここを取り違えると台帳のパスも一緒にずれる。
- 書き出し後にファイルが開けることを確認。

### 5. Gmail 下書き作成（送付は人が1クリック）
- 宛先＝**取引先マスタの請求先To**（契約マスタ側に入っていればそちらを優先）、CC＝同じ順で解決した CCアドレス。件名例：`【{ISSUER_NAME}】請求書送付（{件名}）`。本文は定型（お礼＋添付＋振込先＋支払期限）。
- **MFのPDF**を添付して**下書きのみ作成（送信しない）**。**MF 側からは送らない**（二重送付になる）。運用者が内容を確認し、Gmailで送信する＝実質「1クリック送付」。
  （MF API にメール送信は無い。郵送が要る場合のみ別途 `posting` を使う方針。）
- **添付が不確実なとき（重要）**：Gmail のメール系コネクタの下書き作成ツールは添付が不確実（「添付未対応」表記・検証不可）なことがある。その場合は **Claude in Chrome の `file_upload`** で、Drive上の公式PDF（または暫定PDF）を**既存下書きに直接添付**する：宛先で一意特定（`in:draft to:<addr>`）→開く→添付。**navigate→screenshot→click の順**で確実に開き、処理済みは一覧上位に繰り上がるため**固定座標でなく宛先検索で毎回特定**、重複下書きは作らない。Chrome不可なら人が手動D&D添付（本文に「PDF添付」と書くので添付漏れ注意を伝える）。

### 5.5 本文パーソナライズ（任意・レビュー前提）
- 当月ご一緒した取り組みを **Obsidian（`30_Projects/_Active/{社名}/議事録`、`obsidian-knowledge-consult` 経由）→ Plaud → Drive** の順で拾い、お礼文に1段落反映。記録が無い社は具体を書かず**厚めの汎用お礼にフォールバック**（不正確リスクを避け無理に具体を書かない）。
- **安全ガード（必須）**：送付先は客先本人。社内戦略・価格/割引・人脈・未確定構想などの**機微は本文に出さない**。件名/INVと本文を突合し取り違え防止。宛名の固有漢字は台帳表記を厳守（自動変換の誤字注意）。**送信前レビュー必須**。

### 6. 台帳更新
- 各行：請求ステータス→**「下書き済」**、請求書番号(=MF billing_number)・請求日・支払期限・**送付請求書ファイル**を記入。
- **送付請求書ファイルは、台帳フォルダからのフォルダ込み相対パスで書く。ファイル名だけは不可。**
  例: `02.送付請求書/2026-08/INV-2026-08-001_サンプル株式会社_月額顧問料.pdf`。
  ファイル名だけを書くとどの月フォルダか解決できず、押すまで気づけない参照切れになる
  （2026-08-31 の棚卸しで31行がこれだった）。`sheets_append_row` は実ファイルを指していない値を
  弾く／自動補正して `path_fixes` で報告するので、返り値を必ず読むこと。詳細は `docs/運用ルール.md` §5-4。

## 留意

- 送信・確定は人。下書きまで。
- 一括案件は該当月のみ。月額は各月1通。
- **金額・期間は契約マスタ**、**宛名・住所・宛先は取引先マスタ**を正とし、相違があれば人に確認。
  会社の情報を契約マスタから読んで済ませないこと（1社で契約が複数あるとズレる）。
- 入金確認・消込は対象外（別ワークフロー）。
- **月初スケジュールの発火漏れ防止（重要）**：月初ドラフト・スケジュール（`osi-finance-monthstart-invoice-draft` 等／毎月1日）は、(a) スケジュールを新規登録・再作成した月は登録が発火時刻を過ぎると当月分が発火しない（cronは過去回を遡らない）→ **登録は月末までに済ませ初回は手動確認**、(b) 発火漏れ月の未請求分は次回実行で**併せて拾う（取りこぼし防止）**。

## エラー処理

詳細は **[`docs/エラー処理ガイド.md`](../../docs/エラー処理ガイド.md)** を正本とする。本スキルで詰まりやすい点：

- **`タブが見つかりません`**：台帳フォルダの設定（`xlsx_ledger_dir`）か、台帳ファイルがフォルダに揃っているかを見る。エラー文に既知のタブ名が並ぶので、綴りの取り違えもそこで分かる。
- **請求書に宛先が入らない／MF 側で送付先が空**：`department_id` に空の既定部署を選んでいる（手順3-1）。`person_dept` が入っているほうを使う。
- **発行が 403**：MF の権限が読み取りのみ。「MF を接続して」で `data.write` を含めて再認可する。
- **Gmail下書きにPDFが添付されない**：メール系コネクタの添付は不確実 → Chrome `file_upload` で既存下書きに添付、または人が手動添付（手順5）。
- **（フォールバックで自前PDFを作る場合）英数字が □ 化**：非埋め込みCIDフォントが原因。weasyprint + Noto Sans CJK JP 埋め込みに切替、生成後は画像化で目視検証。
- **請求書PDF・台帳xlsx の Drive 格納が失敗**するとき：Google Drive の**ローカル同期フォルダにコピー**して配置する（直アップロードは大容量で不安定）。配置後に開けるか確認。
- repo/台帳ファイルの差し替えは **in-place 編集を避け新規 Write**（`.fuse_hidden*` 残り対策）。
- `osi-finance-settings.md`（発行者・採番・振込先）が無ければ作成を案内し、埋まるまで採番・格納先確定を止める。送信・確定は人（下書きまで）。
