# タイプ判定の意思決定木

「知識化して」と言われた時、ユーザーに聞かずに以下の順で自律判定する。

## 判定の3段階

### 第1段階: 時間軸で大別

会話内容が以下のどれに当たるかをまず判断する。

| 時間軸 | タイプ候補 | 例 |
|---|---|---|
| 今日のこと・気づき | `daily` | 「今日○○について考えた」 |
| 永続的な原則・抽象化された知識 | `concept` | 「この原則は他の場面でも効きそう」 |
| 特定の打ち合わせ・会議の記録 | `meeting` | 「○○社との打ち合わせメモ」 |

### 第2段階: 対象で細分化

第1段階で `concept` 系（永続的な何か）と判断した場合、対象を見て以下に分類：

| 対象 | タイプ | フォルダ |
|---|---|---|
| 自分の思考・抽象化された原則 | `concept` | `20_Concepts/` |
| 特定の人物・組織の情報 | `person` | `40_People/` |
| 他人の発信・記事・書籍・動画の要約 | `resource` | `50_Resources/` |
| 特定の案件・クライアント関連 | `project` | `30_Projects/_Active/[案件]/` |
| 業務領域全体の俯瞰 | `area` | `60_Areas/` |

### 第3段階: 既存との関係

タイプが決まったら、Step 2 の検索結果を見て：

| 状況 | 挙動 |
|---|---|
| 同タイプで類似の既存ノートあり | **既存に追記**（patch_content）|
| 既存ノートはあるが、別の角度から書く価値あり | **新規作成 + 既存にリンク** |
| 既存ノートなし | **新規作成** |

「類似」の判定基準：タイトル + 主要概念で 70% 以上重複している場合は同主題と見なす。

## 迷うパターンの解消

複数タイプに該当する場合の判定ルール：

| 状況 | 判定 |
|---|---|
| Concept か Resource か（自分の解釈と他人の発信が混ざる） | 「自分の所感」が主なら **Concept**、「引用・要約」が主なら **Resource**。両方の比重が高ければ両方作る |
| Concept か Project か（プロジェクトでの学びを抽象化） | プロジェクト固有の情報は **Project**、汎用化した原則は **Concept**。両方価値があれば両方作る |
| Daily か Concept か（書きながら抽象化が始まる） | **両方作る**（Daily に元メモ、Concept に抽象版、相互リンク） |
| 議事録か Daily か（自分との対話） | 1人作業 → **Daily**、誰かと話した → **Meeting** |
| 1ノートに収まらない | **複数ノートに分割**して相互リンク。1ノート1コンセプト原則を守る |

## タイプごとの保存先と命名

詳細は vault 内の `90_Meta/命名規則.md` を参照。基本：

| type | パス | 命名 | 例 |
|---|---|---|---|
| daily | `10_Daily/` | `YYYY-MM-DD.md` | `2026-04-29.md` |
| concept | `20_Concepts/` | 自然言語タイトル | `生成AIの社会実装.md` |
| project | `30_Projects/_Active/[案件]/` | 内容に応じて | `プロジェクト概要.md` |
| meeting | `30_Projects/.../議事録/` | `YYYY-MM-DD_対象.md` | `2026-04-29_XYZ定例.md` |
| person | `40_People/` | `氏名_会社名.md` | `山田太郎_ABC社.md` |
| resource | `50_Resources/` | `タイトル_著者.md` | `第二の脳_TiagoForte.md` |
| area | `60_Areas/` | 領域名 | `営業・提案.md` |

## タイトル決定のコツ

- **抽象的すぎない**：「AIについて」ではなく「AIで提案書を作るときの3原則」
- **検索しやすい**：将来の自分が思い出せるキーワードを含める
- **Concept の場合は「結論ベース」**：「○○すべき」「○○が正解」のような断言形が後で見返した時に強い
- **絵文字・記号は使わない**（`90_Meta/命名規則.md` の禁則）

## リンクを張る対象の選び方

新規ノートに `[[既存ノート]]` リンクを張る時、以下を優先：

1. **同じドメイン**（domain frontmatter が一致）── 営業・提案領域なら同領域の Concepts を優先
2. **直接的な概念関係**── 「親子」「対立」「派生」「実例」のいずれか
3. **同プロジェクト**── 同じ案件のノート
4. **MOC（60_Areas/）**── 必ず該当する Area ノートにリンクを張る

最低 3本、理想は 5本。10本以上だと過剰なので絞る。

## 判断つかない時の最大1問ルール

以下のような本当に判断できないケースのみ、ユーザーに確認する：

- ✅ 「Conceptと既存Resourceの両方の性質があり、どちらに重心を置くべきか分からない」
- ✅ 「複数のクライアントに関わる内容で、どのプロジェクトフォルダに置くべきか分からない」
- ❌ 「タイトルどうしますか？」← 自分で決める
- ❌ 「frontmatterのstatusはdraftですか？livingですか？」← 新規はdraft固定でOK

判断つかないことは多くない。8割は機械的に判定できる。
