# Obsidian Knowledge Consult

Obsidian vault に蓄積されたユーザー独自の知識を引き出し、回答に活用するスキル。

## なぜこのスキルか

vault に書き溜めても、引き出されなければ意味がない。普通の Claude は「記憶」を持たないので、毎回ゼロから考える。このスキルがあれば、**ユーザーの過去の思考が常に隣にある**状態で回答できる。

特に AI OSI URI のような「方法論を蓄積するビジネス」では、過去の Concepts（永続ノート）を毎回参照することで、**回答が「ゼロから生成された一般論」ではなく「あなたの思考の続き」**になる。

## トリガーフレーズと挙動

| フレーズ | 挙動 |
|---|---|
| 「vaultから○○について教えて」「知識ベースから」「過去のノートから探して」 | 明示的検索 → 引用付き要約 |
| 「前に何書いたっけ」「自分はどう考えてた？」「私の見解は？」 | 関連 Concepts を探して提示 |
| 「○○案件のときどうした？」「過去の似た案件は？」 | Projects から類似案件を探して教訓を抽出 |
| 「○○さんって誰だっけ？」「あの会社情報は？」 | People / Resources から該当を探す |
| 「Conceptsから○○の関連を」 | 20_Concepts/ に絞って横断検索 |
| 「自分のノートだとどう書いてる？」 | 全フォルダから関連ノートを抽出 |

明示的なフォルダ指定があればそこに絞る。汎用指示なら全フォルダ横断する。

## ワークフロー

### Step 1: vault 構造を理解する（必須・初回）

`mcp__obsidian__obsidian_get_file_contents` で `90_Meta/運用ルール.md` を読む。  
vault がどう組織化されているかを最初に把握する。これによって検索結果の解釈精度が上がる。

すでに同セッション内で読み込み済みなら省略可。

### Step 2: 多角検索

`mcp__obsidian__obsidian_simple_search` で複数キーワードを並列検索。

検索戦略の詳細は `references/search-strategy.md` を参照。基本：

- **概念名そのもの**（「初回提案」「ペルソナ」等）
- **同義語・関連語**（「営業」と「セールス」、「提案書」と「ピッチ」）
- **固有名詞**（クライアント名、人名、案件名）
- **抽象度を上下させた語**（「マーケティング」と「集客戦略」）

1回の検索で結果が薄い場合は、別キーワードで再検索する。**労力を惜しまない**。

### Step 3: 関連ノートを読む

検索でヒットしたノートのうち、関連度が高そうなもの（タイトル・サマリで判断）を `mcp__obsidian__obsidian_get_file_contents` で読み込む。

優先順位：
1. `20_Concepts/` のノート（永続的な思考の核）── 最重要
2. `60_Areas/` のノート（領域 MOC）── 関連 Concepts への入口として
3. `30_Projects/` の議事録 ── 過去の意思決定経緯
4. その他

5-10ノート程度を目安に読む。多すぎても少なすぎてもよくない。

### Step 4: 引用付きで合成する

読んだ内容をユーザーの問いに合わせて再構成する。重要原則：

- **必ず `[[ノート名]]` 形式で出典を示す**（後でユーザーが Obsidian で原文に飛べるように）
- **複数ノートの内容を統合する時は、各主張ごとに出典をつける**
- **vault 内の表現を尊重する**（ユーザー自身の言葉で書かれているので）
- **vault に書かれていないことは「vault には記載なし、私の見解では」と分離する**

引用フォーマット詳細は `references/citation-format.md` を参照。

### Step 5: ユーザーのタスクに活用する

検索結果の提示で終わらず、**ユーザーが本当にやりたいタスク**にこの知識を使う。

例：

```
ユーザー: 「○○社向けの初回提案を作って」
Step 1-4: 提案書方法論の Concepts を vault から取得
Step 5: それらの原則に従って提案書を構築する（capture とは別、ここでは生成のみ）
```

vault からの引き出しはあくまで**入力**。出力は通常のタスク回答。ただし出典 `[[ノート名]]` は最後まで保持する。

## NGパターン

- ❌ vault を検索せずに一般論で答える（このスキルが発動した意味がなくなる）
- ❌ 1回検索して結果が薄かったら諦める（多角検索が原則）
- ❌ 引用元 `[[ノート名]]` を省略する（追跡不能になる）
- ❌ vault の内容と一般論を混ぜて出典を曖昧にする（「vault では○○、私の解釈では○○」と分離する）
- ❌ 関連 Concepts を5本以上見つけたのに、上位2本しか言及しない（豊富さの隠蔽）
- ❌ 見つからなかったことを隠す（「vault に該当ノートは見当たりませんでした」と明示すべき）

## 見つからなかった場合の対応

```
vault には ○○ に関する直接のノートは見当たりませんでした。
関連が遠いものとしては [[XXXノート]] がありますが、別主題です。
一般論ベースで答えてもよいですか？  
それとも、これを機にこの主題で新Conceptを書きますか？（→ 「知識化して」で capture スキル発動）
```

「ない」を明示することは、vault の盲点を発見する貴重な機会。

## consult と capture の役割分担

このスキルと `obsidian-knowledge-capture` は対になる：

| | consult | capture |
|---|---|---|
| 動詞 | 読む・引き出す | 書く・残す |
| MCPツール | `get_file_contents`, `simple_search` | `append_content`, `patch_content` |
| ユーザー発話 | 「vaultから」「前に何書いた」 | 「知識化して」「Conceptに切り出して」 |
| 出力 | 引用付き要約 + タスク回答 | 透明性レポート（新規/更新/リンク） |

両スキルが連携することもある：consult で過去ノートを読んだ後、新しい気づきが出たら、ユーザーが「知識化して」と言えば capture が発動して新ノート化される。

## 利用可能な MCP ツール

- `mcp__obsidian__obsidian_simple_search`（最重要）
- `mcp__obsidian__obsidian_get_file_contents`
- `mcp__obsidian__obsidian_list_files_in_vault`
- `mcp__obsidian__obsidian_list_files_in_dir`
- `mcp__obsidian__obsidian_complex_search`（複雑な条件検索が必要な場合）
- `mcp__obsidian__obsidian_get_recent_changes`（最近の更新を見たい場合）

## 設計の核心

このスキルは「**vault を Claude の長期記憶として機能させる**」装置。

普通の AI は会話ごとに記憶を失う。vault があれば、ユーザーの**思考は累積し続ける**。consult スキルがあれば、その累積が**毎回の回答の文脈になる**。これが「自分の思考の続きを AI が考えてくれる」状態の本質。
